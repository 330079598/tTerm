## 0. 净室边界与本说明的用法

本说明服务于 [P0-09](p0-validation.md#p0-09-终端模型官方-alacritty)、[P0-10](p0-validation.md#p0-10-终端绘制元素)、[P0-12](p0-validation.md#p0-12-滚动滚动条与回滚区锚定)、[P0-13](p0-validation.md#p0-13-原型输入键盘选区剪贴板输入法) 四张实现卡，以及后续的 P2 终端卡。它只描述架构、数据边界、线程模型与取舍，不提供可以逐行翻译的代码、伪代码或 Zed 私有的标识符。

**阅读侧与实现侧分离。** 按[技术选型第 5 节](tech-selection.md#5-终端)的规则，只有本卡执行者阅读了 Zed 的终端源码；P0-09、P0-10、P0-12、P0-13 的实现者不得打开 Zed 的终端 crate。实现者可以读本文、官方 `alacritty_terminal 0.26.0` 的文档与源码、GPUI（`gpui-pre 0.3.11`，经 gpui-kit 0.9.0 带入）的公开接口，以及 tTerm 自己的代码。本卡执行者不参与、后续也不参与上述四张实现卡。

**为什么值得单独写一份说明。** Zed 的终端是在编辑器、工作区、主题、输入法、任务系统和窗口系统里长出来的，直接对照源码实现会把大量与 tTerm 无关的耦合带进来；同时它的许可不允许复制。净室说明的作用是把“可以独立得出的设计判断”与“某个实现的具体写法”分开，让实现者按 tTerm 的约束重新做决定，而不是复刻一个 GPL 项目。

本文的常用术语：

| 术语       | 含义                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------- |
| 终端模型   | `tterm-terminal` 中的对象：持有 Alacritty 的 `Term`，负责解析、网格、回滚区、选区与快照  |
| 视图       | `tterm-terminal-view` 中的 GPUI 实体与绘制元素：负责字体度量、排版、绘制、焦点与输入路由 |
| 快照       | 某一帧开始时从模型取得的只读可见区域数据，视图不持有解析锁                               |
| 显示偏移   | 视口底部相对回滚区底部的距离，0 表示贴着最新输出；增大表示向历史翻                       |
| 回滚区     | 屏幕上方保留的历史行；容量由设置决定，写满后最旧的行被淘汰                               |
| 损坏行     | 自上次快照以来内容发生变化的可见行，附带最小与最大变化列                                 |
| 预编辑文本 | 输入法尚未提交的候选文本，只存在于视图，不写入 PTY                                       |

贯穿全文的几条不变量：

1. 字节解析永远不在界面线程；界面线程只做与可见行数成正比的快照拷贝和排版。
2. 绘制、排版、搜索结果的呈现都不持有解析锁；锁只在“应用命令 + 取快照”这一小段持有。
3. 快照发布后不可变；视图看到的是自洽的一帧，不会在绘制中途看到半更新的网格。
4. 所有写入会话的字节（键盘、粘贴、鼠标上报、查询应答）走同一条有序通道；视图不直接碰 PTY 或 SSH。
5. 每帧最多取一次快照；没有新内容、没有光标动画、没有交互时，不产生新的帧。

## 1. 目标、约束与总体分层

### 1.1 目标

功能目标是与 Tauri 版（xterm.js）一致：屏幕内容、回滚、选区、搜索、链接、输入法、鼠标上报、尺寸变化、调色板与光标行为。性能目标是 [acceptance.md](acceptance.md) 与 P2 卡给出的门槛：P95 帧耗时不超过 16.7ms，持续输出时内存有界，输入与 Ctrl+C 在输出洪峰中仍然及时，30 个后台会话同时输出不影响前台帧率，空闲时不因输出轮询而重绘。

### 1.2 约束

- `tterm-terminal` 不依赖 GPUI、Tauri，也不依赖应用设置与主题；它只依赖 `alacritty_terminal` 与通用工具库。这样 P0-09 的抗崩溃测试、P1 的无界面集成测试都能直接使用它。
- 会话、PTY、SSH、编码转换、背压与平台能力属于 core。终端模型只接收 UTF-8，GBK 等会话编码在 core 转换（P0-09 工作项 4）。
- GPUI 版本通过 gpui-kit 固定为 `gpui-pre 0.3.11` 带入的接口；设计只依赖其中的公开接口，不使用 Zed 应用层的私有能力。
- 不得从 Zed 复制代码，也不得因为参考了 Zed 就引入 GPL 依赖。

### 1.3 分层

| 层       | 位置                     | 负责                                                                                                    | 不负责                                   |
| -------- | ------------------------ | ------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 会话层   | `tterm-core`             | 会话生命周期、PTY/SSH 读写、输出编码转换、有界队列、背压确认、输入有序通道、事件分发、平台能力          | 网格、排版、选区、输入法                 |
| 模型层   | `tterm-terminal`         | Alacritty `Term` 封装、字节写入、resize、回滚容量、快照与损坏行、选区/滚动/搜索的网格操作、链接查找原语 | GPUI、字体、绘制、窗口、输入法候选框     |
| 视图层   | `tterm-terminal-view`    | GPUI 实体与 `Element`、字体度量、行排版与缓存、绘制、焦点、键盘/鼠标路由、输入法状态、滚动条与悬停      | 解析、持久化、会话生命周期、平台打开链接 |
| 平台适配 | `tterm-platform` 与 core | 剪贴板、打开 URL/文件、通知、窗口与输入法平台差异                                                       | 终端状态                                 |

**为什么在“快照”处切开。** 模型与视图之间唯一高频的数据是可见区域快照。把边界定在这里，模型可以完全脱离 GPUI 做单元测试与模糊测试；视图可以在不持有解析锁的情况下排版和绘制；后台标签可以继续解析而不生成快照；将来若需要无界面回放或测试工具，也可以直接驱动模型。反过来，如果让视图直接读网格，绘制时间就会与解析锁耦合，最容易出现“输出洪峰时界面卡住”的问题。

### 1.4 与 Zed 的总体差异

| 关注点   | Zed 的形态                                        | tTerm 的决定                                                      | 理由                                                      |
| -------- | ------------------------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------- |
| 会话归属 | 终端对象同时管理 PTY 与编辑器内的生命周期         | 会话归 core，模型可被视图重新附着                                 | P2-01：视图销毁不结束会话，标签移动/分屏后重新附着        |
| 视图耦合 | 终端视图依赖编辑器、工作区、任务、面包屑          | 终端视图只依赖模型、平台 trait 与 gpui-kit                        | 减少迁移面积；tTerm 的标签与分屏由 P3 自己组织            |
| 绘制     | 视图元素直接读取模型内容并排版                    | 相同思路，但模型只发布快照，视图不持锁                            | 锁边界更清楚，便于后台标签与多视图                        |
| 输入编码 | 模型内部完成按键到字节的转换                      | 编码放在 P0-28 的协议模块，视图调用                               | 输入协议可单独测试；模型不依赖键盘布局与平台修饰键        |
| 变更追踪 | 每帧重建可见区域快照，不消费 Alacritty 的损坏信息 | 第一版可以全量拷贝可见行，但接口必须暴露损坏行，供 P0-10 增量更新 | P0-09 明确要求变更行追踪；30 个后台会话需要更低的拷贝上限 |
| 回滚锚定 | 依赖内核的显示偏移，未额外解决写满后的锚定        | P0-12 必须给出方案，目标是 xterm.js 的行为                        | nyaterm 的补丁证明了这是真实问题；tTerm 不打内核补丁      |

## 2. 模型与视图的职责

### 2.1 模型负责什么

- 接收 UTF-8 字节并推进 Alacritty 的解析器；维护主屏幕、备用屏幕、回滚区、模式、光标、标题、响铃、剪贴板请求、查询应答等终端状态。
- 维护显示偏移、回滚容量、选区锚点与选区文本、搜索匹配的网格坐标、行内链接查找所需的缓存。
- 在锁内应用视图排队的命令：滚动、设置选区、扩展选区、resize、清屏、选择全部、滚动到匹配。
- 产生快照与损坏行；提供“只读快照”的版本号；提供复制选区文本、查找某单元格的链接等低频操作。
- 向 core 发出需要在会话层处理的意图：写 PTY（查询应答、剪贴板读取后的回写）、设置标题、响铃、子进程退出、光标闪烁变化、更新窗口尺寸请求。

模型不负责：字体与像素、光标绘制形状、悬停提示、输入法候选框、滚动条外观、快捷键优先级、剪贴板读写本身。

**为什么选区和滚动偏移放在模型。** 选区的锚点是网格坐标，resize 重排、回滚淘汰、备用屏幕切换都会改变它与屏幕行的关系；如果视图自己保存像素坐标或屏幕行号，重排后就会错位。显示偏移也一样，它是网格状态而不是滚动条状态。反过来，光标是否闪烁、当前悬停的是哪个链接、输入法预编辑到哪里，都是“这一帧的界面状态”，视图重建后可以丢弃。

### 2.2 视图负责什么

- 用字体度量把窗口尺寸换算成行列数，维护单元格宽高、内边距、原点与设备像素吸附。
- 每帧向模型取快照（或增量），把可见行排版成文本 run、背景矩形、搜索/选区高亮、光标与输入法预编辑，并按正确顺序绘制。
- 维护焦点、键上下文、快捷键动作、右键菜单、滚动条交互、悬停链接与工具提示、光标闪烁。
- 把键盘、鼠标、滚轮、输入法事件翻译成模型命令或会话输入；决定哪些事件交给应用快捷键、哪些交给终端。
- 维护输入法的预编辑状态与候选框锚点，把候选框几何以窗口坐标报告给 GPUI。

视图不负责：解析字节、保存历史、直接写 PTY/SSH、决定会话生命周期。

### 2.3 生命周期

一个会话对应一个模型；一个可见终端对应一个视图。视图可以在标签移动、分屏重组、窗口重建时销毁并重新附着到同一个模型。重新附着时不能假设旧快照仍然有效：必须强制全量快照，并让输入法重新取得光标坐标。后台标签的模型继续解析并累积损坏行，但视图不取快照、不排版、不通知重绘；切回前台时再取一次全量快照。

如果将来需要同一个会话在两个分屏同时可见，每个视图应各自持有快照与滚动条状态，而选区、显示偏移这类网格状态仍然只有一份，两个视图会看到相同的滚动位置。这个限制要写进 P3 的分屏设计；在 P0 阶段按“一个模型一个可见视图”实现即可。

## 3. PTY 输出到屏幕：数据流与线程

### 3.1 输出路径

1. 会话层的读取线程从 PTY 或 SSH 通道读到字节，完成会话编码到 UTF-8 的转换、UTF-8 边界拼接与必要的日志/录制。
2. 字节进入每会话的有界队列。队列满时读取线程阻塞，让 PTY 内核缓冲或 SSH 窗口向上游施加背压；不允许无界堆积。
3. 解析线程从队列取出至多一个预算量（例如 16–64 KiB 或 2–4ms 可以处理完的字节数），取得模型的公平锁，推进解析器。
4. 解析线程在字节处理完后检查终止序列、标题、响铃、剪贴板、查询应答等事件；事件不在解析线程里直接碰界面，而是进入 core 的事件通道。
5. 解析线程释放锁。若这一批产生了可见区域的变化，它向视图发一个“有新内容”的唤醒，而不是每个写入都发。
6. 视图在下一帧开始时合并唤醒，取一次快照。取快照时先应用视图排队的命令，再消费损坏行，拷贝需要的行与元数据，然后立刻释放锁。
7. 视图在锁外排版、绘制。绘制期间解析线程可以继续推进下一批；界面不会因为绘制耗时而阻塞解析，解析也不会因为绘制耗时而持有锁。

**为什么解析放在读取侧而不是界面线程。** 持续输出时一秒可能有几十 MB 的字节；即使 Alacritty 的解析器很快，放在界面线程也会把帧预算吃光，输入与 Ctrl+C 的响应会排在输出后面。把解析放到后台线程后，界面线程每帧只处理“可见区域有多大”的数据，最坏情况也有确定上限。

**为什么不是每来一段输出就通知界面。** 通知本身会触发一次帧调度；如果每个 PTY 读取块都通知，输出洪峰时会出现大量无效帧。按批唤醒、每帧最多取一次快照，可以把“解析速度”与“帧率”解耦：解析可以跑得比屏幕刷新快，屏幕只取它需要的最新状态。

### 3.2 线程与锁

| 工作                | 建议线程                    | 是否持有解析锁 | 说明                                       |
| ------------------- | --------------------------- | -------------- | ------------------------------------------ |
| PTY/SSH 读取与解码  | core 的读取线程             | 否             | 只做 I/O、编码转换、UTF-8 拼接、入队       |
| 字节解析            | 每会话一个后台解析任务/线程 | 是，按批持有   | 处理字节、更新网格、收集事件；批间释放锁   |
| 取快照              | GPUI 界面线程               | 是，短时间     | 应用命令、消费损坏行、拷贝可见行；不做排版 |
| 排版与绘制          | GPUI 界面线程               | 否             | 只读快照                                   |
| 搜索                | core 后台线程               | 是，分块持有   | 扫描回滚区；可取消；结果带版本             |
| 复制选区/取选区文本 | 界面线程或后台线程          | 是，短时间     | 只在用户触发时做，不在每帧做               |
| 写输入/查询应答     | core 的有序写入通道         | 否             | 不直接写 PTY；由会话层按顺序发送           |

锁使用 Alacritty 公开的公平互斥锁（`FairMutex`）。选它的原因是：解析线程会连续写入，普通互斥锁可能让界面线程长期拿不到锁；公平锁让已经在等的界面取快照请求在下一批之后得到机会。仅“公平”还不够，解析必须主动分块：每批处理量要有上限，批间释放锁并让出执行权。否则一次 `cat` 大文件会让界面等完整块解析完。

界面线程持锁期间只做 O(可见行数) 的工作：应用少量命令、读取损坏行范围、拷贝行数据、读取光标/模式/选区元数据。绝不在锁内做字体测量、文本 shaping、颜色解析、正则搜索、日志格式化或分配大块内存。

### 3.3 事件与唤醒

解析线程产生的事件分两类：

- **会改变屏幕内容的事件**：普通输出、清屏、resize、备用屏幕切换。它们通过损坏行与“有新内容”的唤醒体现，不单独发送逐字节事件。
- **需要应用层处理的终端事件**：标题变化、响铃、剪贴板读取/写入、颜色查询、窗口尺寸查询、光标闪烁模式变化、子进程退出。它们进入 core 的事件通道，由 core 适配成 `AppEvent`（A3），界面按需订阅。

查询应答有一个额外约束：应答必须与用户输入走同一条有序写入通道。应用可能先发颜色查询再发设备属性查询，如果两个应答由不同路径写回，顺序就会颠倒。模型产生“要写这些字节”的意图，core 把它排在当前输入之后写出；模型不直接持有 PTY 写端。P2-12 会进一步规定每种查询的唯一应答方，P0 阶段先把接口留成“意图 + 有序写回”。

唤醒的合并策略：解析线程每批结束时最多发一次唤醒；界面合并同一帧内的多次唤醒；如果这一批没有产生损坏行、没有状态变化、也没有低频事件，就干脆不发。输入后紧跟的输出（回显、重绘的提示符）可以走快速路径，在很短的窗口内立即唤醒一次，避免按键回声等待一个批处理周期；这与现有 Tauri 版的输入回声窗口一致。

### 3.4 背压与确认

现有 Tauri 版用“未确认字节数”限制 WebView 不要被输出淹没：发送到前端的字节在解析完成后确认，未确认超过约 1 MiB 就暂停发送。原生版的解析在进程内，背压点前移到“读取线程 → 解析线程”的有界队列：

- 解析线程处理完一批后，向 core 报告已消费的字节数，core 据此释放读取线程。
- 队列容量按“一批的最大字节数 × 少量批数”设置，不能按回滚区大小设置。
- 界面取快照的速度不影响背压；即使窗口最小化、标签在后台，解析仍然继续并确认，因为回滚区容量是有界的。
- 输入路径不排在输出队列后面：小量输入直接进入有序写通道，避免 Ctrl+C 被前面的输出拖住。会话层要保证输入与查询应答的相对顺序，但不要求它们等待输出队列清空。

**为什么确认放在解析之后而不是绘制之后。** 解析完成意味着字节已经被吸收进网格，内存占用进入回滚区上限；绘制只是把已有状态显示出来。若等绘制确认，后台标签或最小化窗口会永远不确认，读取线程会被无谓地卡住。P2-02 的验收也要求“背压确认在解析完成后发出”。

### 3.5 被否决的备选方案

- **界面线程解析。** 实现最简单，但输出洪峰直接破坏帧预算与输入延迟，和 P2-02、P2-25 的目标冲突。
- **完全 actor 化：解析线程独占模型，界面只能发命令、收快照。** 锁竞争最小，但滚动、选区拖拽、resize 都需要等一次往返，交互延迟与状态同步复杂；而且复制选区文本、链接查找也要排队。当前选择“共享模型 + 公平锁 + 快照”是在复杂度与延迟之间的折中。若 P0-21 测得锁竞争确实是瓶颈，再考虑把选区/滚动状态复制到视图侧，但不改为完全 actor。
- **无锁通道传每个单元格变化。** 分配与同步开销远大于拷贝可见行；还会让“一帧自洽”难以保证。

## 4. 快照与变更追踪

### 4.1 快照的内容

快照是某一帧的只读视图，至少包含：

| 类别     | 内容                                                                                                       |
| -------- | ---------------------------------------------------------------------------------------------------------- |
| 版本     | 单调递增的版本号；损坏行被消费后递增                                                                       |
| 网格     | 可见行数、列数、单元格宽高（由视图提供，模型只保存最近一次 bounds）                                        |
| 可见行   | 每行的单元格序列：字符、宽字符/占位标志、前景色与背景色（语义色，不是已解析的 RGBA）、属性、链接、零宽附加 |
| 光标     | 网格坐标、形状、是否可见、光标处字符                                                                       |
| 模式     | 应用光标键、插入、换行、括号粘贴、鼠标上报、备用屏幕、焦点上报等                                           |
| 滚动     | 显示偏移、回滚总行数、是否在顶部/底部                                                                      |
| 选区     | 网格起止点、是否块选择；选区文本按需生成                                                                   |
| 搜索     | 匹配的网格范围、活动匹配、版本                                                                             |
| 损坏信息 | 整屏失效标志，或一组“屏幕行 + 最小列 + 最大列”                                                             |
| 底部状态 | 底行是否被占用（用于底部锚定）                                                                             |

颜色保留为 Alacritty 的语义颜色（命名色、索引色、真彩色），由视图在绘制时映射到当前调色板。这样切换主题只需要重绘，不需要重新解析，也不需要模型知道主题。

### 4.2 坐标

快照的可见行按屏幕行编号（0 是视口顶行），而选区、搜索匹配、链接使用网格绝对行。两者通过显示偏移换算：

- 屏幕行 = 绝对行 + 显示偏移。
- 绝对行可以为负，表示在屏幕上方、仍在回滚区内的行；0 是主屏幕的第一行。
- 只有换算后的屏幕行落在 `0..可见行数` 的单元格才会出现在快照里。

**为什么快照按屏幕行存。** 绘制只关心“这一帧第几行画什么”，按屏幕行存可以避免滚动时重排整份数据的索引；选区与搜索仍然保存绝对行，因而在滚动后不需要重新计算，只要在绘制时换算。两者的换算必须只有一处实现，并有单元测试覆盖负行、顶部、底部、回滚淘汰边界。

### 4.3 损坏行与增量

Alacritty 0.26 提供了按行的损坏追踪（`TermDamage`）：整屏失效，或一组带左右边界的行。模型在每次取快照时消费这些信息并重置。

**损坏信息只在原地修改时是逐行的。** 以下按 `alacritty_terminal 0.26.0` 的源码核对（评估时补充，与 Zed 无关）：

- 滚动区域每向上滚一行（输出走到屏幕底部后的每个换行），`Term` 都把整屏标记为损坏。所以 `cat`、编译日志、`tail -f` 这类持续输出时，每一批拿到的几乎都是“整屏失效”，而不是“新增的那一行”。
- 用户翻看历史（显示偏移不为 0）时有新输出，同样走整屏失效，见 4.5。
- 只有不滚动屏幕的修改才给出逐行范围：在提示符打字、TUI 原地重绘（vim、htop、进度条）、光标移动。
- 普通光标的旧位置与新位置每次都会被计入损坏范围，所以光标所在的一两行几乎每帧都“损坏”，这不代表这些行的字符变了。

因此，损坏信息只能回答“哪些行可能变了”，在持续输出时它给不出任何节省。持续输出下的复用要靠 5.4 节按行内容做键的排版缓存：屏幕滚动一行后，其余各行的内容与上一帧相同，只是换了屏幕行号，按内容查缓存仍然命中。内核不告诉模型这一批滚动了多少行（nyaterm 给内核加的滚动计数正是补这个缺口，tTerm 不打该补丁），所以不要设计依赖“滚动行数”的平移复用。

第一版允许“全量拷贝可见行”，但接口必须同时给出损坏行。这样 P0-09 能先交付正确性，P0-10 再用损坏行跳过原地重绘时未变化的行，不需要改模型接口。全量拷贝也只允许拷贝可见区域，不能触碰回滚区；这是 P0-09 评估重点“拷贝量与可见行数成正比”的底线。

推荐的增量形态是行级写时复制：快照中的每一行是一个不可变的行对象，损坏行被替换成新对象，未损坏行复用旧对象。视图持有上一帧的快照，模型发布新快照时只替换损坏行。它只在原地修改时生效：持续滚动输出、resize、备用屏幕切换时整屏失效，走全量拷贝，再由视图的行内容缓存避免重新排版。

**为什么 Zed 每帧重建整份可见内容也够用。** 一个普通终端只有几十行、每行几百个单元格，整份拷贝在桌面 CPU 上通常是微秒级；实现简单，状态自洽，不容易出现“某行忘了更新”的 bug。tTerm 仍然要求损坏行，是因为：P0-09 的验收明确要求；4K/大字号或分屏时可见单元格数可能翻几倍；后台会话数量多时，减少每帧分配能降低分配器压力。先保证正确，再用测量决定是否启用行级写时复制。

### 4.4 失效规则

| 变化                            | 快照动作                         | 原因                                           |
| ------------------------------- | -------------------------------- | ---------------------------------------------- |
| 解析器原地写入（不滚动屏幕）    | 只更新损坏行                     | 损坏信息已经覆盖变化的列                       |
| 输出使屏幕向上滚动              | 整屏失效，排版按行内容命中缓存   | Alacritty 对每次屏幕滚动报整屏损坏（见 4.3）   |
| 滚轮/滚动条改变显示偏移         | 整屏刷新                         | 屏幕行与绝对行的对应关系整体改变               |
| resize、字体/DPI 改变单元格度量 | 整屏刷新                         | 行列数、换行与重排都可能变化                   |
| 主屏幕与备用屏幕切换            | 整屏刷新                         | 单元格来源与回滚语义不同                       |
| 选区、光标、模式变化            | 只更新元数据，必要时重绘相关区域 | 不改变字符内容                                 |
| 主题/调色板变化                 | 不改快照，只重绘                 | 快照保存语义色                                 |
| 搜索匹配变化                    | 更新匹配元数据                   | 匹配范围是绝对行，绘制时换算                   |
| 回滚区写满后淘汰最旧行          | 至少整屏刷新，并重新计算锚点     | 绝对行号与历史行身份不再稳定（P0-12 专门处理） |
| 子进程退出、清屏                | 按解析结果产生损坏行或整屏刷新   | 清屏可能改变整屏                               |
| 视图重新附着                    | 强制整屏刷新                     | 旧快照可能已经过期                             |

**为什么选区与光标变化不算“内容损坏”。** 它们不改变字符与颜色，只改变覆盖层。把它们混进损坏行会让每个光标移动都导致整行重排；正确做法是快照里带上元数据版本，绘制时只重画覆盖层。Alacritty 的损坏信息也不包含选区与 Vi 光标，这一点与它的设计一致。

### 4.5 与滚动锚定的关系

用户向上滚动后，新输出到来时 Alacritty 会增加显示偏移，让视口继续看着同一段历史。此时可见内容没有变化，但 Alacritty 仍然报整屏损坏（4.3），不能靠损坏信息发现“其实没变”。模型可以重新拷贝可见行（代价与可见行数成正比），由视图的行内容缓存全部命中；也可以记录取快照时的显示偏移与回滚行数，二者同步增加且未到上限时判定视口内容不变，直接沿用上一份快照。后一种做法要有测试证明判定正确，否则用前一种。回滚区写满后，显示偏移被上限钳住，最旧的行开始被淘汰，视口里的行可能在同一帧内整体上移；这时必须整屏刷新，并把“用户原本盯着的锚点”单独保存。P0-12 的核心难点就在这里，详见 6.2。

## 5. 绘制：排版与缓存

### 5.1 单元格度量

视图每帧（或尺寸/字体/DPI 变化时）计算：

- 单元格宽度：用等宽字体的 `m` 前进宽度，通过 GPUI 文本系统的字体度量取得；不要用平均宽度或测量整行后除列数。
- 行高：字号乘以设置中的行高倍数，再按设备像素取整。
- 行列数：可用像素除以单元格宽高后向下取整，并加一个极小的容差，避免浮点误差把最后一行/列吃掉。
- 原点：按设备像素吸附，避免窗口缩放或分屏拖动时字形在亚像素位置抖动。
- 最小宽度：至少保留两个单元格的宽度。Alacritty 在只有一列宽时渲染某些 emoji 会出错，这是上游已知问题；把下限设成两列比在绘制层做特判更稳。

**为什么用 `m` 的宽度。** 终端网格要求所有单元格等宽；等宽字体中 `m` 通常是最宽的标准字符，字体设计也以它作为前进宽度的基准。用整行测量再平均会把宽字符、emoji、组合字符的宽度差异摊进单元格，导致光标与列对不齐。宽字符仍然占两列，由 Alacritty 的单元格标志决定，不靠测量。

**为什么原点要吸附设备像素。** 终端是网格渲染，允许小数原点会让相邻字形的栅格化位置在帧之间跳动，表现为整屏轻微闪烁；窗口拖动、分屏调整时尤其明显。横向原点按缩放因子向下取整，纵向按行高取整，可以消除这类抖动。

**为什么要有底部锚定。** 当窗口高度不是行高的整数倍时，多出来的像素如果放在顶部，提示符会离底边很远；如果放在底部，内容会贴底。Zed 在独立终端模式下把可用高度向下取整到整行，并在“备用屏幕”或“底行被占用”时把余量放到顶部，让最后一行贴着底边。tTerm 目标是与 xterm.js 一致，采用同样的底部锚定；具体余量放顶部还是底部要有截图对比。

### 5.2 排版流水线

1. 只取快照中与当前裁剪区域相交的可见行。终端被分屏、抽屉或滚动容器裁剪时，屏幕外的行不参与排版。
2. 按行分组；同一行内，把字体、字号、前景色、背景色、下划线、删除线、链接样式相同的连续单元格合并成一个文本 run。合并只发生在同一行且列连续的情况下，跨行一定断开。
3. 背景色不是默认背景的单元格，合并成背景矩形；同色、同行且相邻的矩形可以继续合并；跨行的同色区域可以按行拆成多个矩形，或按列区间合并。矩形数量要远小于单元格数。
4. 空白单元格、宽字符的占位单元格、没有可见样式的空格不产生文本 run，只可能产生背景矩形。
5. 方框绘制字符、块元素、Powerline 分隔符先用字体自带字形；P0-28 移植 Alacritty 的内置字形后，再替换成按子单元格绘制的矩形/路径，以消除字体接缝。
6. 光标单独排版：块、下划线、竖线、空心块；宽字符或 emoji 上的光标宽度取“字形宽度与单元格宽度的较大者”，空白字符用单元格宽度，避免光标被拉宽或缩窄。
7. 输入法预编辑文本、搜索/选区高亮、悬停下划线是覆盖层，不参与普通文本 run 的合并。

### 5.3 样式解析

- 反显：交换前景与背景。
- 默认背景：不画背景矩形，直接透出终端背景。
- 最小对比度：为可读性调整前景色；但两类颜色不调整：应用明确指定的真彩色/高位索引色，以及方框、块元素、Powerline 等装饰字符。前者是应用有意为之，后者必须与相邻背景精确衔接，调色会产生接缝。
- 链接：悬停时加下划线和高亮色；普通状态下按 OSC 8 或识别结果决定是否加下划线。
- 下划线/删除线：随文本 run 一起传给文本系统；双下划线、波浪线等扩展样式按 GPUI 的支持程度降级，不能支持的记录为差异。
- 选区与搜索高亮：作为半透明色块画在文本下方，圆角半径跟设置；活动搜索匹配与普通匹配用不同颜色。

### 5.4 缓存

终端层的缓存单位是“行布局”，不是整屏：

- 键包含：该行的字符内容、每个 run 的样式、字体（族、字重、特性、回退链）、字号、单元格宽度、缩放因子、主题版本。
- 值包含：合并后的文本 run、背景矩形、装饰字符矩形、行内链接范围。
- 只有损坏行、主题变化、字体/DPI/宽度变化、行内容变化时才重建；滚动只是把已有行布局按新的屏幕行位置复用。
- 搜索/选区高亮不进入行布局缓存，它们是覆盖层，随元数据变化单独生成。

GPUI 的文本系统本身对相同文本、相同字体 run 的行布局有跨帧复用（保留上一帧与当前帧），所以“同一行文本不变”时重复调用 shaping 不一定重新栅格化。但终端的批处理、样式解析、背景合并仍然每帧发生；终端层缓存的价值是避免这些工作，并让“只重排损坏行”成为可控的行为，而不是依赖文本系统的内部缓存。P0-10 的评估重点“每帧的排版是否有缓存”应当用缓存命中率和 prepaint 耗时分项证明。

**为什么不在绘制时读模型。** 绘制可能因为遮挡、动画、输入法候选框而重复发生；如果每次绘制都锁模型、重新扫描网格，输出洪峰时会把解析线程拖慢。快照把“取数”与“画”分开，绘制只读不可变数据。

### 5.5 绘制顺序与裁剪

1. 终端背景与内边距。
2. 非默认背景矩形。
3. 搜索匹配与选区高亮（半透明覆盖）。
4. 普通文本 run。
5. 下划线/删除线/链接装饰。
6. 光标（如果可见且没有预编辑文本）。
7. 输入法预编辑文本及其背景。
8. 视图自己的覆盖层（搜索栏、提示条等由 GPUI 兄弟元素绘制，不进入终端元素）。

使用 GPUI 的内容裁剪，只绘制与可见区域相交的行；整个终端被滚出视口时直接跳过排版。绘制期间不持有模型锁；所有数据来自快照。

### 5.6 空闲与动画

没有输出、没有交互、光标不闪烁时不应产生帧。光标闪烁是唯一的常驻动画：只在获得焦点、光标可见、光标形状允许闪烁时，以固定周期切换并请求重绘；失焦、输入法预编辑、备用屏幕隐藏光标时停止。闪烁造成的重绘只改光标覆盖层，不应触发整屏重新排版；评估时把“空闲无光标闪烁”和“空闲有光标闪烁”分开记录，后者按动画帧计算，不算输出轮询。

## 6. 滚动、选区、搜索、链接

### 6.1 坐标与边界

- 绝对行：网格中的行号，0 是主屏幕顶行，负值向上进入回滚区。
- 显示偏移：视口底边相对最新输出的距离；0 表示贴底，增大表示向上翻。
- 屏幕行：视口内的行号，0 是顶行；换算见 4.2。
- 列：0 起；宽字符占两列，第二列是占位，不参与文本选择。

所有“像素 → 单元格”的换算放在视图，使用当前快照的单元格宽高与原点；所有“单元格 → 字节/选区/搜索”的换算放在模型。像素换算要钳制到网格内：点在终端外时，选区拖拽用最近的行/列，鼠标上报则丢弃或按模式处理。

### 6.2 滚动

滚动来源有四类，必须统一到“显示偏移”这一个状态：

- 滚轮：以像素为单位累积，除行高得到整行增量；小数余量保留到下一次，方向反转或到达边界时把余量清零，避免“滚了半行没反应，再滚一下跳两行”。
- 键盘/动作：行、页、顶部、底部。
- 滚动条：拖动滑块直接设置显示偏移；滑块几何由总行数、可见行数、当前偏移算出，拖动结果按行取整。
- 程序输出：不改变用户意图；贴底时跟随新输出，向上翻时保持视口内容不变（见下）。

鼠标上报模式下滚轮不滚动本地视图，而是按终端协议上报；备用屏幕开启且应用允许 alternate scroll 时，滚轮转成上/下方向键序列。按住 Shift 时强制本地滚动，作为鼠标上报的逃逸。

**回滚区写满后的锚定。** 当视口不在底部时，新输出会让 Alacritty 增加显示偏移，视口继续看着同一段历史；这是一条隐含的“锚定”。但显示偏移有一个上限（回滚容量）。写满之后，最旧的行被淘汰，绝对行号整体前移，显示偏移被钳在上限，视口内容会在下一次输出时发生位移。用户看到的是：正在读历史，突然跳行或闪烁；如果此时选着文本，选区也会跟着错位。nyaterm 为此给内核加了滚动计数，tTerm 不采用带补丁的内核。

P0-12 要在不改内核的前提下解决，候选方向有三类：

1. **视口内容比对**：在写满边界附近记录视口首行/末行的内容指纹或稳定标识，新输出后比较，推算出实际移动的行数，再调整显示偏移。实现不需要内核补丁，但指纹碰撞、重复行、宽字符都要处理。
2. **行身份**：模型维护“绝对行 → 单调行号”的映射，淘汰时更新；滚动时用行身份而不是绝对行号锚定。需要额外的每行元数据，内存与淘汰逻辑要仔细。
3. **上游补丁**：向 Alacritty 官方提交滚动计数补丁，合入前接受与 xterm.js 一致的退化行为。不得 fork。

无论选哪种，行为基准都是现有 xterm.js 版：滚动时历史不丢失、不跳行；写满后不在底部时快速输出不闪烁；锚定行被淘汰时有确定行为。P0-12 必须把方案写成决策记录，并给三类场景的自动化测试。

**为什么滚动偏移放在模型而不是视图。** 视口内容由网格、显示偏移和回滚淘汰共同决定；如果视图自己保存“滚到第几行”，淘汰后这个数字会指向另一行。模型持有显示偏移，才能在输出、resize、备用屏幕切换时一并修正。

### 6.3 选区

选区状态机：

- 按下：记录锚点（网格点 + 侧别），左键单击开始普通选区；双击选词，三击选行。双击/三击的选择类型由模型解释，视图只传点击次数。
- 拖动：移动超过阈值（约 2 个逻辑像素）才开始扩展，避免“窗口聚焦的那一下点击”把剪贴板里的内容替换成单个字符。拖动到终端外时按距离加速自动滚动，每帧最多滚动少量行，并先更新选区再滚动，顺序与 Alacritty 一致。
- 松开：结束选择；若开启“选中即复制”，把选区文本写入剪贴板；若按下与松开落在同一个链接上，打开链接而不是复制。
- Shift：鼠标上报模式下强制本地选择；已有选区时 Shift+点击扩展而不是重新开始。
- 失焦：选区状态由模型保留，是否显示活动高亮由视图决定；与 Tauri 版对比后再固定这一行为。
- 重排/淘汰：选区锚点存绝对行。行数变化时 Alacritty 会按行偏移旋转选区；列数变化时 Alacritty 会直接清空选区，tTerm 要在这个时点明确告知用户或恢复选区。回滚淘汰后锚点可能指向另一行，不能假装它仍然正确；按 P0-12 的锚定方案重定位，无法重定位时清除选区并记录这一退化。

**为什么选区文本按需生成。** 选区可能覆盖几十万行回滚；每帧生成字符串会浪费内存与时间。快照只带选区范围，复制时才生成文本。小选区可以在界面线程持锁生成后立即释放；大选区放到后台线程，锁只覆盖文本提取那一段，界面只接收结果，不能等字符串生成完才返回。

### 6.4 搜索

搜索是“用户显式发起、可能很重”的操作，不能放在界面线程：

- 视图把查询、选项（正则、大小写、整词）和当前版本交给模型；模型在后台线程分块扫描回滚区，定期释放锁，允许取消。
- 结果是一组绝对行范围 + 一个版本号；扫描期间如有新输出、resize、滚动淘汰，版本失效，旧结果丢弃或标记为过期。
- 视图只渲染当前快照内可见的匹配；活动匹配用不同颜色，并在选中时滚动到匹配起点。
- 下一个/上一个按光标位置或当前活动匹配移动；没有活动匹配时从光标附近开始。
- 持续输出时，搜索结果的绝对坐标可能因淘汰而漂移；不能简单地平移旧结果，必须按版本重新扫描或维护行身份。P2-07 要给出 10 万行回滚的耗时数据。

**为什么不在每次输出后自动重跑搜索。** Zed 的做法是每次唤醒都让搜索 UI 失效，简单但会在输出洪峰中反复扫描。tTerm 应在“网格行数变化/淘汰/resize”时失效，而不是光标移动或选区变化时失效；同时给搜索加去抖与取消，避免用户输入查询时堆积后台任务。

### 6.5 链接

链接识别按优先级：

1. 单元格上的 OSC 8 超链接：直接取 URI 与范围，范围可能跨多行、跨单元格。
2. 行内 URL：按协议前缀识别，去掉尾部标点；识别范围必须在同一逻辑行内，跨行的 URL 不作为链接。
3. 文件路径：按配置的正则与超时识别，相对于该行对应的当前工作目录；支持 `路径:行:列` 形式。路径是否存在由平台层异步判断，判断结果只影响悬停提示与可点击状态，不阻塞终端。

交互：

- 悬停需要按住平台的主修饰键（macOS 的 Command、Windows/Linux 的 Ctrl）；鼠标移动超过一小段距离或经过一小段时间才重新查找，避免每个像素都锁模型。
- 找到链接后记录范围与一个递增的链接 ID；视图显示手型光标与提示，提示内容可以是 URL 或解析后的绝对路径。
- 点击时要求按下与松开在同一链接；在鼠标上报模式下，主修饰键点击链接要抑制按下上报，并吞掉后续移动/松开，避免发给应用一个没有按下的“松开”序列。
- 打开 URL/文件走平台 trait，不在终端模型里直接调用系统 API；路径打开失败要有用户可见提示。

**为什么链接查找放在模型。** 链接范围是网格坐标，跨行、宽字符、零宽字符都影响范围；只有模型能看到完整行与 OSC 8 数据。视图只保存“当前悬停的链接 ID/范围”，鼠标移开即可丢弃，不需要理解网格。

## 7. 输入法

### 7.1 目标与状态

输入法要解决四件事：预编辑文本显示在光标处；候选框跟着光标但不追逐 TUI 自己画的假光标；组合期间的按键不被终端当成普通输入；提交的文本只发送一次。

视图维护一个组合状态：空闲、组合中。组合中保存预编辑字符串、预编辑内的选中范围、组合开始时的锚点单元格。预编辑文本只存在于视图；模型和 PTY 只看到提交后的 UTF-8 文本。

### 7.2 GPUI 输入接口的映射

GPUI 通过 `InputHandler` 把平台输入法的请求转给焦点元素。终端视图需要提供：

| 平台请求         | 终端视图的回答                                              | 理由                                                                |
| ---------------- | ----------------------------------------------------------- | ------------------------------------------------------------------- |
| 选中文本范围     | 始终返回光标处的空范围（0..0）                              | 终端没有可编辑文档；候选框应以光标为锚点，即使备用屏幕/TUI 隐藏光标 |
| 预编辑范围       | 返回预编辑字符串的 UTF-16 长度                              | 平台据此知道哪些文本还在组合中                                      |
| 取指定范围文本   | 返回空                                                      | 终端不向输入法暴露回滚内容                                          |
| 替换文本         | 清空预编辑状态，把文本编码后交给会话输入通道                | 这是提交路径；只发一次                                              |
| 替换并标记       | 更新预编辑字符串与选中范围，不发送                          | 这是组合路径                                                        |
| 取消标记         | 清空预编辑状态                                              | 组合取消或窗口失焦                                                  |
| 范围的窗口坐标   | 光标单元格的原点 + 预编辑内偏移，宽至少一个单元格、高为行高 | 候选框定位                                                          |
| 点对应的字符索引 | 返回空或按单元格宽度估算                                    | 终端不需要平台选择手柄                                              |
| 长按重音菜单     | 关闭                                                        | 终端按键应直接进入 shell，不弹系统重音菜单                          |

**为什么始终返回空选中范围。** 如果返回终端选区的实际范围，输入法会以为自己在一段可替换文本里工作，候选框可能跑到选区两端，提交时还可能试图替换整段选区。终端的光标位置才是输入法锚点；选区是剪贴板概念，不是编辑概念。

### 7.3 预编辑的绘制

- 预编辑文本画在组合锚点单元格处，先画一块终端背景色的矩形盖住原字符，再画带下划线的预编辑文本；文本可以超出单元格宽度，但不能换行。
- 组合期间不画硬件光标，避免光标与预编辑文本重叠。
- 组合期间如果有新输出，预编辑文本保持在锚点；不要跟着终端光标移动，否则 TUI 的旋转指示器会让候选框满屏跳。锚点在新输出导致锚点行滚出视口时，按 7.4 的隐藏光标策略处理。
- 提交后立即清空预编辑，把文本发送到会话；不要在下一帧继续绘制残留。

### 7.4 候选框定位

GPUI 用 `bounds_for_range` 的返回值放置候选框，平台通常在组合开始前就会读取一次。实现要注意：

- 返回窗口坐标，不是终端元素内的相对坐标；要把快照原点、内边距、滚动偏移都算进去。
- 光标移动、滚动、resize、DPI 变化、标签切换后要让平台重新读取，否则候选框会停在旧位置。GPUI 提供的字符坐标失效通知要在这些时机调用。
- 组合开始时记录锚点；组合期间光标因输出移动，不更新候选框锚点。这是 tTerm 现有 WebView 版 `imeCursorGuard` 的核心行为：避免 TUI 隐藏/移动光标时候选框追逐。
- 光标被应用隐藏时：短暂隐藏（约 500ms 内）视为重绘中间态，沿用最后一次可见光标位置；长时间隐藏视为 TUI 自己画光标，使用当前光标位置。这个阈值需要实机验证，放进设置或常量并在 P0-18/P2-11 调整。
- Windows 的输入法在组合开始前就可能读取候选框位置；必须在安装、聚焦、resize、单元格尺寸变化时预先放置锚点，不能等组合开始才第一次报告。
- 备用屏幕（vim、tmux、htop 等）仍然有光标位置，候选框应锚定它；不要因为备用屏幕就返回空范围。

### 7.5 按键与重复提交

- 组合期间，平台会把按键交给输入法；视图的普通按键处理要先看“是否优先字符输入”，是则直接返回，不编码、不发送。
- 组合中的 Enter、Escape、方向键属于输入法；组合结束后平台可能再发一次按键事件。要用组合状态与事件顺序去重，不能把确认候选词的 Enter 又发给 shell。
- 提交文本只走“替换文本”路径；不要同时从按键处理里再发一次字符。
- 粘贴与输入法提交是两条路径，但都要经过会话输入通道；括号粘贴模式只影响粘贴，不影响输入法提交。
- 组合中切换标签、窗口失焦、终端重置时，要取消组合并清空预编辑，通知平台取消标记。

### 7.6 与现有四个输入法修复的关系

Tauri 版有四个针对 WebView 的输入法修复：光标守卫、上下文清理、提前输入、焦点修复。原生版的判断原则是：

- **光标守卫**：修的是“候选框追逐 TUI 假光标/隐藏光标”的终端层问题，原生版需要同等行为，落在 7.4。
- **上下文清理**：修的是 WebView 隐藏 textarea 里残留文本导致拼音与数字之间插入空格，属于 WebView 实现细节；原生 GPUI 没有这段 textarea，预计不需要，但要由 P2-11 在 macOS 拼音下实测确认。
- **提前输入/焦点修复**：大概率是 WebView 的焦点与合成事件时序问题；原生端如果 GPUI 的输入法事件顺序正确，不需要照搬。P2-11 逐项审查并写结论。
- 任何从 WebView 时代继承的行为，都不能未经验证直接搬进原生版；以 P0-16、P0-18 的实机矩阵为准。

### 7.7 测试

至少覆盖：macOS 拼音/五笔、Windows 微软拼音、Linux fcitx5（X11 与 Wayland）；组合中输出洪峰；组合中滚动；组合中 resize；候选框在光标贴近右/下边缘时的翻转；备用屏幕 vim/tmux；组合中切换标签；组合提交后 Enter 不重复发送。每个场景要有录屏或截图与事件日志。

## 8. 按键与鼠标事件的路由

### 8.1 事件层级

GPUI 把事件送到拥有焦点的元素。终端元素的 hitbox 负责判断指针是否在网格内；视图负责决定事件是应用快捷键、终端输入还是本地选择；模型只接收“已经决定要写什么”的字节或“要改变什么状态”的命令。

- 键盘：窗口 → 焦点元素 → 视图按键处理 → 若终端处理则停止传播，否则交给应用快捷键。
- 鼠标：元素 hitbox → 视图/模型鼠标处理 → 写上报字节或改变本地选区/滚动。
- 滚轮：元素滚动处理 → 视图决定本地滚动、备用屏幕方向键、或鼠标上报。
- 输入法：平台 → GPUI 输入处理 → 视图的输入处理器；普通按键处理在组合期间让路。

### 8.2 键盘

1. 组合中或事件标记为优先字符输入：交给输入法，不进入终端编码。
2. 否则把 `Keystroke` 与当前模式交给 P0-28 的协议模块编码。模式至少包括：应用光标键、应用小键盘、插入、换行、括号粘贴；若 P0-28 支持 kitty 键盘协议，还要带上该协议的标志。
3. 编码成功：把字节交给会话输入通道；停止事件传播，避免同一按键再触发应用快捷键。
4. 编码失败：不消费事件，让快捷键系统处理（复制、粘贴、搜索、切标签、字体缩放等）。
5. 焦点进入/离开：若应用开启了焦点上报模式，发送对应的 CSI 序列；失焦时把光标画成空心或隐藏，停止闪烁。
6. 粘贴：读取剪贴板文本，按括号粘贴模式包装，过滤粘贴内容中的控制序列；是否弹出多行确认由 P2-05 决定。粘贴不经过按键编码。
7. Vi 模式：如果 P2 决定支持，Vi 动作应在视图层拦截，不发送给 shell；当前 P0 不要求。

**为什么键盘编码不放在模型。** 编码依赖平台修饰键、键盘布局、应用快捷键优先级与用户设置（例如 macOS 的 Option 作为 Meta）；这些都属于视图/平台层。模型只关心模式位与最终字节。把编码放在独立模块（P0-28）可以逐条对照测试，不会把输入协议与网格状态混在一起。

### 8.3 鼠标

鼠标处理的核心判断是“这次事件属于本地选择，还是属于应用”：

1. 应用是否开启了鼠标上报（1000/1002/1003 等模式），且用户没有按住 Shift 强制本地选择。
2. 是否按住了平台主修饰键并且指针下有链接；如果是，优先链接手势。
3. 是否是右键：鼠标上报模式下右键也上报；否则弹出终端上下文菜单。
4. 是否是中键：Linux 上的中键粘贴主选区是目标行为，具体在 P2-04 按 Tauri 版确认；其他平台按设置或忽略。

具体路由：

- 左键按下：聚焦终端。若主修饰键 + 链接：记录按下时的链接，抑制上报。否则若上报模式：发送按下报告；否则记录选区锚点。
- 移动：上报模式下只在单元格变化时发送移动报告，避免每个像素都发；本地选择模式下超过拖拽阈值后扩展选区；指针移出终端时自动滚动。
- 左键松开：上报模式下发送松开；本地选择结束，按设置复制；若按下/松开在同一链接，打开链接。若之前抑制了按下上报，松开必须吞掉，不能发出没有按下的松开序列。
- 右键：上报模式下发送按下/松开；否则显示上下文菜单，菜单操作走应用动作。
- 滚轮：上报模式下发送滚轮报告；备用屏幕 + alternate scroll 时发送方向键；否则本地滚动。
- 双击/三击：按点击次数选择词/行；点击计数由平台提供，视图传给模型。
- 悬停：主修饰键 + 指针在网格内时，节流查找链接；移出或松开修饰键时清除悬停。

**为什么鼠标上报要“只在单元格变化时发送”。** 终端协议里鼠标位置是单元格坐标，同一单元格内的像素移动对应用没有意义；每个像素都发会让应用收到大量重复事件，甚至触发它自己的节流。Zed 与 Alacritty 都做这个去重。

**为什么 shift 是逃逸键。** 应用开启鼠标上报后，用户仍然需要能选中文本复制。Shift 是事实标准；macOS 上 Option 也可以作为替代。这个判断必须在“是否上报”之前做，否则选不中。

### 8.4 事件顺序与状态

视图做决定时使用当前快照里的模式与显示偏移，不额外加锁；决定之后把命令排入模型队列或把字节排入会话通道。模型在下一帧取快照前按入队顺序应用命令。这样：

- 滚动、选区、resize 的顺序确定；
- 鼠标上报使用的模式不会在事件处理中途变化；
- 不会出现视图持锁等待、模型持锁解析的交叉阻塞。

如果某一帧内同时有输出、滚动和选区扩展，先应用视图命令，再消费损坏行，最后生成快照；用户看到的仍然是“先滚动、再看到新内容”的自洽结果。这个顺序要在测试里固定下来。

## 9. resize

### 9.1 触发与顺序

resize 可能由窗口、分屏、侧栏、字体、字号缩放、DPI/显示器切换、主题行高变化引起。顺序固定为：

1. 视图重新测量字体与可用区域，算出新的列数、行数与单元格尺寸。
2. 如果行列数或单元格尺寸没有变化，什么都不做，避免每帧都发 resize。
3. 视图把新的网格尺寸交给模型；模型在锁内更新边界、执行 Alacritty 的重排、记录损坏行。
4. 模型把“需要通知 PTY/SSH 新窗口尺寸”的意图交给 core；core 发送 `SIGWINCH`/窗口尺寸消息。
5. 下一帧视图取到整屏失效的快照，重新排版。

**为什么先模型后 PTY。** 如果先告诉 PTY 新尺寸，应用可能立刻按新尺寸输出，而模型还没重排，字节会被按旧网格解释。先让模型知道新尺寸，再让应用知道，能减少一帧的错位。反向的顺序在快速拖动时会出现闪烁与错行。

### 9.2 合并与节流

拖动窗口边缘/分隔条时，每帧都可能得到新的像素尺寸，但只有行数或列数真正变化时才需要 resize。视图应：

- 只在行列数或单元格尺寸变化时入队。
- 合并待处理的 resize：队列尾部已有 resize 时替换它，而不是追加一串。
- 对 PTY 的 resize 也做合并；一次拖动结束后只发最后一个尺寸。
- 用一个单调递增的 generation 标记 resize；旧 generation 的迟到事件丢弃，避免“缩小后又被旧的大尺寸覆盖”。

**为什么不能每个像素都发。** 每次 resize 都会触发 Alacritty 的换行重排与应用的重绘；高频 `SIGWINCH` 会让 vim/tmux 疯狂重绘，表现为闪烁与卡顿。Zed 在入队前合并同一尺度的 resize，正是为了避免这个现象；tTerm 的 P2-22 也要求拖动分隔条不卡顿。

### 9.3 重排与状态

- Alacritty 对主屏幕做换行重排；备用屏幕通常不重排，避免全屏应用内容错位。
- 光标、选区、显示偏移、搜索匹配都要在重排后修正。列数变化时，按行保存的工作目录历史与链接缓存要失效；行数变化时，选区端点可能落在屏幕外，要钳制。
- resize 后整屏失效，不能沿用旧的行缓存；字体/DPI 变化还要清空文本 shaping 缓存。
- 如果用户正在向上滚动，resize 后应尽量保持视口内容稳定；做不到时至少保持显示偏移不跳到底部。
- 备用屏幕切换与 resize 同时发生时，以最终的网格状态为准；用 generation 防止旧 resize 覆盖新状态。

### 9.4 测试

拖拽窗口边缘、拖拽分屏、改变字体、改变字号、跨不同 DPI 显示器移动、从最大化恢复、在 vim/tmux/htop 中 resize；每一步检查行列数、光标位置、选区、滚动位置、PTY 收到的尺寸与屏幕内容。P0-13 只要求原型可用，完整的 P2-22 再扩展。

## 11. 对实现卡的约束与验收建议

### P0-09 终端模型

- `tterm-terminal` 不依赖 GPUI、Tauri；只依赖 Alacritty 与通用库。
- 解析在后台，界面取快照时锁持有时间与可见行数成正比；不得在锁内排版。
- 提供完整可见快照、损坏行、版本号；第一版可全量拷贝可见行，但接口保留增量能力。
- 不复制回滚区到快照；不因回滚区变大而变慢。
- 抗崩溃测试：随机字节与手写边界序列至少 10 万组无 panic；报告给出种子与运行时间。
- 报告声明未阅读 Zed 终端源码。

### P0-10 终端绘制元素

- 由字体度量算单元格宽高与行列数；宽字符、emoji、零宽字符、方框/Powerline 字符有专门处理。
- 行级排版缓存，以行内容与样式为键；原地修改时只重排损坏行，持续滚动输出时按行内容命中缓存（Alacritty 此时报整屏损坏，见 4.3）；字体/DPI/主题变化清空。
- 缓存命中率至少分三种负载分别报告：原地重绘（如 htop）、持续滚动输出（如 `cat` 大文件）、用户翻看历史时有输出。
- 调色板类型放在 `tterm-terminal`，字段对应 `src/lib/terminalPalette.ts`；绘制时映射语义色。
- 空闲不重绘（光标闪烁按动画单独计）；后台标签不排版。
- GPUI profiler 记录每帧 prepaint/paint 耗时与缓存命中率，供 P0-21/P2-25。
- 报告声明未阅读 Zed 终端源码。

### P0-12 滚动、滚动条与回滚锚定

- 小数滚动累积、边界限制、显示偏移；滚动条几何、拖拽、搜索标记。
- 后台标签继续解析，停止快照与通知。
- 回滚写满后的锚定必须给出不改内核的方案，或明确接受与 xterm.js 一致的退化行为；不得 fork Alacritty。
- 三类自动化测试：滚动时历史丢失/跳行；写满后不在底部时快速输出闪烁；锚定行被淘汰。
- 报告声明未阅读 Zed 终端源码。

### P0-13 原型输入

- 键盘编码接 P0-28；鼠标选区、复制粘贴、输入法预编辑与候选框定位可用。
- 输入法遵循 7.2–7.5；至少在三平台 shell 中完成中文输入、复制、粘贴。
- 记录未实现的按键、鼠标模式与输入法场景。
- 报告声明未阅读 Zed 终端源码。

### 共同约束

- 不把 Zed 的代码、注释、类型名或测试搬进 tTerm；不引入 GPL 依赖。
- 第三方代码（如果后续从 Alacritty/nyaterm 复制）按 README 执行规则第 6 条登记，保留许可与来源。
- 所有坐标换算、选区、滚动、输入法的关键路径有单元测试；测试断言用户可见结果，不只断言内部字段。

## 12. 开放问题

1. **回滚写满后的锚定算法**：视口内容比对与行身份各有成本；需要在 P0-12 用真实负载比较，并确认宽字符/重复行下的稳定性。
2. **Windows 输入法**：gpui-pre 的候选框时序与光标更新是否足够；P0-18 与 P2-11 实机验证，必要时按决策 007 第 4 条给 gpui-pre 打补丁（不 fork 整个 Zed）。
3. **多视图共享会话**：分屏同时显示同一会话时滚动位置与选区如何共享；P3 再决定，当前按一模型一可见视图实现。
4. **搜索大回滚区的锁竞争**：后台分块扫描是否会让解析饥饿；需要 P2-07 的 10 万行数据与锁等待指标。
5. **动态回滚容量**：Alacritty 的 `set_options` 可以调整历史容量，但缩容会丢弃历史；P2-06 要定义“修改设置后不重开会话”的语义与内存释放时机。
6. **字体回退与字形溢出**：中文、emoji、Nerd Font 符号的宽度可能超过网格；需要确定裁剪还是允许溢出，并以截图对比为准。
7. **空闲光标闪烁与“空闲不重绘”的验收口径**：建议把闪烁算作动画帧，单独记录；P0-10 与 P2-25 统一口径。
8. **剪贴板与 OSC 52 的异步性**：平台剪贴板可能是异步的，终端查询应答与写入顺序要避免在等待剪贴板时阻塞解析线程。
