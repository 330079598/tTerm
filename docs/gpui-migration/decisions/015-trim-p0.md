# 015 收窄 P0，尽快进入 G1；性能对比最后统一做

- 日期：2026-11-09
- 决策人：stone
- 状态：已决定

## 背景

到 2026-11-09，P0 已经回答了"能不能在官方 Alacritty 和 GPUI 上搭出可用的终端"：P0-09 至 P0-15 跑通了模型、绘制、输入、输入法、回滚与本地 PTY，P0-24 的 8 个组件在 macOS 深浅两种主题下达标，P0-26 验证了从 Tauri 版自动升级。

剩下的 P0 卡不再回答这个问题：

- P0-02、P0-03、P0-05 剖析的是 Tauri 版自己的瓶颈。它们原本是 G0 判断"值不值得迁移"的依据，但[决策 001](001-formal-migration.md) 已经决定正式迁移，G0 也已不再决定是否迁移。
- P0-16、P0-17、P0-18 是在找平台边角的问题：Linux 输入法、无 GPU 与远程桌面、多屏 DPI 与显示环境变化。这些问题不会推翻迁移，而 P2-11、P2-25 与 P5-07 本来就要重测同样的场景。在原型上测一遍、到正式实现时再测一遍，前一遍的结论大多会作废。

决策人希望尽快在 GPUI 版里看到应用外壳（标题栏、标签栏、分屏），也就是尽快进入 P1 与 P3。

## 决定

1. **G1 之前只做两件事：**
   - P0-24 的 Windows 通道对比：8 个组件在 Windows 上达到对齐门槛（决策 012 第 4 条）。同日由[决策 016](016-mac-windows-either.md) 改为待补：macOS 已达标即满足 G1。
   - P0-22 精简版：一页报告。逐项列出迁移计划第 6 节的停止条件，写明结论，或写明"推迟到哪张卡"；按现有任务卡重新估算工期。
   - 原计划的第三件事 P0-21（原型性能对比）按第 5 条推迟。
2. **以下卡推迟，不阻塞 G1：**

   | 卡                                     | 去向                                                                                                        |
   | -------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
   | P0-01 剩余部分（vtebench、macOS 基线） | 统一性能对比之前补齐（第 5 条）                                                                             |
   | P0-04 剩余部分（端到端延迟、分屏拖动） | 统一性能对比之前补齐（第 5 条）                                                                             |
   | P0-02、P0-03、P0-05                    | 只在要修 Tauri 版性能时再做，不阻塞任何 GPUI 卡                                                             |
   | G0                                     | 取消。性能基线用 P0-01，Tauri 版要先修什么由决策人另行决定                                                  |
   | P0-16                                  | 并入 P2-11 的验收，Linux 部分按决策 012 在 Linux 发布前做                                                   |
   | P0-17                                  | 能否运行、渲染适配器、降级手段并入 P2-25；与 Tauri 版的 CPU 对比并入第 5 条的统一对比                       |
   | P0-18                                  | 输入法、DPI、多屏、字体回退并入 P2-11；显示环境变化（睡眠唤醒、热插拔、切换显卡、RDP 重连、锁屏）并入 P2-25 |

3. **G1 的标准相应调整**（[acceptance.md 第 4 节](../acceptance.md#g1-技术验证通过进入-p1)）：输入法矩阵与无 GPU 环境两条移到 G2；"三平台运行 vim、tmux、htop 与 AI TUI"按决策 012 先只要求 Windows，macOS 有就记录。
4. P0-22 的依赖从"P0-15 至 P0-21"改为 P0-24 已达标的平台部分。
5. **与 Tauri 版的性能对比在迁移完成后统一做一次。** 时间是 P4 完成后、G4 之前，放在 P5-07 里，P5-10 引用它的数据。对比用 P0-01 的负载与口径，覆盖迁移计划第 9 节的指标：吞吐、帧耗时、内存、空闲唤醒与能耗、启动时间、无 GPU 环境的 CPU。P0-21 并入这次对比，不再单独做。在这之前，各卡不再和 Tauri 基线做对比，只做不依赖基线的自检：P2-25 用 P0-10 的绘制基准确认帧耗时在预算内、内存有界、空闲不重绘。P0-01 与 P0-04 的剩余部分，以及每个要发布平台的 Tauri 基线（按决策 016 补 macOS 基线），在统一对比之前补齐。P1 中保护 Tauri 版不退化的对比（如 P1-04 的吞吐与内存相差不超过 5%）不受影响，照常做。

## 风险

- 输入法与无 GPU 环境是原计划的停止条件。推迟后，如果到 P2 才发现 GPUI 平台层在这些环境下有无法绕过的问题，P1 与 P3 已经投入的工作不会白费（共享核心与工作区对任何界面都有用），但终端和发布时间会受影响。P2-11 与 P2-25 的评估要把这两项当作停止条件看待。
- 不剖析 Tauri 版，就少了一份"迁移到底换来多少收益"的对照。G4 的性能对比仍以 P0-01 的基线为准，所以 P0-01 的剩余部分必须在统一对比之前补齐。
- 性能对比放到最后，如果 GPUI 版在某项指标上明显不如 Tauri 版，到那时才会发现，修起来牵动的代码更多。P2-25 的自检（帧耗时预算、内存有界、空闲不重绘）能挡住最明显的问题，但挡不住"比 Tauri 版慢"这类相对退化。
