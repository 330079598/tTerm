# P0-25 GPUI 绘制能力核实

## 结论

完成。任务卡的 10 项在 `gpui-pre 0.3.11`（经 `gpui-kit 0.9.0` 带入）上逐项核实：2 项支持、4 项部分支持、4 项不支持。每项都有一份可运行的演示（`crates/tterm-gpui/examples/p0_25_gpui_capabilities/`）或测试，并附证明性的截图或源码位置。

有两类项没有在本机闭环，按规则记录：

- **Windows 与 Linux。** 本机只有 macOS，涉及这两个平台的结论只按源码给出位置与生效条件，标为“源码确认，未运行验证”。
- **窗口级模糊的可见效果。** 无头渲染拍不到合成器在窗口后面做的模糊（无头上下文把背景清成不透明黑），演示与运行命令已准备好，截图步骤标为 `[人工]`。

### 1. 窗口级模糊 —— 支持（分平台不同）

| 平台     | 结论                           | 证据                                                                                                                                                                                                                                                                                                                                                                             |
| -------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 通用 API | 支持                           | `WindowBackgroundAppearance` 有 `Opaque`／`Transparent`／`Blurred`／`MicaBackdrop`／`MicaAltBackdrop`：`gpui-pre-0.3.11/src/platform.rs:2899-2919`；建窗口时用 `WindowOptions.window_background`（`gpui-pre-0.3.11/src/platform.rs:2667`），运行时可改 `set_background_appearance`（`gpui-pre-0.3.11/src/window.rs:3285`）                                                       |
| macOS    | 支持，截图 `[人工]`            | `gpui-pre-macos-0.3.11/src/window.rs:1885`：`Blurred` 时挂 `NSVisualEffectView` 子类 `BlurredView`（类定义 `:275`）；`initWithFrame` 设 `NSVisualEffectMaterial::UnderWindowBackground`、`BehindWindow`、`Active`（`:3935-3951`），并清掉层背景只留模糊（`:3955-3974`）；切回不透明时移除视图（`:1902`）                                                                         |
| Windows  | 源码确认，未运行验证           | `Blurred` → `SetWindowCompositionAttribute(…, state 4)` 即 Acrylic：`gpui-pre-windows-0.3.11/src/window.rs:931`，`is_acrylic = state == 4` 在 `:1654`，需要 Windows 10 build 17763 以上（`:1630-1636`）；`MicaBackdrop` → `DWMWA_SYSTEMBACKDROP_TYPE = 2`、`MicaAltBackdrop` → `4`（`:934`、`:938`），需要 Windows 11 build 22621 以上，低于该版本静默返回（`:1606-1614`）       |
| Linux    | 部分支持，源码确认，未运行验证 | Wayland：只有合成器提供 `ext-background-effect`（`gpui-pre-linux-0.3.11/src/linux/wayland/window.rs:2484`）或 `kde-blur`（`:2508`）时才真正模糊，否则只透明；X11：`set_background_appearance` 只调 `update_transparency`（`gpui-pre-linux-0.3.11/src/linux/x11/window.rs:1625`、`:302`），没有模糊；无头窗口是空实现（`gpui-pre-linux-0.3.11/src/linux/headless/window.rs:151`） |

演示：`--window --scene blur-window`。根视图不画页面底色，中间一张 80% 不透明的卡片。

`docs/gpui-migration/reports/assets/P0-25-blur-window.png` 是无头渲染的同一场景，**它只证明内容保持透明**：无头渲染把画布清成不透明黑（PNG 角像素 `(0,0,0,255)`），合成器放在窗口后面的模糊不在渲染结果里。真实效果要人跑上面第二条命令并截屏，期望文件名 `P0-25-blur-window-[manual].png`，标记 `[人工]`。

### 2. 元素级背景模糊 —— 不支持

找过的地方：

- `gpui-pre-0.3.11/src` 全文搜索 `backdrop`：只命中 `WindowBackgroundAppearance` 的文档注释（`gpui-pre-0.3.11/src/platform.rs:2899-2918`），没有任何“取背景再模糊”的 API。
- `Background` 只有四种 tag —— `Solid`、`LinearGradient`、`PatternSlash`、`Checkerboard`（`gpui-pre-0.3.11/src/color.rs:745-752`），没有滤镜或毛玻璃。
- 场景图元只有 `Shadow`／`Quad`／`Path`／`Underline`／`MonochromeSprite`／`SubpixelSprite`／`PolychromeSprite`／`Surface`（`gpui-pre-0.3.11/src/scene.rs:222-231`），没有背景采样图元；`Shadow.blur_radius`（`gpui-pre-0.3.11/src/scene.rs:576`）模糊的是阴影自身，不是它后面的内容。
- `gpui-base 0.9.0` 与 `gpui-component 0.9.0` 同样没有：搜索 `backdrop_blur`／`backdrop_filter` 无命中。

替代画法：不透明度更高的同色底。演示 `P0-25-blur-element.png`（色条模拟终端内容 + 80% 不透明遮罩 + 对话框），能看到下层只是被压暗，色条边缘仍然是硬的。

影响：现有 6 处 `backdrop-filter: blur` 换成不透明底，代价是透过浮层看不到被虚化的终端内容。

### 3. 圆角内容遮罩 —— 不支持

- `ContentMask` 只有一个字段 `bounds`（`gpui-pre-0.3.11/src/window.rs:2455-2458`），`intersect` 是矩形求交（`:2469-2472`）。
- `overflow_hidden` 走 `Style::overflow_mask`（`gpui-pre-0.3.11/src/style.rs:638-660`），只由边界与边框计算，不含圆角；结果进 `with_content_mask`（`gpui-pre-0.3.11/src/elements/div.rs:2601`、`gpui-pre-0.3.11/src/window.rs:4390`）。
- 圆角只存在于 `PaintQuad.corner_radii`（`gpui-pre-0.3.11/src/window.rs:8082-8097`），是元素**自己**填充的形状，不参与裁剪。

演示 `P0-25-rounded-mask.png`：左图是 `rounded(24) + overflow_hidden` 加一个铺满的子元素，子元素四角是直的，父元素的圆角被盖住；右图是替代画法（父元素内边距 24、子元素自己 `rounded(16)`）。

影响：孤岛风格（`src/styles/islands.css`）里贴边的终端、列表、图片都要改成内边距方案；不透明背景上还可以在四角补画背景色，透明或模糊背景上只能靠内边距。

### 4. 线性渐变的色标数量上限 —— 部分支持，上限 2

- `Background` 的色标是定长数组 `colors: [LinearColorStop; 2]`（`gpui-pre-0.3.11/src/color.rs:784`），整个结构 `repr(C)` 直接进 GPU。
- 构造函数只收两端：`linear_gradient(angle, from, to)`（`gpui-pre-0.3.11/src/color.rs:865-876`）。
- 着色器同一形状：`array<LinearColorStop, 2>`（`gpui-pre-wgpu-0.3.11/src/shaders.wgsl:404`），只插值 `colors[0]` 与 `colors[1]`（`:437-455`），中间没有循环。

替代画法（演示 `P0-25-linear-gradient.png`，三条）：

1. 两个色标直接可用；
2. 需要第三个颜色时用两个相邻矩形各画一段渐变，接缝处取同一个颜色；截图里接缝像素与两侧同色，只差 GPU 抖动；
3. 两个色标放在同一百分比上得到硬停，这是百分比唯一多出来的控制。

影响：31 处渐变要逐处确认是否真要第三个颜色，需要的按上面两种改法处理。

### 5. 径向渐变 —— 不支持

- `gpui-pre-0.3.11/src` 全文搜索 `radial`（不区分大小写）：**零命中**。
- `BackgroundTag` 没有径向变体（`gpui-pre-0.3.11/src/color.rs:745-752`）；也没有 `mask`／`clip-path` 一类图元（`gpui-pre-0.3.11/src/scene.rs:222-231`）。

替代画法（演示 `P0-25-radial-gradient.png`）：用 `PathBuilder` 画圆（48 边形），24 个同心圆由外到内递进颜色近似径向渐变；圆环是“先画实心圆、再用背景色画内圆”。200×200 的尺寸上看不出台阶。

影响：`ui/spinner.css` 的 `mask: radial-gradient` 环形改为圆环路径；其余径向渐变按同心圆近似。

### 6. 字间距（letter-spacing） —— 不支持

- `TextStyle`（`gpui-pre-0.3.11/src/style.rs:438-480`）没有字间距字段。
- `TextRun`（`gpui-pre-0.3.11/src/text_system.rs:1070-1083`）只有 `len`／`font`／`color`／背景／下划线／删除线。
- `shape_line(text, font_size, runs, force_width)`（`gpui-pre-0.3.11/src/text_system.rs:672-678`）没有间距参数；`Font`（`:1134-1151`）只有 family／features／fallbacks／weight／style。
- 全文搜索 `letter_spacing`／`letter-spacing`：**零命中**。

替代画法（演示 `P0-25-letter-spacing.png`，三行同字符串）：逐字符 `shape_line` 后按累计宽度加间距画。第二行是每字 +3px，第三行是同样的逐字路径但 +0px，作为对照：第一行与第三行的结尾 x 对齐，说明差别只来自额外的间距，不是逐字绘制本身。

影响：现有的 `tracking-*` 没有对应能力，逐处去掉并记入差异表；确实要加宽的位置（全大写标签等）改为逐字符自绘，成本是每次布局 N 次 shaping。

### 7. 多层阴影 —— 支持

- `StyleRefinement.box_shadow` 是 `Vec<BoxShadow>`（`gpui-pre-0.3.11/src/style.rs:292`），`BoxShadow` 有 offset／blur／spread／inset（`:349-370`）。
- `paint_drop_shadows` 对每一层插一个 `Shadow` 图元（`gpui-pre-0.3.11/src/window.rs:4785-4816`），内阴影另走 `paint_inset_shadows`（`:4821`）；绘制顺序即数组顺序。
- 样式方法 `shadow(Vec<BoxShadow>)` 由宏生成（`gpui-pre-macros-0.3.11/src/styles.rs:384-400`），Tailwind 的 `shadow_sm` 本身就是两层（`:428-437`）。

演示 `P0-25-shadows.png`：1 层、2 层、3 层与 inset 四张卡片并排，放在中灰底上（近黑页面上黑色阴影看不出层次，这是演示取景，不是 GPUI 的限制）。

影响：现有 92 处 `shadow-*` 可以 1:1 还原；每层一个图元、一次模糊，按现在的 1–3 层没有性能问题。

### 8. SVG 着色 —— 部分支持（只支持单色）

- `svg()` 元素绘制时只取 `style.text.color`（`gpui-pre-0.3.11/src/elements/svg.rs:150`、`:152`、`:173`、`:182`、`:184`），也就是 `text_color(...)`。
- `paint_svg` 把 SVG 渲染成 **alpha 掩码**（`gpui-pre-0.3.11/src/window.rs:5231-5243`；掩码由 `SvgRenderer::render_alpha_mask` 产出，`gpui-pre-0.3.11/src/svg_renderer.rs:231-249`），再用这个掩码与一个颜色画 `MonochromeSprite`（`gpui-pre-0.3.11/src/window.rs:5259-5267`）。文件自带的 fill／stroke 颜色全部被丢掉。

演示 `P0-25-svg-color.png`：同一个三色文件（橙色矩形、蓝色圆、绿色斜线）用三种 `text_color` 各画一次，每次都是纯单色。

替代画法：多色图标要么拆成多个 `Svg` 元素各给一个颜色，要么用 `SvgRenderer::render_single_frame`（`gpui-pre-0.3.11/src/svg_renderer.rs:222`）栅格化成图片再按图片画，缓存自己做。

影响：Lucide 图标是单色描边的 `currentColor` 图标，正好是 GPUI 唯一支持的用法，图标这一项不受影响；只有多色 SVG 资源需要另想办法。

### 9. `debug_selector` —— 部分支持（只在测试构建）

- 只有在 `#[cfg(any(test, all(debug_assertions, feature = "test-support")))]` 时 `debug_selector` 才写入（`gpui-pre-0.3.11/src/elements/div.rs:901-920`），否则是空操作（`:922-925`）。
- 记录发生在 `div` 的 paint 里：`record_debug_bounds`（`gpui-pre-0.3.11/src/elements/div.rs:2581-2585`），存储在 `Frame::debug_bounds`（`gpui-pre-0.3.11/src/window.rs:1088-1091`，`#[cfg(any(test, feature = "test-support"))]`）。
- 读取只有一个入口：`VisualTestContext::debug_bounds(selector)`（`gpui-pre-0.3.11/src/app/test_context.rs:1031`），返回 `Bounds<Pixels>`；`TestAppContext` 本身没有这个方法，要先 `VisualTestContext::from_window`（`:886`）。

验证：测试 `debug_selector_records_the_layout_bounds`（`crates/tterm-gpui/src/app/tests.rs`）在 400×300 的测试窗口里放两个带 `debug_selector` 的 div，断言读回的边界：

```text
test app::tests::debug_selector_records_the_layout_bounds ... ok
```

- `p0-25.box`：origin `(24, 16)`、size `(100, 50)`，即 `ml(24)`、`mt(16)` 与自身尺寸；
- `p0-25.second`：origin `(24, 66)`、size `(40, 30)`，紧跟第一个盒子；
- `p0-25.missing`：`None`，未标记的选择器不在表里。

两个盒子尺寸与边距固定、不含文字，断言值不随字体度量变化，三平台应当相同。

影响：W0-04 的布局 JSON 必须用 debug 构建并启用 `test-support` 才能生成，且只能在测试上下文里读；发布版二进制里取不到选择器边界。这一点要在 W0-04 的文档里写明。

### 10. `capture_screenshot` —— 支持（测试与无头上下文）

- 无头：`HeadlessAppContext::capture_screenshot`（`gpui-pre-0.3.11/src/app/headless_app_context.rs:163-171`），经 `Window::render_to_image`（`gpui-pre-0.3.11/src/window.rs:3088-3095`，`#[cfg(any(test, feature = "test-support"))]`）。
- macOS 真实渲染：`VisualTestAppContext::capture_screenshot`（`gpui-pre-0.3.11/src/app/visual_test_context.rs:379-386`），用 Metal 把当前帧渲到纹理再读像素，窗口放在屏幕外。
- **发布版没有截图 API**：`render_to_image` 与两个 `capture_screenshot` 都在 `cfg(test)`／`test-support` 下，正常启动的程序里没有取窗口图像的方法。

验证：本报告的 8 张截图全部由 `--screenshot` 走无头路径生成，尺寸是逻辑尺寸的 2 倍（760×460 → 1520×920，DPR 2）；同一场景连续生成两次，PNG 的 SHA-256 相同（见“检查”）。

影响：P0-23／W0-04 的自动截图只能在无头或测试上下文里做；真实窗口的窗口级模糊、系统合成器效果仍要 `[人工]`。

## 偏差

1. **分支起点与任务说明不一致。** 说明里写 `GPUI` 当前为 `c42a888`，实际 HEAD 是 `527f247`（P0-28 通过后的状态表提交）；分支 `migrate/P0-25-gpui-capabilities` 已经存在并指向 `527f247`。本卡直接在该分支上工作，没有重建也没有改写它的起点。
2. **演示拆成目录，不是单文件。** 卡片允许“一个 example 用参数切换”。8 个场景放在一个文件会到 815 行，超过 800 行限制，所以按仓库“先拆文件”的规则拆成 `examples/p0_25_gpui_capabilities/{main,scenes}.rs`（188 + 640 行）与同目录的 `assets/`。命令名不变。
3. **第 9 项用测试，不用 example。** `debug_selector` 的记录要求 `test-support` 特性，读取接口只属于 `VisualTestContext`，在 example 里拿不到。所以第 9 项的“演示代码”是 `crates/tterm-gpui/src/app/tests.rs` 里的测试，断言精确数值而不是只截图。
4. **窗口级模糊的截图只能 `[人工]`。** 无头渲染把背景清成不透明黑，PNG 里没有模糊。文件 `P0-25-blur-window.png` 只作为“内容保持透明”的证据保留，真机截图要由 stone 补 `P0-25-blur-window-[manual].png`。
5. **阴影演示特意放在中灰底上。** 近黑页面上黑色阴影几乎看不见，为了让截图能比较层次，第 7 项把卡片放在 `#2d333b` 的底上。这是取景，不是 GPUI 的限制。
6. **`openpty` 测试本次通过，测试本身没有改。** 原因见“检查”：会话的文件沙箱在检查期间改为不受限。这里只如实记录，不代表卡片修好了什么。
7. **worktree 的 `node_modules` 是符号链接。** worktree 没有自己的安装，pnpm 检查借用主仓库已安装的包（版本与 `pnpm-lock.yaml` 一致）。这只影响检查的执行方式，不改变仓库内容。

## 遗留问题

1. **窗口级模糊没有真实窗口证据。** 需要 stone 在 macOS 上按第 1 项的命令截一张 `P0-25-blur-window-[manual].png`；Windows 的 Acrylic／Mica 与 Linux 的 Wayland 模糊同样要真机。
2. **Windows 与 Linux 全部项未运行验证。** 除第 1 项的 Windows／Linux 两行外，其余项的平台差异（阴影模糊半径、SVG 的 2 倍栅格化、`debug_selector` 的边界数值）都没有在另外两个平台实测。建议 P0-15 或 P0-17 顺带抽一次截图对照。
3. **逐字符字间距的开销没有测。** 演示只画 20 个字符。若 P4 大量使用，需要测 shaping 开销，或限制在少数标签上。
4. **多色渐变拼接还没有组件。** 演示是两根矩形手拼，接缝依赖两端颜色相同。W0-05／P3 需要决定是否做一个内部按矩形拼接的 `multi_stop_gradient` 辅助，以及百分比硬停的用法规范。
5. **截图能力在发布版不可用。** P0-23 需要决定截图工具链只依赖无头／测试上下文（本卡证据支持这条），以及真实窗口截图是否长期只能 `[人工]`。
6. **`debug_selector` 的构建前提要写进 W0-04。** debug + `test-support` 缺一不可，且只能经 `VisualTestContext` 读取；在 release 下跑对比会静默拿不到边界，必须写死在 W0-04 的文档里。
7. **SVG 的高 DPR 锐度未验证。** `paint_svg` 固定以 `SMOOTH_SVG_SCALE_FACTOR = 2`（`gpui-pre-0.3.11/src/svg_renderer.rs:81`）栅格化，3 倍屏上图标是否够锐需要 P0-24 对比时确认，本卡没有验证。
