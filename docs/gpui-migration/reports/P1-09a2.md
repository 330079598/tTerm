### 依赖倒转

#### `config/save.rs`：保存后的副作用

改前调用顺序：

```text
save_config command
  -> run_blocking(save::save_config(SaveConfigContext, config))
     -> 读取旧 secret_storage_mode
     -> SessionLogState::validate_config
     -> 写配置文件
     -> 应用 SFTP 带宽限制
     -> background::apply_config
     -> system_integration::apply_config
     -> SessionLogState::apply_config
```

改后调用顺序：

```text
save_config command
  -> run_blocking(save::save_config(Arc<SessionLogState>, config))
     -> 读取旧 secret_storage_mode
     -> SessionLogState::validate_config
     -> 写配置文件
     -> 应用 SFTP 带宽限制
     -> 返回 AppConfig
  -> background::apply_config
  -> system_integration::apply_config
  -> SessionLogState::apply_config
```

副作用顺序没有变化，只把最后三步移到 command 中服务返回之后执行。

#### `backup`：应用版本来源

改前：

```text
command(app: AppHandle, ...)
  -> app_identity::get(&app)?.version
  -> backup service(...)
```

改后：

```text
command(services: State<AppServices>, ...)
  -> services.shared.identity.version
  -> backup service(...)
```

本地备份与 WebDAV 共 10 个 command 都改成同一顺序；去掉了只为读取版本而注入的 `AppHandle`。command 签名检查通过，说明前端可见的参数没有变化。

#### `tunnel`：刷新托盘

改前：

```text
command -> app_context::tunnel
  -> TunnelContext { tray: background::tray::TrayContext }
  -> 保存或删除规则、更新状态
  -> background::tray::refresh_tunnels(&TrayContext)
```

改后：

```text
command -> app_context::tunnel
  -> TunnelContext {
       tray: services.shared.platform.tray,
       tray_state: services.app.tray,
       manager: Weak<TunnelManager>
     }
  -> 保存或删除规则、更新状态
  -> context.refresh_tray()
  -> background::tray::refresh_tunnels_with(&dyn Tray, &TrayState, &TunnelManager)
```

`TunnelReporter` 也在发布状态、保存流量和发事件之后，用同样的三个依赖刷新托盘，运行时顺序与改前一致。使用的是 P1-08 已有的 `tterm_platform::tray::Tray`（`is_present`、`present`、`dispatch`、`remove`），没有修改 trait。

### `save_config` 的线程与顺序

改前（第 1 轮 `d758e244` 之后的错误状态）：

```text
save_config async command，tokio 工作线程
  -> run_blocking(save::save_config(..))
     -> 读取旧 secret_storage_mode、校验、写配置、应用 SFTP 带宽限制
     -> spawn_blocking 线程结束
  -> background::apply_config，tokio 工作线程
     -> 托盘显示/移除，可能读数据库，阻塞 tokio 工作线程
  -> runtime.block_on(system_integration::apply_config)，tokio 工作线程
     -> tokio panic: Cannot start a runtime from within a runtime
  -> SessionLogState::apply_config 不会到达
```

改后：

```text
save_config async command，tokio 工作线程
  -> 构造 SaveConfigContext
  -> run_blocking，以下全部在同一个 spawn_blocking 线程
     -> save::save_config
        -> 读取旧 secret_storage_mode、校验、写配置、应用 SFTP 带宽限制
     -> background::apply_config
     -> runtime.block_on(system_integration::apply_config)
     -> SessionLogState::apply_config
  -> 返回 tokio 工作线程
```

这与 `d758e244` 之前的顺序和线程上下文一致。`save::save_config` 出错仍会在任何副作用前返回；系统集成刷新仍只记录错误；会话日志错误仍作为 command 的错误返回。

测试用 `#[tokio::test(flavor = "multi_thread")]` 经 `run_blocking` 调用 `apply_saved_config`，以假托盘、假系统集成和假事件接收器记录三项副作用及其 `ThreadId`。断言顺序为托盘、系统集成、会话日志，且三者都不在异步调用线程。另一个反向测试直接在当前 Tokio 上下文中调用 `Handle::block_on`，断言其 panic。

测试针对抽出的 `apply_saved_config` 副作用层，而不是完整 command：完整 command 的 `save::save_config` 会写真实配置文件，不适合在单测中调用。该测试覆盖了本次回归的运行时上下文、执行线程和三项副作用顺序；文件写入本身是同一闭包中的前一步，且第 1 轮已经位于 `run_blocking` 中。

### 托盘刷新的生命周期

改前（第 1 轮 `e091d794` 之后的错误状态）：

```text
refresh_tunnels
  -> 当前线程先 upgrade 为 Arc<TunnelManager>
  -> dispatch 闭包捕获强 Arc
  -> manager 在排队期间无法释放
```

改后：

```text
refresh_tunnels
  -> dispatch 闭包只捕获 Weak<TunnelManager>
  -> 原生线程执行闭包时 upgrade
  -> 升级成功：按 manager 状态重建菜单
  -> 升级失败：用空隧道列表继续 rebuild_if_changed
```

`TunnelContext::refresh_tray` 和 `TunnelReporter::set_state` 也直接把各自的 `Weak` 交给 `refresh_tunnels_with`，不再提前升级。

回归测试用假托盘暂存 dispatch 闭包，先丢弃外部 `Arc<TunnelManager>`，确认 `weak.upgrade()` 已为 `None`，再执行闭包并断言仍呈现空隧道菜单。强引用捕获的旧实现会因 manager 仍存活而无法通过该测试。

隧道仍经由 `background::tray::refresh_tunnels_with` 访问托盘。这可以接受，因为迁移图已不再把 `background/tray/mod.rs` 列为适配或 `STAY` 表头，工具将它视为可移动文件；本次也没有修改 `tterm-platform::tray::Tray`。

### `run_sync` 的应用版本

改前：

```text
run_sync(app: AppHandle, ..)
  -> app_identity::get(&app)?.version
  -> sync service
```

改后：

```text
run_sync(.., services: State<AppServices>)
  -> services.shared.identity.version
  -> sync service
```

`AppServices.shared.identity` 就是 `app_identity::initialize` 放进去的同一个 `Arc<AppIdentity>`，版本值不变。`AppHandle` 在该 command 中只用于取版本，因此一并去掉；它是 Tauri 注入参数，不是 IPC 参数。`node scripts/migration/command-signatures.mjs --check` 通过，基线文件无改动。

同步命令改完后，`app_identity::get` 只剩 Linux 徽标分支使用。为避免 macOS 构建出现死代码警告，该函数及其专用导入按 Linux 或测试门控；Linux 行为未变，macOS 测试仍覆盖未初始化时的错误。
