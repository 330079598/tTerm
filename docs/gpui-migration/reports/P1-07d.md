## 偏差

### 需要确认：骨架遗漏系统通知与系统集成能力

任务卡明确要求：“不改 `src-tauri/src/services/` 下的定义。需要新字段，或去掉 Tauri 类型需要新建平台 trait 时，以‘需要确认’停下。”计划 2.2 又要求骨架一次定义全部字段、读取方从 AppServices 取具体依赖。下面两项在实际代码中存在，但不在骨架中。

1. **系统通知 `Notifications`。** `notification/mod.rs::init` 在原启动位置创建 `NativeNotifications`、调用 initialize，并通过 `app.manage(Arc<dyn Notifications>)` 托管。`show_notification` 和 `notification_permission` 直接读取这份托管能力。`services/shared.rs::PlatformServices` 只有 `badge`，没有 `notifications`；AppBadge 也不提供通知发送或权限查询。现有 `tterm_platform::notifications::Notifications` trait 已足够，无需新建 trait，但要把读取方按计划改为来自 AppServices，需要补字段及初始化接线。
2. **系统集成 `IntegrationState`。** `system_integration/mod.rs::initialize_with` 托管 `IntegrationState(Result<Arc<dyn SystemIntegration>, String>)`，其中保留初始化错误，让应用继续启动、command 再返回带恢复建议的错误。`integration` 用 try_state 读取它，四个 command 使用它。`PlatformServices` 与 `AppLevelServices` 均无对应字段。现有 `tterm_platform::integration::SystemIntegration` trait 已具备操作方法，无需新建 trait；骨架需要一个能保留初始化失败语义的字段，不能直接用一个必定成功的 Arc 代替。

[缺失能力的源码位置扫描](P1-07d-evidence/missing-services.txt) 可复现上述托管与读取；对应文件分别是 `src-tauri/src/notification/mod.rs`、`src-tauri/src/system_integration/mod.rs`，现有骨架是 `src-tauri/src/services/shared.rs` 和 `services/app.rs`。

建议评估者修订骨架并确认：

- 增加 `shared.platform.notifications: Arc<dyn Notifications>`。
- 增加系统集成依赖，例如 `shared.platform.integration: Result<Arc<dyn SystemIntegration>, String>`，或一个保存同样成功／失败状态的无 Tauri 包装类型。
- 同时明确构造与初始化分工：通知 delegate 初始化仍在原 notification::init 位置，系统集成初始化错误仍不终止启动；不要为了填字段改变数据库、迁移、密钥库与主窗口的启动顺序，也不要创建两份能力。

这两项是建议，尚未改字段或自行选择替代设计。没有通过继续在 command 里读取这两个旧 manage、另设全局状态，或每次重新构造能力来绕过计划。
