挂入外壳。没有迁移 P3-05 主题系统或 P3-07 实际标签栏，只预留内容和工具插槽。
保留 P3-03 的语言观察、默认标题翻译、程序 OSC 标题和重置语义。

P2-05 正在其他工作树实现 clipboard/paste/OSC52。本分支没有修改它们的实现文件；
集成时须保留该分支的粘贴对话框挂载。现有 automation Close 改为走同一保存门控。

## 单位、数据与退出生命周期

GPUI 的 `WindowBounds` 和 display rectangles 使用逻辑坐标。新值以明确的
`LogicalBounds { x, y, width, height }` 存在 **`gpui_window_state`**，外层另有
`maximized` 字段。不会把逻辑值放入 core 已承诺物理单位的 `Bounds`，也不使用保存的
scale 猜测所有显示器的 DPI。数据仍属于既有 `com.stone.tTerm.gpui-dev`
隔离身份，不读写 Tauri 的 `window_state`。

逻辑 placement 与 core 物理 placement 目前保持两套有明确单位的适配；可后续独立抽取
单位无关数学。GPUI 未公开统一的物理显示器拓扑，本批没有证明混合 DPI 原生恢复正确。
负原点、断屏、零尺寸和非有限浮点数有逻辑测试，不把这些测试称为多 DPI 实机证据。

启动加载在窗口创建前通过现有 Tokio runtime 的 blocking worker 完成。移动/缩放回调
只更新内存。正常关闭先记录最终状态，hook 返回 `false`；异步等待后台保存结果后才
`remove_window`，最后窗口关闭时才退出。重复关闭不会重复发起保存。数据库写入失败
会输出错误并允许窗口关闭，避免磁盘满时困住用户。

应用级强制 quit 的 `on_app_quit` 仍受 GPUI 200 ms 上限约束，只是 best effort；
正常关闭依靠上述 gate。应用级退出保护留待 P3-12，不能声称此处保证任意 force quit。

gate 回归通过真实 `attach` 与 `VisualTestContext::simulate_close` 触发：writer latch
阻塞超过 200 ms，期间检查窗口仍存在、重复关闭只有一条写入；释放后检查窗口移除。
`ReleaseOnDrop` 在失败断言路径也释放 writer，避免 Tokio runtime drop 永久等待。
该测试已通过。真实 Tokio worker 会跨线程唤醒 GPUI 任务，测试使用官方
`cx.executor().allow_parking()` 允许真实 I/O；初次运行因默认确定性调度器拒绝这种唤醒
而失败，随后开启该模式，最终窗口模块 33 项全部通过。没有新增生产延时。
