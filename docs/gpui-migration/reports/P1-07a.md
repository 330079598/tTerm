## 偏差

### 第 2 轮需要确认：SSH 到 proxy 的 Tauri 依赖

本轮起点 `8b1462ab` 已包含修订 `9dac7363`。只读核对得到以下调用链：

```sh
rg -n 'open_stream\(|ensure_allowed\(' src-tauri/src/{ssh,proxy}
```

原始输出：

```text
src-tauri/src/proxy/approval.rs:62:pub(crate) async fn ensure_allowed(
src-tauri/src/proxy/connect.rs:139:pub async fn open_stream(
src-tauri/src/proxy/connect.rs:151:    super::approval::ensure_allowed(app, &proxy.name, template, prompt_owner).await?;
src-tauri/src/ssh/jump/connect.rs:95:    open_stream(ctx.app, proxy, target, ctx.prompt_owner)
```

`ssh/jump/connect.rs:24` 的 `ConnectContext.app` 为 `&AppHandle`；`open_proxy_stream` 在上述位置把它交给 `proxy::connect::open_stream`。`proxy/connect.rs:139` 的定义接受 `app: &AppHandle`。继续调用的 `proxy/approval.rs:62` 同样接受 `app: &AppHandle`，在第 76 行通过 `app.state::<Arc<PromptBroker>>()` 取提示服务，第 108 行通过 `prompt_scope::reveal(app)` 唤起窗口。

这条路径服务于 SSH 的 ProxyCommand 审批，不能删掉或绕过，否则改变 core 行为。让 SSH 后台任务不持有 `AppHandle`，需要将 `open_stream` 与 `ensure_allowed` 改为接受具体的 PromptBroker 和 MainWindow 依赖，并修改取状态、建立 fallback owner、唤起窗口等函数体。仅修改调用行不能使现有函数接受无 Tauri 的依赖。把持有 AppHandle 的闭包传入 SSH 也仍然违反“后台任务不捕获 AppHandle”的要求。

第 1 轮授权对其他卡模块的限制仍然有效：

> 别的卡负责的模块里，只允许改因为你改了签名而必须跟着改的调用行，并在报告里列出。

本轮仅将 session_log 调整归 a，未将 proxy 定义及实现调整归 a。因此请求评估者明确授权 a 对 `proxy/connect.rs::open_stream` 与 `proxy/approval.rs::ensure_allowed` 做必要解耦，或先由 d 提供无 Tauri 的同等接口。预计具体依赖可用现有 `shared.prompts` 和 `shared.platform.main_window`，不需要修改 services 字段或新增 trait。当前未实施任何一种方案。
