## 结论

计划完成，**未实施**。本卡要移植的 13 个模块已逐个盘点：13 个源文件、1734 行、112 个导出、9 个测试文件里的 55 个 `it(...)`；其中 `appConfig`、`appConfigNormalize`、`terminalShells`、`startup` 没有测试文件。用 node 实跑真实 TS 模块得到 72 条规格检查（4 次运行：macOS/Windows/Linux 各一次稳定版，macOS 一次预发布版），全部通过；Rust `AppConfig::default()` 的 100 个字段与前端 `defaultConfig` 逐项比对，只有 `secret_storage_mode` 一处不同（已定位原因）。

### Rust `AppConfig::default()` 与前端默认值的逐字段比对

脚本解析 `src-tauri/src/config/defaults.rs` 的 `impl Default for AppConfig`，把 100 个字段与前端 `defaultConfig` 逐项比较（`values["defaultsParity"]`），并断言差异集合正好是文档化的那一项：

| 平台 | 差异 |
| --- | --- |
| macOS | `secret_storage_mode`：前端 `system`，后端 `hybrid` |
| Linux | 同上 |
| Windows | 无（后端 `default_secret_storage_mode()` 在 Windows 上就是 `system`） |

`hybrid` 是旧版保留值，供一次性密码迁移判断密码原来存在哪里，之后与 `system` 等价（`defaults.rs` 的注释如此说明）。前端 `normalizeSecretStorageMode` 把 `password`/`vault` 归为 `password`、`memory` 归为 `memory`、其余（含 `hybrid`）归为 `system`，实跑确认。

### c1：不依赖 P1-09b2 的六个模块

本轮提交的 `P1-11c-evidence/node-<platform>.json` 同时是 Rust 测试的夹具：按 P1-11f 的做法用 `include_str!` 读入，测试直接比对 `values` 里的期望值，而不是把 60 多个数字手抄进源码（手抄一次就多一处漂移点）。平台相关的期望值按 `cfg!(target_os)` 选文件。

#### 1. `config::scrollback`（源 `scrollback.ts`，11 个导出）

新增 `crates/tterm-core/src/config/scrollback.rs`：

```rust
pub const DEFAULT_SCROLLBACK_LINES: u32 = 10_000;
pub const UNLIMITED_SCROLLBACK_SENTINEL: u32 = 0;
pub const UNLIMITED_SCROLLBACK_BUFFER: u32 = 10_000_000;
pub const MAX_EXPLICIT_SCROLLBACK_LINES: u32 = 10_000_000;
pub const UNLIMITED_SCROLLBACK_INITIAL: u32 = 10_000;
pub fn normalize_scrollback_config(value: Option<f64>) -> u32;   // 0.4→0、0.6→1、-3→1、NaN/None→10000
pub fn resolve_scrollback_lines(value: Option<f64>) -> u32;      // 0→10_000_000
pub fn is_unlimited_scrollback(value: Option<f64>) -> bool;
```

`grown_scrollback_capacity` 内部用 `u64` 做 `lines * 2`，避免 `u32` 溢出（TS 是 f64，永远不溢出）；到达上限时返回 `UNLIMITED_SCROLLBACK_BUFFER`。11 个导出对应 11 个 Rust 项，测试 6 条对应 11–16 号用例，另加 `0.4/0.6`、`-3`、`u32::MAX` 三个边界。`resolve_scrollback_lines` 只表示“xterm 该拿多少行”，GPUI 终端是否采用由 P2 决定，本卡只提供函数与常量，不接线。

## 风险

### 1. UTF-16 与字符串边界

- `countLineFeeds` 用 `charCodeAt` 逐码元比较 `0x0a/0x0b/0x0c`；这是 ASCII，Rust 用 `text.bytes().filter(|b| matches!(b, 0x0a | 0x0b | 0x0c)).count()` 等价，不要用 `chars()` 与 `\n` 以外的判断。
- `programName` 的 `replace(/^"|"$/g, "")` 只去掉**一个**首尾引号；后端现有 `local_shells::program_name` 用 `trim_matches('"')` 会去掉全部引号，且用 `rsplit_once('.')` 后对 stem 做了 `trim()`。实跑给出两处反例：`"nu .exe"→"nu "`（后端会给 `"nu"`）、`'""nu.exe""'→'"nu'`（后端会给 `"nu"`）。c2 必须逐字复现 TS：`js_trim` → 去掉一个首引号/尾引号 → 按 `[\\/]` 切 → 取最后一段 → `replace(/\.[^.]+$/, "")`，只有结果为空串时才回退到原文件名；不得对 stem 再 `trim`。
- `favorite_themes` 去重是字符串相等（UTF-16 码元序列）；Rust `String` 相等等价。
- `js_trim` 与 JS `trim` 的空白集合：用已有的 `tterm_terminal::js_text::js_trim`，不要用 Rust 的 `trim()`（`programName`、`sftp_external_editor`、`default_proxy_id`、`sudo_prompt_patterns`、`terminal_log_name_template` 都涉及）。

### 2. 正则

| 位置 | TS pattern / flags | 计划 |
| --- | --- | --- |
| `shellCommands` `BREAKS` | `[\s;&|()<>'"\\]` 再加反引号（原文是这套字符类） | `regress`，无 flags |
| `shellCommands` 注释判断 | `/[\s;&|()]/` | 同上 |
| `shellCommands` 空白判断 | `/\s/` | 同上（JS `\s` 含 U+FEFF/U+00A0） |
| `shellCommands` here-doc | `^<<(-?)[ \t]*\\?(['"]?)([^\s'"\\;&|<>()]+)\2` | 同上，反向引用 `\2` 保留 |
| `shellCommands` 关键字黏连 | 字符类 `'`、`"`、反引号、`\\` | 逐字符判断即可 |
| `shellCommands` 换行切分 | `/\r\n?|\n/` | 手写 `split_lines`，不匹配 U+2028/9 |
| `programName` 扩展名 | `\.[^.]+$` | `regress`；`.` 不含换行，行末换行时不去扩展名 |
| `programName` 引号 | `/^["']|["']$/g` | 手写去一个引号（`g` 无意义，每次只匹配一处） |

不要用 Rust `regex` 近似 `\s`：那是 White_Space 集合，不含 U+FEFF，与 JS 不同（P1-11b/f 已踩过同类问题）。

### 3. 数字

- `Math.round` 与 `f64::round` 只在负数恰好 `.5` 时不同：JS `Math.round(-0.5) = -0`，Rust `(-0.5).round() = -1`。受影响的是 `terminal_letter_spacing`（范围 -5..10，负半分可达）。统一用 `tterm_terminal::theme::js::js_round`（已有，`js_text` 里没有）。
- `normalizeUiScalePercent` 的顺序是“先 `round(value/10)*10`，后 clamp 80..200”；`normalizeTerminalLineHeight` 是“先 `round(value*100)/100`，后 clamp 1..2”。顺序不能换。
- `Number.isFinite` 必须在前：`Math.min(Math.max(NaN, …))` 是 `NaN`，TS 靠前置判断挡住；Rust 用 `Option<f64>` + `is_finite()`。
- 上限都落在 `u8/u16/u32` 内（最大 `MAX_BANDWIDTH_LIMIT_KIB = 10_485_760`），`as u16/u32` 的饱和转换不会触发。
- `grownScrollbackCapacity` 用 f64 计算，`u32` API 需要 `u64` 中间值。
- `sessionNonce` 是 `>>> 0`，Rust 用 `u32::wrapping_add(1)`。

### 4. 序列化

- `normalizeConfig` 保留未知键、也保留错误类型的原始字段；Rust `AppConfig` 做不到。计划：**丢弃未知键，错误类型回退默认值**，并在报告偏差里逐类说明（这只会影响已经损坏或来自更新版本的文件；Rust 的 `load_config_file` 今天更严格，一个类型错误会让整份配置读取失败）。
- `agent_config_dirs` 在 Rust 是 `BTreeMap`（按键排序），TS 按插入顺序序列化；这是既有差异，本卡不改。
- `keyword_highlight.sets` 的 `null`（不是 `[]`）已在 P1-11b 有逐字节测试，本卡不重复。
- c1 的 `TabSettings` 与 `AppConfig` 有三处类型转换（图标、AI 指示、分屏模板，见第 3 节）：模板的 `LayoutShape → Value` 必须保持 `type/orientation/children/sizes` 顺序与全精度尺寸（P1-11d1 的 `serialize_sizes`），枚举用 serde 转小写 id。
- `local_shells` 的键序是 `id,name,path,args`；`TabConnection` 的键序见上文。
- `AppConfig` 的字段顺序不变；`sync/snapshot.rs::SYNCED_SETTINGS` 的 snake_case 键名不变。

### 5. 与现有后端行为的差异（必须写进报告的“偏差”）

| 项 | 前端 `normalizeConfig` | 后端现状 | 本卡做法 |
| --- | --- | --- | --- |
| `secret_storage_mode` 默认 | `system` | `hybrid`（非 Windows） | 默认值保持后端不动；“`hybrid` → `system`”的归一化照前端实现 |
| 错误类型的字段 | 原样保留 | 整份配置读取失败（serde 报错） | 归一化时回退默认值；严格读取不在本卡改 |
| 未知键 | 透传 | 丢弃 | 丢弃 |
| `local_shells` 损坏项 | 原样保留 | 整份配置读取失败 | 丢弃该项 |
| `update_channel` 缺失 | `stable`（预发布版也如此） | `default_update_channel()`（按版本） | 照前端：`stable` |

| `TabConnection`、`TerminalShellType` | 已在 core（P1-11d2） | 不变 |

合并顺序：

1. **c1 现在合**（六个模块都不碰 b2 会移动的文件，只在 `tterm-core/src/lib.rs` 与 `config/mod.rs`、`workspace/mod.rs` 各加一两行 `mod`）。
2. **b2 合入 `GPUI`**（由 P1-09 的评估者派工；不在本卡范围）。
3. **c2 从新的 `GPUI` 切出**（或把 c1 分支 rebase 到 b2 之后），实现 `app_config_normalize`、`limits`、`local_shells`、`terminal_shells`；这一批会改 b2 移动过的 `config/defaults.rs`（让 `default_font_family()` 转调 core）和 `config/tests.rs`（删掉重复的字体测试），并新增 `config/app_config_normalize.rs` 等文件。
4. 冲突面很小：`lib.rs` 的 `mod` 行、`config/mod.rs` 的模块声明、`workspace/mod.rs` 的模块声明；c1 不碰 `config/defaults.rs`、`config/local_shells.rs`、`terminal/pty.rs`，所以与 b2 的移动提交不会冲突。

如果评估者更希望一次只派一个分支，也可以把 c1 与 c2 合成一张卡等 b2，但那样会让 `scrollback`、`shellCommands` 等完全独立的模块空等，不符合“七组彼此独立”的初衷。

## 偏差

1. **任务卡把 `monitorMetrics`、`sftpStartDirectory`、`userVerification` 归在 P1-11g，但 `appConfigNormalize` 需要其中两个小函数。** 本计划的建议见“需要确认”第 1 项；若不调整，c2 无法在不重复实现的前提下完成 `normalizeConfig`。
2. **四个模块没有 TS 测试**（`appConfig`、`appConfigNormalize`、`terminalShells`、`startup`）。任务卡说“现有 `*.test.ts` 是规格”，对这四个模块没有规格可抄，因此本轮用真实 TS 模块实跑生成期望值（`P1-11c-oracle.mjs` 的 `values` 部分），与 P1-11f 处理无测试模块的做法一致。
3. **`spinnerStyle`、`uiStyle`、`startup` 不移植。** 任务卡没有列出这三个模块的去向；本计划在“不迁移的模块及理由”里逐个说明，`spinnerStyle` 的默认值由已有的 `TabAgentIndicatorConfig` 覆盖。
4. **`normalizeSecretStatus` 暂不移植**，理由与依赖见上表；如果评估者要求完整性，可在 P1-11g 合并后补一个提交。
5. **`appConfig.ts` 的常量清单里有一项后端已经在别处定义**（`DEFAULT_TERMINAL_FONT_FAMILY` 与 `defaults::default_font_family()`），计划在 c2 合并为一处，不新建第二份。
6. **本报告没有运行任何 `pnpm` 检查**：这个 worktree 没有 `node_modules`（见“环境与证据”）。实施阶段必须在有依赖的环境里跑全量检查。

## 遗留问题

- `tterm-terminal::theme::js::js_round` 是可复用的 JS 兼容取整，但路径挂在 `theme` 下；`js_text.rs` 里没有。建议以后（P1-13 或独立清理卡）把 JS 数字辅助函数移到 `js_text`，本卡直接引用现有路径，不做跨卡重构。
- `js_trim` 在 `tterm-terminal` 里有 `js_text` 与 `theme::js` 两份，`workspace::pane_templates` 还有第三份 `pub(crate)` 副本（P1-11d2 提升可见性时留下）。本卡只使用 `js_text` 的那份，重复清理留作后续。
- 后端的 `load_config_file` 对类型错误的字段是“整份失败”，前端是“逐字段容错”。P1-11c 的归一化让 GPUI 端在**保存前**容错，但读取仍然严格；是否让读取也容错，需要单独的任务卡（会改变 Tauri 版行为）。
- `terminal_renderer`、`hidden_renderer_release_secs`、`background_throttling` 是 WebView 专有设置。按“不改持久化格式”保留字段与归一化，但 GPUI 端不使用；P4 设置界面是否隐藏它们待定。
- Windows/Linux 的真实运行验证待补（决策 016）；本卡只有纯逻辑与 macOS/Windows/Linux 的 Node 实跑，没有 Rust 侧的三平台运行。

## 需要确认

1. **`normalize_monitor_visible_metrics` 与 `normalize_sftp_start_directory` 由谁实现？** 建议由 P1-11c 的 c2 先落地这两个函数（`monitor_metrics.rs` 2 条测试、`sftp_start_directory.rs` 只含 `normalize_sftp_start_directory` 与 `SFTP_START_DIRECTORIES`，`sftpStartPath`/`sftpFallbackPath` 仍留给 P1-11g），P1-11g 改为复用。若不同意，c2 必须等 P1-11g。
2. **`normalizeConfig` 对未知键与错误类型字段的处理是否可以定为“丢弃/回退默认值”？** 这是与前端 `{...config}` 语义的唯一实质差异（见风险第 4、5 条）。保持持久化格式不变这一点不受影响。
3. **`secret_storage_mode` 的默认值 `hybrid` 是否维持后端现状？** 本计划不改默认值，只让归一化把 `hybrid` 当作 `system`；如果要统一成 `system`，需要同时改后端默认值与密码迁移逻辑，属于另一个卡。
4. **c1 是否现在就能派工？** c1 不依赖 b2，但会在 `tterm-core/src/lib.rs`、`config/mod.rs`、`workspace/mod.rs` 加行，b2 派工时需要知道这些文件已有 c1 的改动（合并顺序见上）。
5. **`normalizeSecretStatus` 是否要在本卡补？** 需要 P1-11g 的 `normalizeVerificationMethod`；若希望本卡收口，可以在 c2 里连带移植这两个小函数，代价是 c2 依赖 g 的一个小模块。
6. **`terminalShellLabel` 的翻译接口**：计划用 `impl Fn(&str, &str) -> String` 闭包（与 TS 同形），而不是返回 `(&'static str, &str)` 让调用方查表；若 P3 的 i18n 接口另有形态，请以那边为准。
