## 单元格度量与行列数

### 公式

Tauri 版实际运行的是 xterm.js 的 `CharSizeService`、WebGL 渲染器（失败时退到 Canvas 渲染器，两者算单元格的方式相同）和 `FitAddon`。GPUI 版照这三处的算法：

```text
font               = 字体链里第一个已安装的字体
char_width_device  = floor(advance('m', font) * dpr)
cell_width_device  = char_width_device + round(letter_spacing)
font_height        = ascent(font) + |descent(font)|
char_height_device = ceil(font_height * dpr)
cell_height_device = floor(char_height_device * line_height)
cell_width         = cell_width_device  / dpr
cell_height        = cell_height_device / dpr

available_width  = floor(width)  - (有回滚区 ? 10 : 0)
available_height = floor(height)
columns = max(2, floor(available_width  / cell_width))
rows    = max(1, floor(available_height / cell_height))
```

- **字体链。** GPUI 只在主字体缺字时才查 `FontFallbacks`；主字体未安装时，它直接换成平台 UI 字体（Windows 是比例字体 Segoe UI）。`FontSet::resolve` 因此像浏览器处理 CSS `font-family` 一样，从链里挑第一个已安装的字体当主字体，其余的留作缺字回退。
- **字符宽度。** `advance('m')` 用 GPUI 文本系统的字形前进宽度；xterm 量的是 `'W'`，等宽字体下两者相同。WebGL/Canvas 渲染器把它按设备像素向下取整（`Math.floor(charSizeService.width * dpr)`），所以 JetBrains Mono 14px 的 8.4px 前进宽度在 DPR 1、1.25、1.5、2 下都得到 8px 的单元格。
- **字间距。** xterm 把 `Math.round(letterSpacing)` 加在设备像素上，GPUI 版照做；DPR 2 下 1px 字间距只让单元格宽 0.5 个逻辑像素。
- **行高。** 字高按设备像素 `ceil`，再乘 `line_height` 后 `floor`，与 xterm 一致。DirectWrite 在 GPUI 的 `FontMetrics` 里返回**负的 descent**（`direct_write.rs` 取 `-(metrics.Base.descent)`；本机 JetBrains Mono 14px 是 `ascent=14.28`、`descent=-4.20`），所以取绝对值；其他平台本来就是正数。
- **可用区域。** `FitAddon` 用 `parseInt` 读容器的 CSS 宽高，并在有回滚区时减去滚动条宽度；tTerm 设置了 `overviewRuler: { width: 10 }`（`openTerminal.ts`），所以减 10px。GPUI 版把可用宽高截成整数，在模型有回滚区时同样留出 10px（`SCROLLBAR_GUTTER`），P0-12 的滚动条画在这里。
- 默认字号 14、行高 1、字间距 0（`src/lib/appConfig.ts` 的 `DEFAULT_TERMINAL_FONT_SIZE = 14`、`terminal_line_height: 1`、`terminal_letter_spacing: 0`）。
- 列数下限 2 行数下限 1；模型 `GridSize` 也会再钳一次。

### 本机结果

Windows 11，默认字体链的前两项 `JetBrains Mono Nerd Font`、`JetBrainsMono Nerd Font` 未安装，解析到第三项 `JetBrains Mono`。`--metrics` 用平台真实的文字系统（DirectWrite）测量：

```text
font=JetBrains Mono (chain starts with JetBrains Mono Nerd Font) size=14 line_height=1 letter_spacing=0
metrics: units_per_em=1000 ascent=14.2800 descent=-4.2000 advance(m)=8.4000
dpr=1: cell=8.0000x19.0000 logical
  800x600: 98 columns x 31 rows
  1200x800: 148 columns x 42 rows
dpr=1.25: cell=8.0000x19.2000 logical
  800x600: 98 columns x 31 rows
  1200x800: 148 columns x 41 rows
dpr=1.5: cell=8.0000x18.6667 logical
  800x600: 98 columns x 32 rows
  1200x800: 148 columns x 42 rows
dpr=2: cell=8.0000x18.5000 logical
  800x600: 98 columns x 32 rows
  1200x800: 148 columns x 43 rows
```

- 列数在常见 DPR 下都相同：800 宽 → **98** 列，1200 宽 → **148** 列。
- 行数随 DPR 变，因为行高按设备像素取整；同一 DPR 下才应与 Tauri 完全相同。
- 行高依赖字体的 ascent/descent。GPUI 用 DirectWrite 的度量，xterm.js 用浏览器的 `fontBoundingBoxAscent/Descent`；两者对 JetBrains Mono 都应是 hhea 的 1020/300（18.48px），但浏览器这一侧没有在本机测过，DPR 1.25 这类取整边界上若有差别会差一行，由下面的 `[人工]` 步骤确认。

### 与字间距的关系

GPUI 没有字间距（P0-25 第 6 项）。终端不依赖字间距：每个字符由视图自己定位到 `column * cell_width`。主题把 `terminal_letter_spacing` 设为非零时，单元格按上面的设备像素公式变宽，字形仍画在单元格左边缘，列位置与列数和 xterm.js 一致；只是字形之间多出的空白落在单元格右侧，而不是由文本系统分摊。字形前进宽度大于单元格时（8.4px 对 8px），字形会伸进右侧单元格 0.4px，xterm.js 的 WebGL 渲染器也是如此。

### `[人工]` Tauri 对照步骤

1. 打开 Tauri 版，确认终端字体解析到 `JetBrains Mono`，字号 14，行高 1，字间距 0，回滚区不为 0。

## 绘制

绘制顺序按设计说明 5.5：终端背景 → 非默认背景矩形 → 选区 → 文本 → 内置字形/装饰 → 光标。

- **背景**：同一行相邻、同色的非默认背景合并成一个矩形；跨行不合并。反色单元格的背景是交换后的前景色。
- **文本 run**：同一行内字体、字重、斜体、前景色、隐藏、下划线种类/颜色、删除线都相同的连续单元格合并为一个 `TextRunSpec`，每行每个 run 只调用一次 `shape_line`。空白单元格、宽字符占位、隐藏文字不进入 run。
- **逐字形定位**：shaping 后把每个字形按字节偏移映射回列号，用 `column * cell_width` 绘制；同一单元格内的组合字符/emoji 簇保留相对偏移。粗体/斜体用不同的 GPUI `Font`；关闭连字（`FontFeatures::disable_ligatures`），否则终端列会错位。
- **宽字符与 emoji**：Alacritty 的 `WIDE_CHAR` 占两列，第二列是 spacer，不产生字形；emoji 走 `Window::paint_emoji`，普通字形走 `paint_glyph`。宽字符上的光标宽 2 列。
- **内置字形**：U+2500–257F、U+2580–259F、U+1FB00–1FB3B、U+1FB82–1FB8B、U+E0B0–E0B3 直接使用 P0-28 的 `builtin_glyph` 几何，画矩形/多边形，不再请求字体。`GlyphFill::ForegroundAlpha` 按覆盖率叠在前景色的 alpha 上。
- **下划线**：单、双、波浪、点、虚线都画；双线是两条矩形，波浪是 `PathBuilder::stroke` 折线，点/虚线按 4px/7px 节距画小矩形。颜色取 `underline_color`，没有设置时取前景色。
- **删除线**：按单元格区间合并后画一条矩形。
- **暗淡**：前景色向背景色混合 50%。**反色**：解析完前景/背景后交换。**粗体**：标准 8 色使用 bright 变体（xterm.js 默认行为），真彩色/索引色不调整。**隐藏**：不画字形，但保留背景。
- **光标**：
  - 块：填充光标色，并在字符位置用 `cursor_accent`（未设置则用终端背景色）重画该格；宽字符覆盖两列。
  - 下划线：底部 2px 条。
  - 竖线：左侧 2px 条。
  - 空心块：四条 1.5px 边框。
  - 失焦：块光标画成淡色空心块，文字保持原样；下划线/竖线降为半透明。
  - 闪烁：只在可见、窗口激活、有焦点、程序允许闪烁且光标可见时运行；隐藏/失焦停止。闪烁帧只重画光标覆盖层，复用上一帧快照和行布局（`blink_reuses`）。

## 滚动

- 滚轮像素先进入 `ScrollAccumulator`：符号反转清零余量，按 `cell_height` 取整，余量留到下一次。
- 取整后调用 P0-28 的 `wheel_action(modes, shift, Wheel { lines, columns: 0 })`：
  - `Scroll(n)` → `Terminal::scroll(Scroll::Delta(n))`，然后请求一帧；
  - `Alternate(arrows)` → 通过回调把 SS3 方向键写给 PTY（演示里接上）；
  - `Report(_)` → 本卡不实现，留给 P0-13 的鼠标编码；
  - `None` → 清掉余量。
- 滚动条、拖拽、锚定不属于本卡，留给 P0-12。

## 缓存与重绘

### 行缓存

- 每个可见行计算 `row_hash`：所有单元格的字符、前景/背景语义色、属性、下划线色、零宽字符、是否有超链接，再加 `style_epoch`（调色板、字体、度量变化时递增）。
- **快照版本不是缓存键**：`Snapshot::version()` 每次取快照都加一，如果放进键里会让每帧全部失效。版本只用于“闪烁帧复用上一帧”的快速路径；真正失效按行内容。
- 缓存键相同就直接复用 `Arc<RowLayout>`，不再 shaping、不再解析颜色、不再合并背景。缓存上限 1024 行，按最近两帧的使用情况淘汰。
- 损坏行只作辅助：`Damage::Rows` 未列出的行且上一帧同一屏幕行存在时，直接复用上一帧行布局（`damage_reuses`）；`Damage::Full`（持续滚动、滚动偏移变化、resize）走内容哈希。P0-27 已经指出，Alacritty 在滚动时会整屏损坏，所以不能只信损坏行。
- **损坏行复用只在同一样式纪元内进行。** Alacritty 的损坏只反映单元格变化，不知道调色板或字体换了；而行布局里存的是解析好的颜色和 shaping 结果。`FrameData` 因此记下自己的 `style_epoch`，纪元不同的上一帧不参与复用，闪烁帧的整帧复用也一样（`a_palette_change_recolors_rows_that_received_no_output`）。

### 实测命中率

发布版基准，1200×800、DPR 2、每帧 148×43。设计说明要求的三种负载是持续输出、原地重绘和翻看历史时有输出；空闲与全屏 TUI 作为两端的对照：

| 场景             | 缓存命中 | 未命中 | 损坏行复用 | 缓存命中率 | 含损坏行复用的总复用率 |
| ---------------- | -------- | ------ | ---------- | ---------- | ---------------------- |
| 空闲             | 120      | 0      | 5040       | 100.00%    | 100.00%                |
| 持续输出         | 8358     | 240    | 1722       | 97.21%     | 97.67%                 |
| 原地重绘         | 683      | 316    | 9321       | 68.37%     | 96.94%                 |
| 翻看历史时有输出 | 10320    | 0      | 0          | 100.00%    | 100.00%                |
| 全屏 TUI         | 120      | 4802   | 238        | 2.44%      | 6.94%                  |

- 持续输出是每帧一行；屏幕向上滚一行后，其余 42 行的内容与上一帧相同，按内容命中。
- 原地重绘模拟 htop：进入备用屏幕画一次静态表格，此后每帧只改一行时钟和三行仪表。未改动的行由损坏信息直接复用；改动的行里，时钟每帧都是新内容，仪表按 40 帧循环，循环一圈后按内容命中。
- 翻看历史时有输出：视口停在历史里 30 行处，每帧新增一行。Alacritty 为保持视口位置调整显示偏移并报整屏损坏，但可见内容没变，全部按内容命中。
- 全屏 TUI 每帧重写整屏，没有可复用的内容，命中率低是预期结果，不是缓存失效错误。

### 空闲不重绘

- `view::tests::an_idle_unfocused_window_draws_no_frames`：在 10 秒模拟时间里推进时钟，只允许测试自己显式渲染的那一帧，`ViewStats::frames` 不增加。没有输出、没有光标闪烁时没有任何定时器或轮询。
- 真实窗口证据：`cargo run -p tterm-gpui --example terminal_view -- --idle-check` 先等首帧稳定 1 秒，再测 9 秒，输出：

  ```text
  idle_check: start_frames=2 end_frames=2 delta=0 redraw_requests=0 blink_toggles=0 output_notifications=0
  ```

  即 9 秒内新增帧数为 **0**，没有重绘请求、没有闪烁切换、没有输出通知。

- 空闲基准里 120 次显式 `draw` 的缓存命中率为 100%，`rows_laid_out=0`：没有重新 shaping。
- 只有光标闪烁是常驻动画；`view::tests::the_blink_timer_stops_when_the_view_is_hidden` 先让定时器切换光标，再隐藏视图，推进 5 秒后 `blink_toggles` 不再增加。
- `view::tests::a_hidden_view_suppresses_output_frames`：隐藏视图收到 100 次输出通知，`redraw_requests=0`、`suppressed_notifications=100`；重新显示时只请求 1 帧。
- 后台标签的模型仍由会话线程写入；视图不取快照、不排版、不 `cx.notify()`。切回前台时 `set_visible(true)` 请求一帧并取最新快照。

- p95 总耗时：空闲 151.0µs，持续输出 965.2µs，原地重绘 476.9µs，翻看历史时有输出 958.9µs，全屏 TUI 1492.9µs，均低于 16.7ms 的 60Hz 预算。

- 与评审前的数据相比，paint 明显变慢（持续输出 p50 从 48.8µs 到 542.0µs）：评审前 Windows 基准用的是占位文字系统，字形没有真实栅格化，那组数字不能代表真实开销，已作废。调试版没有按真实文字系统重测。

## 偏差

1. **Windows 没有 GPUI 的无头渲染器。** `gpui-pre-platform` 的 `current_headless_renderer` 只在 macOS（Metal）和 Linux（WGPU）返回 `Some`，Windows 返回 `None`（`gpui_platform.rs:100-120`）。因此 `--screenshot` 改为打开一个真实 GPUI 窗口（请求位置在屏幕外，Windows 把它移回 `512,185`），调用 `Window::render_to_image`（Windows 的 DirectX 实现，源码注释明确说它是 macOS 无头路径的 Windows 对应物），不经过屏幕录制。这不是“无头上下文”，但结果是未上屏的纹理读回；本会话没有屏幕录制权限，截图命令会短暂创建并销毁一个窗口。
2. **截图尺寸与请求的窗口尺寸不同。** GPUI 报 `scale_factor=1`，但 Windows 把 1200×800 的窗口物理缩放为 1536×1095（含非客户区）。截图记录的是实际纹理尺寸；报告中的行列数仍按逻辑尺寸计算。
3. **调色板没有搜索高亮字段。** `src/types/theme.ts` 的 `TerminalPalette` 没有搜索字段，所以 Rust 类型也不加；`TerminalPalette::search_match` / `search_active` 作为 P2-07 的方法从黄色派生，不冒充主题字段。
4. **Windows 的 descent 符号。** GPUI 的 `FontMetrics` 约定 descent 为正，但 DirectWrite 实现返回负值（JetBrains Mono 14px 是 `-4.20`）；本卡在 `measure_cell` 里取绝对值。这影响所有平台的同一条公式，macOS/Linux 的 descent 本来就是正，取绝对值不改变结果。
5. **滚轮上报模式没接。** `WheelAction::Report` 留给 P0-13；本卡只做本地滚动与备用屏幕方向键。`Shift` 的滚轮语义仍按 P0-28 的记录：上报模式下仍上报。
6. **失焦光标画成空心。** xterm.js 的 `cursorInactiveStyle` 默认是 `outline`；本卡对所有失焦形状都画淡色轮廓/半透明形状，没有额外读配置项。
7. **字间距只有单元格宽度。** GPUI 不能给字形加 spacing；非零 `letter_spacing` 时字形画在单元格左边缘，剩余空白留在右侧。默认 0，所以默认布局与 Tauri 一致。
8. **基准的 DPR 是 2。** `HeadlessAppContext` 在这个 crate 的版本里报 `scale_factor=2`，所以 1200×800 对应 148×43；`--metrics` 列出 DPR 1、1.25、1.5、2 四种结果。两者都写进报告，避免混用。
9. **基准每帧强制 refresh。** 无头上下文没有平台帧循环，`Window::draw` 会复用上一帧；基准在每次 draw 前调用 `window.refresh()`，模拟真实输出批次的完整重绘。真实应用里由 `cx.notify()` 触发同样的完整 draw。
10. **`hdrhistogram` 是新增包。** 它由 GPUI 的 `profiler` feature 引入（`hdrhistogram = "7"`，锁定 7.5.4），只在启用 profiler 的 dev 构建里使用；没有 git 来源。
11. **Windows 的无头平台没有真实文字系统。** `gpui-pre-windows` 的 `WindowsPlatform::new(true)` 用 `NoopTextSystem`：任何字体名都能“找到”，度量固定为 `units_per_em=1000`、`ascent=1025`、`descent=-275`。`--metrics` 与绘制基准因此在 Windows 上改用 `current_platform(false)` 的 DirectWrite 文字系统（不开窗口）。单元测试仍用无头平台，所以 Windows 上的单元测试不能验证字体解析与度量；这两项靠纯函数测试（`first_available`、`cell_size`、`grid_for`）、`--metrics` 输出和截图证明。
12. **单元格比字形前进宽度窄。** 照 xterm.js 渲染器取整后，JetBrains Mono 14px 的单元格是 8px，字形前进宽度 8.4px，字形会伸进右侧单元格 0.4px，与 Tauri 版的显示一致。

## 遗留问题

1. **Tauri 版的行列数对照还没有闭环。** 需要 stone 按“`[人工]` Tauri 对照步骤”执行 `stty size`，把结果填进验收表。这是本卡唯一的验收未验证项。
2. **真实 PTY 输入没有接。** `terminal_view` 只显示输出和滚轮滚动；键盘、选区、剪贴板、输入法属于 P0-13，`TerminalViewConfig::input` 目前只用于备用屏幕滚轮方向键。
3. **滚轮上报模式。** `WheelAction::Report` 仍是空分支，P0-13/P2-04 要接鼠标编码并决定 Shift 的滚轮语义。
4. **搜索高亮。** `TerminalPalette::search_match` / `search_active` 只是派生色；搜索范围、活动匹配和覆盖层绘制属于 P2-07。
5. **缓存命中率在全屏 TUI 下很低。** 每帧整屏重写时没有可复用的行；6.94% 的总复用率是内容决定的下限。若 P0-21 认为需要，可以研究“按绝对行身份缓存回滚行”，但不能依赖 Alacritty 的滚动计数。
6. **空闲测试用的是测试平台。** `an_idle_unfocused_window_draws_no_frames` 在测试调度器上推进 10 秒；真实窗口的 10 秒空闲帧计数仍建议 P0-21 在目标机器上复测，尤其是 Windows 的 DWM 强制重绘行为。
7. **macOS/Linux 未运行。** 本机只有 Windows；公式、字体 fallback、光标形状和测试是跨平台的，但真实渲染、DirectWrite 以外的字体度量和 KP typography 需要 CI/真机确认。截图只有 Windows。
8. **emoji ZWJ 序列。** 截图中 `👨‍👩‍👧‍👦` 在 DirectWrite 下被拆成多个字形；文本 run 保留了组合序列，能否合成一个字形取决于字体/平台。P0-15 应与 Tauri 版逐项对照。
9. **光标闪烁的相位。** 本卡从获得焦点开始计时，失焦重置为可见；xterm.js 的相位可能从最后一次输入开始。P0-13 接入输入后要与 xterm 对照。
10. **滚动条区域。** 网格右侧留出的 10px（`SCROLLBAR_GUTTER`）目前只画终端背景；P0-12 在这里画滚动条与搜索标记。
11. **行缓存只比较 64 位哈希。** 命中时不再逐格比较行内容；两行哈希相撞时会显示另一行的布局，概率极低且不会报错。P0-21 若测到比较的开销可以接受，可以在命中时再比一次内容。
12. **Windows 单元测试测不到字体。** 单元测试的无头平台在 Windows 上没有真实文字系统（偏差第 11 条）；字体解析与度量的跨平台确认依赖 macOS/Linux 的 CI 与 `--metrics`。
