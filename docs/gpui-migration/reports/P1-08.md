# P1-08 平台能力 trait：第 1 轮设计（macOS）

## 设计

### 1. 本轮结论与依据

**需要确认（设计待评估）。** 本轮只提出接口与提交计划，不实施、不加依赖、不修改 `status.md`。以下方法签名是评审草案，不是已经存在或已经编译通过的代码。按 dispatch §3.2，评估通过后再开始下一轮。

- 基准：`migrate/P1-08-platform-traits`，`3c824e557ad1786ac6cf07f54ec210e7a6729fe9`；开始时工作区干净。
- 环境：Mac mini M4 / macOS Apple Silicon；环境能力与缺口以 `environments.md` 为准。本轮没有启动应用、访问应用数据目录或系统剪贴板。
- 已按要求阅读 AGENTS、README §1/2/4/6、P1 现状与 P1-08、决策 003/016、tech-selection §2.1、environments、dispatch §6，并补读 dispatch §3.2/5、P1-01 报告及 P5-01/02/03。
- 遵守 A7/A9：公开能力接口使用 `Result<T, String>`，定义放 `crates/tterm-platform`；Tauri 实现放 `src-tauri/src/platform/`。接口不暴露 Tauri、GPUI、IPC Channel、原生裸指针或插件错误。
- 本卡最终验收仍为“core 不依赖任何 `tauri-plugin-*`；Tauri 版功能不变”。本轮只完成设计证据，不能据此判定这两项实施验收通过。

### 3. 注入、依赖与线程约定

依赖方向为 `tterm-core → tterm-platform`（只需 trait），Tauri 同时依赖二者；P5 原生 UI adapter 可以依赖 GPUI，但 `tterm-platform` 的公共接口不依赖 GPUI。暂不往 platform 添加 `tterm-core` 依赖，以免 AppPaths 所在 core 与 platform 成环。

`AppPaths` 已在 `tterm_core::paths`，保持唯一类型、现有 native/Tauri 构造、标识与目录规则。AppServices 持有 `Arc<AppPaths>`；adapter 构造时从中克隆需要的 `PathBuf`（如 cache_dir、local_data_dir），或由宿主传入明确的目录参数。platform 接口不重新求应用目录、不再声明 `Paths` trait。Library/Services、/usr/local/bin、注册表等系统位置是系统集成实现的职责，不伪装成应用私有路径。

当前基准还没有 AppServices；P1-07 与本卡并行，不能先造第二个容器。建议在 Tauri 先 manage 一个**具体的临时注入结构** `PlatformServices`，P1-07 把它作为 `AppServices.platform` 字段持有（类型定义在 platform）；容器是字段集合，不是把所有方法堆成一个大 trait。各字段是 `Arc<dyn 相应能力>`，字段命名为 open_targets、file_dialogs、clipboard、notifications、app_badge、tray、main_window、updates、process、system_info、file_drag、system_integration、application_menu。领域服务只克隆所需字段，不持有 AppServices 反向引用；不采用泛型传播到所有 command/领域服务。

单实例不放进这个延后构造的服务容器：宿主在打开 DB/路径初始化前取得 `Box<dyn InstanceGuard>` 并持有至进程结束；Tauri 插件仍在第一位安装，其内部守卫不暴露给 core。`SingleInstance` 由启动器持有 `Arc<dyn SingleInstance>`，早期回调只排队 LaunchRequest，不能假设 AppServices/窗口/路径已就绪。沿用 P1-01 报告已确认的早期回调事实。

异步接口用标准库装箱 future，保持对象安全，不引入 async-trait。以下所有异步方法都返回这个别名：

```rust
pub type PlatformFuture<'a, T> =
    std::pin::Pin<Box<dyn std::future::Future<Output = Result<T, String>> + Send + 'a>>;
```

所有服务 trait 为 `Send + Sync`，可从 Tokio 工作线程访问；这不表示其内部 OS 对象可跨线程移动。GPUI adapter 用可发送的命令代理和 oneshot，UI 实体持有实际 Window/菜单对象。Tauri adapter 使用 run_on_main_thread/插件回调。**主线程不 block_on 自己投递的任务**，也不带业务锁等待用户或下载；UI 关闭时必须释放回复通道并返回 String 错误。OS 非 Send 对象在 UI 回调内创建/销毁，不跨 await。

同步 UI 方法是“验证参数并执行/投递请求”，`Ok(())` 表示请求已接收，不能承诺显示服务器已经完成绘制。这样保留当前 macOS blur 的“投递成功即返回、实际失败记日志”语义。异步对话框/通知/拖拽返回最终选择或 OS 接收结果。阻塞文件、注册表、脚本、安装操作在 run_blocking/专用线程；更新网络在 Tokio，UI 回调不执行同步磁盘工作。同步查询需用缓存或宿主线程安全 API，不同步等待 GPUI UI 线程。

#### 4.8 更新检查、下载与安装：Updates

```rust
pub struct UpdateTicket(pub String);
pub struct DownloadedUpdate(pub String);
pub struct AvailableUpdate {
    pub metadata: AppUpdateMetadata,
    pub ticket: UpdateTicket,
}
pub enum UpdateRetention {
    Transient,
    Pending { channel: String },
}
pub trait UpdateProgress: Send + Sync {
    fn report(&self, event: AppUpdateDownloadEvent);
}
pub trait Updates: Send + Sync {
    fn check(&self, channel: String)
        -> PlatformFuture<'_, Option<AvailableUpdate>>;
    fn release_ticket(&self, ticket: UpdateTicket) -> Result<(), String>;
    fn download(&self, ticket: UpdateTicket, retention: UpdateRetention,
        progress: std::sync::Arc<dyn UpdateProgress>)
        -> PlatformFuture<'_, DownloadedUpdate>;
    fn install(&self, download: DownloadedUpdate) -> PlatformFuture<'_, ()>;
    fn discard(&self, download: DownloadedUpdate) -> PlatformFuture<'_, ()>;
}
```

ticket/下载 ID 是 adapter 内存中的不透明句柄，不是版本号、路径或可持久化凭据。实现表保存真实 Tauri Update 与已验签字节；未知/跨实例 ID 返回 String 错误，不 panic；下载记录失败可重试、成功安装/丢弃后清理。AppUpdateMetadata 与下载事件保持现有 serde 命名和数据形状。UpdateProgress 只把原事件交给 Tauri Channel；发送失败仍忽略，不把 UI 断连变成下载取消。

check/download/install/discard 异步，release_ticket 同步；check/download 在 Tokio，install 的同步部分在阻塞线程，只有保存窗口/安装所需 UI 接线回 UI。check 不安装，install 不重新联网检查版本、不主动请求重启（平台安装器自身是否结束进程沿用插件行为）。命令服务保留按 channel 的 pending map：download command 重新 check，并传 Pending { channel }；缓存 bytes 在 AppPaths.cache_dir/updates 原子落盘，安装读取磁盘以保留文件丢失报错/清记录行为；直接 download_install command 传 Transient，仍不额外落盘。adapter 以不透明 DownloadedUpdate 绑定内存/缓存文件，接口不接受可任意覆盖的安装包路径。

必须原样保留：stable/beta-dev 路由与未知渠道回退、15s 连接/30s 读超时、至多 3 次网络重试与 2s/4s 退避、每次重新下载首块前 Started 清计数、Progress chunk_length、Finished 发送时机（它不是“安装成功”）、验签、安装前 save_now、成功后 quarantine 清理/缓存删除。metadata/ticket 由一次 check 配对；不把先前下载换成新发布版本。check 的只读 ticket 由 command 提取 metadata 后调用同步 release_ticket 释放；download 取得 ticket 即移出检查表，成功移交下载记录，失败丢弃。release_ticket 只操作内存表、重复释放成功无操作；未知 ticket 的 download/install 仍返回错误。command 被取消时用 adapter 私有 RAII guard 清理未交付 ticket，禁止无限积累。

持有：`platform.updates: Arc<dyn Updates>`。窗口保存通过宿主注入 install 前钩子，不把 MainWindow 或 core AppServices 强引用进 Update 对象。Tauri Update/Error 和重试错误分类只在 adapter 内；仅在最终返回处转 String，不能先转字符串再判断可重试性。

补充源码核实：锁定的 `tauri-plugin-updater` 的 `updater.rs:938–979` 在 Windows 启动安装器后直接 `std::process::exit(0)`。因此 install 的 future 成功路径在 Windows 不一定能返回，不能把必须执行的 save_now 放在 await install 后，也不能依赖之后的 ProcessControl::restart 清理资源。这属于必须保持并在 P5 单独验证的现有平台差异，不在 P1 顺便修复为统一退出流程。

P5-01/P5-03：`cargo-packager-updater` 加现有 `reqwest`/`minisign-verify`（或自写同协议适配）；这是选型候选，P0-26 已知原清单缺 format 不兼容，P5-03 决定补字段或自解析。接口没有“tauri target/Update”参数，因此可替换；P1 不改 latest.json、公钥、安装模式或过渡版策略。

#### 4.9 最终进程退出与重启：ProcessControl

```rust
pub trait ProcessControl: Send + Sync {
    fn exit(&self, code: i32) -> Result<(), String>;
    fn restart(&self) -> Result<(), String>;
}
```

同步提交最终进程请求，成功后可能不再返回；Result 只用于请求派发失败，不能承诺退出后返回。Tauri exit 调 AppHandle.exit(code)，restart 保留 process 插件/宿主重启语义；GPUI adapter 在 UI 线程调用退出/重启，不直接 std::process::exit 跳过清理。

该能力不决定是否应退出。业务层仍先 blockers 确认→app-will-quit→ready_to_quit 或 1500ms 超时→exit(0)；重复退出放行规则与 code=None 才拦截规则不动。TS relaunch 不强行并入上述确认流程（否则会改变导入/更新重启行为）。持有：`platform.process: Arc<dyn ProcessControl>`。

P5-01：GPUI `App::quit/restart` 与宿主退出钩子；GPUI quit 没有任意退出码参数，原生 launcher 记录 code 并在 event loop 结束返回 ExitCode，重启保留 bundle/可执行文件与参数，不能仅用 current_exe 复制 Tauri bundle 假设。

#### 4.10 单实例与第二次启动：SingleInstance

```rust

    pub cwd: std::path::PathBuf,
}
pub trait LaunchRequests: Send + Sync {
    fn received(&self, request: LaunchRequest);
}
pub trait InstanceGuard: Send + Sync {}
pub enum InstanceClaim {
    Primary(Box<dyn InstanceGuard>),
    Forwarded,
}
pub trait SingleInstance: Send + Sync {
    fn claim_or_forward(&self, identifier: &str, request: LaunchRequest,
        receiver: std::sync::Arc<dyn LaunchRequests>)
        -> Result<InstanceClaim, String>;
}
```

同步早期启动（不在窗口 UI 处理期间调用），Forwarded 时不打开 DB/启动业务。守卫保证实例锁/监听生命周期；接收可来自后台线程，只入队，按原 argv/cwd 规则解析，不用进程全局 current_dir 代替发送方 cwd。Tauri 的特殊点是插件内部已经取得守卫并退出次实例：启动 adapter 包住注册步骤，Primary guard 可是持有注册生命周期的薄对象，不能在 setup 中再抢一次锁；保持 plugin-first 接线，不要求同一条 builder 链强行成为普通 command。

P5-01：`interprocess` 的本地 socket/命名管道加 `fs2` 文件锁（或带完整 argv/cwd IPC 的单实例库），按应用标识隔离；仅防重的 `single-instance` 锁不够，不能忽略传参。最终库与三平台行为留 P5 验证，本轮不加依赖。

#### 4.11 系统信息：SystemInfo

```rust
    fn preferred_theme(&self) -> Result<Option<PreferredTheme>, String>;
```

#### 4.12 原生拖出与目录刷新：FileDrag

```rust
pub trait FileDrag: Send + Sync {

        -> PlatformFuture<'_, DragOutResult>;
```

### 5. 任务卡未展开的问题与待确认点

1. **依赖顺序缺口**：P1-08 只依赖路径卡，AppServices 与事件卡并未合入基准。确认使用临时 PlatformServices 注入后交 P1-07 收口；本卡不能重写 A2/A3/A4，尤其不能另造退出 broker。
2. **单实例启动接口不是普通运行期服务**：确认保留 Tauri plugin-first 的早期接线及宿主守卫，不把 claim 放进 setup。P1-01 已证明回调可以早于路径初始化；第二实例的窗口显示缺失不等于丢失目录队列。
3. **前端调用不在 core**：确认本卡不迁移 TS 插件/窗口调用；Rust adapter 可供 GPUI 接入，但“不再依赖插件”是 core 的验收，Tauri 包与 TS 客户端仍依赖插件。
4. **文件剪贴板只读、拖出是远程下载协议**：确认不新增文件写入和剪切；FileDrag 不简化成现成本地文件拖拽。file promise/source 生命周期可晚于鼠标释放。
5. **窗口背景与模糊有创建期约束**：Windows 初建效果不能延后，macOS radius 依赖私有 CGS。确认共享值类型、宿主创建与运行时操作分开，WebView CSS/节流/devtools/IME frame 不进 trait。
6. **通知包含权限、点击、徽标与声音存储**：确认 Notifications/AppBadge/Tray 三者职责；Fallback 与 Windows overlay restore 不能漏。声音播放、GPUI 原生 IME、窗口几何状态留对应 UI 卡。
7. **更新不是 download_and_install 一个方法**：确认 tickets 隐藏 Update 类型、渠道 pending map 与离线安装保持，以及显式 release_ticket/取消 RAII 的票据生命周期。P0-26 的 format 不兼容与 macOS 替换验证仍未解决，P1 不能顺手改发布协议。
8. **系统集成不随应用标识完全隔离**：即使数据目录隔离，/usr/local/bin/tterm、Library/Services 和 Windows 右键菜单仍是全局位置；不能在日常机器上以“隔离标识”名义直接测试安装/删除。需临时 HOME/Services/bin 注入夹具或可丢弃账户/VM。
9. **通用技术布局文档提到 paths/credentials 在 platform**：实际 P1-01 已把 AppPaths 放 core，以既有实现为准；凭据库属于 P1-07/09 的 SSH 安全存储，不因 tech-selection 一行描述扩张本卡。
10. **规模与平台实测边界**：下面按约 8–10 人天的 P1 实施拆分估算，不含 P5 原生实现/完整打包和跨平台人工补验；若要求本卡实现原生库、重做菜单或更新协议，将超过 L，应先拆卡。所有候选新依赖下一轮仍须核对 pins/锁定版本，不因本报告列名就批准添加。
