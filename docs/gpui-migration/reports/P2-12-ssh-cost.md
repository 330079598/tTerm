# P2-12 第四批：SSH 解析开销对照

**当前结论：本机原始四种负载的吞吐回退已消除。** 两轮独立的基线对照均通过，修复和逐轮数据见文末。此结论只针对 SSH 解析专项。

**首轮决定：不同意提交常开额外解析器的版本。** 与第三批 `7991a62f` 相比，四种负载均消耗更多 CPU，且吞吐更低。下表为首轮结果，最终候选见文末；两次使用同一夹具，没有新增 CI 门槛。

| 输入 | 吞吐 MiB/s（第三批 → 候选） | 吞吐变化 | CPU ms（user + sys） | 峰值 RSS MiB |
| --- | --- | ---: | --- | --- |
| 普通文本 | 177.2 → 156.0 | −12.0% | 350 → 410 | 15.36 → 15.36 |
| ANSI 着色文本 | 103.1 → 90.2 | −12.5% | 610 → 690 | 15.69 → 15.53 |
| 混合查询 | 170.9 → 152.3 | −10.9% | 370 → 420 | 16.03 → 16.01 |
| 同步块内固定回复 | 101.0 → 90.8 | −10.1% | 620 → 685 | 15.89 → 16.13 |

Apple M4、macOS 27.2、arm64、rustc 1.99.1、release。两版使用同一份 `pipeline/p2_12_bench.rs`，均走真实 GPUI 解析队列、SSH 能力识别与终端模型，不包含网络、加密、真实桌面或绘制。每进程一个会话，发送 1024 个 64 KiB 块，另加 21 字节屏幕标记；所有样本核对应用和确认字节数、完整回复以及最终可见文本。同步组有意使用两版都能正确回答的顺序，不能代替乱序回归。

每项先预热一对，再串行运行六对，交替先后，不与编译或其它测试并行。表内为各自六次中位数；吞吐按 64 MiB / 夹具内部时间计算，CPU、峰值 RSS 来自 `/usr/bin/time -l`，覆盖整个测试进程。RSS 不是分配器预留容量，未见一致的驻留内存增长不等于零额外分配，更不等于通过 30 分钟长跑。[原始样本](evidence/P2-12-ssh-cost/samples.csv)含预热（round 0）。

复跑：在单独的 `7991a62f` 工作树复制同一夹具，并在 `pipeline.rs` 注册同一个 `#[cfg(test)] mod p2_12_bench;`。两个工作树分别执行 `cargo test --locked --offline -p tterm-gpui --lib --release --no-run --message-format=json-render-diagnostics`，从 Cargo 的 `compiler-artifact` 记录取实际 libtest 路径，**分别保存二进制**。以 `--ignored --list` 找出 `p2_12_bench::` 的四个全名，逐项运行 `/usr/bin/time -l "$bin" "$test" --exact --ignored --nocapture --test-threads=1`，必须实际执行一项。此诊断没有修改或替代仓库 release 双门。

## 修复与最终复测

普通 SSH 输出不再经过第二个 VTE 解析器。同步块中的固定回复实际需要定位时，才按模型保留的字节追踪标记来源。第一轮修复的[中间样本](evidence/P2-12-ssh-cost/repair-samples.csv)不能作为交付证据：独立回归发现，第二次开始同步更新（延长当前块）会误丢之前的真实模式查询。修订版以模型实际保留的后缀为准，并测试了连续开始、同一包中的结束后再开始、逐字节分包及同值远端查询。

| 输入 | 最终吞吐 MiB/s（第三批 → 修复版） | 变化 | CPU ms | 峰值 RSS MiB |
| --- | --- | ---: | --- | --- |
| 普通文本 | 184.0 → 175.1 | −4.8% | 345 → 370 | 14.95 → 15.16 |
| ANSI 着色文本 | 110.5 → 107.1 | −3.1% | 580 → 600 | 15.10 → 15.13 |
| 混合查询 | 175.5 → 166.7 | −5.0% | 360 → 380 | 15.50 → 15.44 |
| 同步块内固定回复 | 109.8 → 106.9 | −2.6% | 580 → 600 | 15.53 → 15.50 |

[最终逐轮数据](evidence/P2-12-ssh-cost/final-repair-samples.csv)：原基线二进制、相同夹具，重新预热并交替测量六对。每轮中的基线为同期实测，不用跨轮绝对速度计算差值。前端六项、Rust fmt、严格 Clippy、workspace 测试与独立 release 门均通过（前台帧 p95 139.708 µs；30 MiB 确认用时 151.733 ms）。

**结论：** 已修复常开解析和连续同步块的乱序；吞吐差距从首轮 10.1%–12.5% 收窄到最终 2.6%–5.0%，不是零回退。暂不提交。下一步优先在相同二进制与负载上分析普通文本和混合查询路径的 CPU 热点，再决定是否仍需调整；不改门槛，也不把通用性能门当作 SSH 零开销的证明。

## CPU 采样与反证（2026-11-25）

**差距可复现，尚未定位到应当修改的代码。** 在上述最终复测的未采样进程中，普通文本和混合查询的退休指令数与第三批分别相差不到 0.01%，消耗的周期却分别增加 5.2% 和 4.9%。两版单独 `--list` 六次的 user、sys 均为 0.00 s（工具精度 0.01 s），而夹具内部计时也有差距，不支持将约 20 ms 归因于测试进程启动。

对保存的两个二进制逐个运行 `/usr/bin/sample <pid> 1 1 -mayDie`；仅统计 `gpui-pty-parser` 的栈顶，不把主线程等待算作解析成本。[样本计数](evidence/P2-12-ssh-cost/profile-stacks.csv)中，普通文本第一轮基线没有捕到解析线程，整对不参与比例计算。`Processor::advance` 本身占解析线程样本的比例，普通文本为 8.2% → 12.6%，混合查询为 8.1% → 11.2%；最多的样本仍在 Alacritty 的字符输入和行重置。未观察到落在独立排序函数的栈顶；这不能排除内联代码或间接效应。反汇编显示，调用 `Handler::input` 的 ASCII 热循环没有新增排序分支，但读取模型指针的字段偏移由 8 变为 24。栈顶占比不是额外周期的因果分解。

每个实验仍用原四种 64 MiB 输入，预热后按三版本全部六种排列串行测量，每项每版本六次；每个进程校验完整回复、屏幕标记与 67,108,885 个确认字节。下表是两组目标输入的吞吐中位数，单位 MiB/s，顺序均为 **第三批 / 未改的第四批 / 实验版**。应在同一行内比较，不能跨轮挑最快的数。

| 单独改变的变量 | 普通文本 | 混合查询 | 判定 |
| --- | --- | --- | --- |
| [普通与排序处理器分型](evidence/P2-12-ssh-cost/profile-handler.csv) | 185.4 / 175.0 / 176.4 | 174.1 / 167.7 / 167.5 | 移除普通处理器的标记字段没有消除差距，不保留额外实现。 |
| [将排序状态装箱](evidence/P2-12-ssh-cost/profile-state.csv) | 186.9 / 176.1 / 176.6 | 168.1 / 161.3 / 164.3 | 混合查询有改善，普通文本几乎无变化；不足以解释共同回退。 |
| [只改变链接顺序](evidence/P2-12-ssh-cost/profile-link.csv) | 184.9 / 175.8 / 175.8 | 175.8 / 167.5 / 167.4 | 同一批目标文件分别正常链接和用 macOS `-order_file` 前置 `Term::input`、`Processor::advance`、`Row::reset`；`nm` 确认地址变化，两组目标输入却无收益。 |

以上三项均为诊断，不进入生产代码或构建配置。第四批保留之前的回复顺序修复，仍不签收。下一次应直接隔离**模型写入与 GPUI 队列**：对两版重放相同的显示切片，在同一进程内对比启用和未启用排序记录的纯模型开销，再与完整流水线对照。仅用于归因，不代替原夹具或调低验收要求。

## 模型与队列分层复测（2026-11-25）

**绕开队列和 SSH 适配器的运行成本，关闭排序记录，仍可复现版本间差距。** 样本来自同一台 M4，预热一轮，再串行测六轮；交替基线/候选先后，同进程的两个新模型也交换先后。下表是按原始 64 MiB 输入折算的中位吞吐，不是网络速度。仅在同一行内比较。

| 对照（左 → 右） | 普通文本 MiB/s | 混合查询 MiB/s |
| --- | ---: | ---: |
| 保存的完整流水线二进制：第三批 → 第四批 | 181.9 → 175.8（−3.4%） | 174.1 → 167.4（−3.9%） |
| 加入分层测试后重编译，完整流水线：第三批 → 第四批 | 185.5 → 168.8（−9.0%） | 176.2 → 162.1（−8.0%） |
| 同一份显示切片，直接写模型：第三批 → 第四批，均关闭排序 | 189.1 → 172.5（−8.8%） | 184.3 → 166.6（−9.6%） |
| 第四批同一进程，直接写模型：关闭 → 启用排序 | 172.5 → 172.1（−0.2%） | 172.5 → 172.2（−0.2%） |

适配器在计时前按生产队列的边界生成显示切片和固定回复；计时区间仍含 `Terminal::write`、提取模型事件及合成完整回复，不是单独的 VTE 内核。每次均校验完整回复和最终屏幕标记；普通文本重放 1,025 片 / 67,108,885 字节，混合查询重放 2,049 片 / 67,091,477 字节并校验 66,560 个回复字节。完整流水线另校验应用及确认字节数。[逐轮样本](evidence/P2-12-ssh-cost/layer-samples.csv)中 round 0 为预热，pair 的进程 CPU/指令/周期只在首行记录，不能拆算两次写入各自的 CPU。

复跑时使用前述 release 构建命令，复制同一组夹具到 `7991a62f`，只把旧版不存在的 `model.enable_ordered_replies();` 换成 `panic!("ordered mode is not present on the baseline")`。两版均运行 `p2_12_bench::layers::{plain,query}_model`，只有候选版运行 `p2_12_bench::layers::{plain,query}_pair`，设置 `P212_ENABLED_FIRST=0` 或 `1`；使用 `--ignored --list` 返回的全名和 `--exact --ignored --nocapture --test-threads=1`。完整队列用原来的两个 64 MiB 测试，原夹具除注册子模块外未改。

**决定：** 不改队列或排序开关。本轮只增加诊断；同一负载在新旧两组测试二进制上回退幅度不同，不能将 −9% 视为产品回退，也不能用两层吞吐相减估算队列开销。下一步在同一诊断二进制内对照第三批与第四批的模型写入实现，保持 VTE、显示切片及回复校验相同；先区分写入实现差异和构建产物差异，再动生产代码。

## 验收：批量跳过控制串之间的文本

`ControlStringFramer` 在普通文本状态只会因 ASCII `ESC` 离开该状态。裸 C1 字节不会开始 OSC/CSI，合法 UTF-8 的续字节也不可能是 `ESC`。旧代码先检查整片是否 ASCII，再查找 `ESC`；一旦包含转义，就逐字节扫描整片，包括已回到普通文本状态的部分。现在用 `memchr` 直接定位下一处 `ESC`，只在控制序列内部逐字节处理。不绕过 VTE，不改 SSH 队列、背压、延迟回复或控制串载荷；`memchr` 复用锁文件中已有版本。扫描冗余在旧版本中也存在，这个修复消除了实测回退，不证明全部历史差距都由它引入。

Apple M4，原四组 64 MiB release 负载，字节、分块、回复和屏幕标记断言均未动。两轮各自预热后，对三个版本的全部六种先后顺序串行各测一次。第一轮复用保存的原基线和修复前二进制；第二轮使用包含同一组分层诊断测试的基线和修复前二进制，最终修复版不变。单位为 MiB/s，均为六次吞吐中位数：

| 输入 | 原基线 → 修复版 | 相对基线 | 同夹具基线 → 修复版（交叉复核） |
| --- | ---: | ---: | ---: |
| 普通文本 | 180.9 → 191.4 | +5.8% | 183.6 → 187.7 |
| ANSI 着色文本 | 108.8 → 147.3 | +35.4% | 110.0 → 148.7 |
| 混合查询 | 175.6 → 180.2 | +2.6% | 174.5 → 180.2 |
| 同步块内固定回复 | 108.3 → 146.5 | +35.3% | 108.9 → 145.7 |

补充隔离：把 `7991a62f` 模型和修复后模型链接进同一临时 release 程序，共用相同版本的 VTE / Alacritty，并交换先后各跑三次。每次均校验回复和最终屏幕；修复版在普通文本 6/6 次、混合查询 5/6 次更快。这项模型直写实验不计队列和网络，不替代完整流水线结果。

[原基线对照](evidence/P2-12-ssh-cost/ground-repair.csv)和[同夹具交叉复核](evidence/P2-12-ssh-cost/ground-matched.csv)均包含预热、运行顺序和进程计数器，`base` / `previous` / `candidate` 分别代表第三批、修复前第四批和本次修复。每轮每项均实际执行一项测试、应用并确认 67,108,885 字节。五个新增扫描用例覆盖分包、非法 UTF-8、裸 C1、载荷保真、取消和结束位置；工作区中的连续同步块及同值远端查询回复顺序回归通过。前端六项、Rust 格式、严格 Clippy、工作区测试均通过。独立 release 门：30 会话负载前台 p95 **251 µs**，30 MiB 全部确认 **168.762 ms**。此门不代替 SSH 专项；两者均不是 G2 或桌面验收。
