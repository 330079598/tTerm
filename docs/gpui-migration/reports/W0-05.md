## 夹具实施方法

1. 夹具只驱动生产组件。每个屏幕入口放在 `src/parity/screens/<feature>.tsx`，通过真实 Provider 和真实组件渲染，不复制 CSS、不写静态示意图；组件需要的状态通过受控 props、真实 hook 的 fixture 数据或事件 mock 注入。
2. `parity/fixtures/<screen>.json` 只保存 JSON 数据和 reject/pending 指令。`src/parity/fixtures.ts` 为每个命令建立 `satisfies` 断言，例如 `const profiles = fixture.commands.list_profiles satisfies SavedProfile[]`，连接、SFTP、隧道、日志、主题等分别使用 `src/types` 中的返回类型。禁止 `as any`、宽泛 `Record<string, unknown>` 代替真实返回类型。
3. 扩展 `src/parity/tauri/core.ts` 的参数匹配后，再扩展 `event.ts` 的事件序列和 `Channel` 的声明式消息。建议每个屏幕 fixture 可选 `events: [{ name, payload, afterMs }]`、`channels: [{ type, messages }]`；未知命令仍写入 `__PARITY_MISSING__` 并让 capture 失败。
4. “打开下拉”在屏幕入口的 `useEffect` 中调用生产组件公开的点击/键盘路径，或由 capture 动作 DSL 对带 `data-parity-action` 的按钮执行 click；“悬停第 2 行”使用 Playwright `hover`，并在布局 JSON 中把稳定元素 ID 标出来。当前工具只有 URL、等待 ready、截图和布局采集，**不支持动作 DSL、hover、拖拽、延迟事件**，B2/B3/B8 前必须补上。
5. 每个屏幕必须在状态 settle 后调用 `onReady`；pending 屏明确由 fixture 保持 pending，但需要屏幕入口在 spinner 已出现后调用一次 ready，避免等待永远超时。事件/Channel 屏要在最后一条消息应用后再 ready。
6. 参考截图只在干净或明确 `-dirty` 的工作树生成；先删除旧缓存再用 `UPDATE_REFERENCE=1` 重跑，防止 dispatch 第 6 节提到的过期目录被当成有效缓存。

## `data-parity` 标记原则

- 只标记要进入布局契约的稳定外框：页面根、面板、对话框 content/overlay、按钮、输入框、列表行、表格列头、进度条、图标部件。文字本身通常由 `textRegions` 自动遮罩，不为每个字加标记。
- 标记 ID 与 `screens.md` 的状态/元素 ID 稳定对应；重复列表行用 `profile-row.<profileId>` 或 fixture 中稳定索引，不能使用随机 React key。
- 标记只增加 DOM `data-parity` 属性或 `data-slot` 属性，不改变 class、布局、事件、tab order、aria 或文本。标记不得在生产逻辑中分支；Tauri 正常运行不读取它。
- 新增标记后必须运行现有 Vitest、`pnpm typecheck` 和 `pnpm check:size`；`fixtures.test.ts` 要检查每个 manifest ID 都有 screen、fixture 和至少一个稳定标记。若标记导致组件文件超限，应先按 AGENTS.md 拆分。
- 元素集合必须覆盖错误、加载、空、禁用、超长文本和权限不足这些评估重点；只标默认态会让屏幕“通过”但漏掉实际风险。

## P3/P4 分界

W0-05 只交 React 参照端的状态清单、夹具、`data-parity` 标记和参考截图生成记录。P3/P4 的 GPUI 视图、Rust 屏幕、GPUI 端标记、跨端比较修复和窗口原生实现不在本卡范围；GPUI 屏幕必须等相应 P3/P4 卡按本清单逐屏实现。

## 偏差与需要确认的问题

1. **任务卡的 150–180 与按目录枚举的候选数存在去重差异。** 本稿列出约 170 个基础 ID，同时批次表保留了约 228 个候选变体；需要评估者确认“数据值不同但布局相同”的变体是否合并，避免清单和截图数量失真。
2. **`screens.json` 当前只有一个全局 `uiScalePercent: 100` 和 `theme`，没有 `ui_style`、blur 或状态级组合。** 任务卡要求 100/125 与默认/孤岛风格，但工具 README 明确 125% 尚未开放；需要确认先扩展 manifest/入口，还是先冻结清单后另开工具卡。
3. **交互覆盖不足。** 现有 capture 不能表达打开下拉、hover、拖拽、事件延迟和 Channel 消息序列；若不补动作 DSL，很多“状态”只能以入口 effect 预置，无法证明真实交互路径。
4. **业务 IPC 命令远多于现有 parity mock。** `src/parity/tauri` 没有按返回类型的业务 fixture，也没有文件选择器、系统应用列表、通知、窗口控制和更新器的可重复模拟；这些必须在批次中补齐或明确 `[人工]`。
5. **平台矩阵与任务卡不完全一致。** capture 已有 macOS WebKit 与 Windows Edge，但 Linux 仍人工；窗口模糊、标题栏按钮、系统通知、串口、Finder/Explorer、Hello/Touch ID 和更新器不能纳入自动 SSIM，需要评估者接受“状态清单自动 + 平台效果人工”的分界。
6. **事件命名存在代码与清单的潜在漂移。** 例如认证事件按 tab id 拼接（`ssh-auth-prompt-tab-*`），清单只能写模式；实现时需在 fixture schema 中允许事件名模板并由测试验证实际监听名。
7. **部分状态由真实外部资源决定。** 字体列表、SSH config、known_hosts、日志二进制、远端 SFTP 目录和系统应用列表不能读取正式用户数据；必须使用独立类型正确的合成数据，人工项另写证据路径。
