# P1-11g g3 连接组、SFTP 辅助、同步类别与设置索引

- 分支：`migrate/P1-11g-g3`，从本机 `GPUI` 的 `4d0b02a9` 切出
- 基线：`4d0b02a9` 已包含 P1-09b3（`5cedd39b`）、P1-11c c1（`fc4ced6f`）与 P1-11g g1（`e58249b3`）
- 本机：Windows 11，Rust 1.99.1，Node 24.19.0，pnpm 11.15.0
- 范围：`profileGroups`、`sftpArchive`、`sftpSearch`/matcher、`sftpDrawerUtils`、`sync`、`settingsSearchIndex`
- 结果：六个模块的纯逻辑已移入 `tterm-core`，新增 33 个 Rust 测试，其中 14 个直接对应现有的 TypeScript 用例；未改 WebView、Tauri、依赖、`status.md` 或文件大小基线

## 偏差

1. **设置索引直接进了 core。** 计划 11.2 建议把索引数据留到 P4 的 GPUI 设置页。这次任务明确包含 `settingsSearchIndex`，因此把页面与 146 个条目一起移植；React 页面结构、翻译调用与 DOM reveal 仍留在 WebView。若设置页结构和索引后续必须来自同一份运行时数据，需要另开一张适配卡。
2. **没有做 NFKC。** g1 的 `settings::search` 仍只做 trim 与小写折叠；本次只搬索引数据，没有引入 `unicode-normalization`，全角输入等规范化差异仍存在。
3. **非 ASCII 组名顺序与 ICU 不同。** `profileGroups` 的 `localeCompare` 在纯 ASCII 上与后端的 `ORDER BY lower(name), name, id` 一致；Rust 采用 ASCII 大小写折叠、原串 tie-break，非 ASCII 名字退回码位序。测试覆盖了计划记录的 `Web/api/Zebra/prod` 顺序。
4. **正则错误文案由 `regress` 决定。** 匹配语义使用已固定的 `regress` JavaScript 方言；V8 的 `Unterminated group` 在这里可能是 `Unbalanced parenthesis`，外层 `Invalid regular expression: /…/i:` 前缀已对齐。错误文案不是稳定 API，测试只约束前缀与“不匹配”行为。
5. **事件与 UI 适配没有搬。** `sync` 只搬类别、事件名、间隔和 `changed_any`；`invoke("run_sync")`、`CustomEvent`、`addEventListener` 与 React 刷新仍由 WebView 承担。`sftpFontSizeStyle` 返回 React style，`localStorage`、DOM 选择与 Tauri IPC 也没有 Rust 版本。
6. **文件系统与时间适配采用 Rust 类型。** `format_bytes` 接收 `Option<u64>`，与 core 的 SFTP entry size 一致；时间函数接收 `DateTime<Local>` 或毫秒时间戳，测试显式构造本地时间，避免 CI 时区漂移。

## 需要确认

1. 是否接受把完整设置索引直接放在 `tterm-core`？当前实现避免了第二份 146 项清单，但 GPUI 设置页后续要保证页面 id 与 React 页面继续同步。
2. 是否要求补齐 NFKC 搜索规范化？补齐需要新增 `unicode-normalization` 并更新 pins，这不属于本次允许的依赖范围。
3. 是否接受非 ASCII 组名的码位序回退？如果要求与 ICU `localeCompare` 完全一致，需要引入 locale/ICU 能力并固定其版本。
4. 是否接受 `regress` 与 V8 在正则错误文案上的差异？匹配语义与 JS flags 已按 `regress` 的 JavaScript 模式实现。
5. 适配层何时接上这些模块仍待后续卡片决定：WebView 的 SFTP 搜索/归档/路径选择、同步监听与设置页搜索，以及 GPUI 对应的视图层目前都不在本次范围内。
