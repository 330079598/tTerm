### 节流、顺序与现有取消的准确边界

核对命令：

```sh
rg -n 'DEFAULT_PROGRESS_INTERVAL|progress_interval|last_progress_at|report_progress' src-tauri/src/sftp/internal/transfer
rg -n 'emit_progress|missing.is_empty' src-tauri/src/sftp/internal/transfer/run.rs
rg -n 'should_emit_delete_progress|emit_delete_progress' src-tauri/src/sftp/internal/api/delete.rs src-tauri/src/sftp/internal/api/delete/batch.rs
rg -n 'PROGRESS_INTERVAL|MAX_RESULTS|channel.send|POLL_INTERVAL|MissedTickBehavior' src-tauri/src/sftp/internal/api/search.rs src-tauri/src/sftp/internal/api/search/walk.rs src-tauri/src/sftp/internal/api/external/watch.rs
```

- **T100**：`transfer/mod.rs:58` 默认 `Duration::from_millis(100)`；upload.rs 的 TransferOptions 与 `download.rs:92` 的 options 使用它。`transfer/lanes.rs:261–282` 在共享 `Mutex<Option<std::time::Instant>>` 下比较间隔，非 finished 才抑制，第一次 lane 报告不受抑制，finished 绕过间隔。`run.rs:240/:330` 的初始化与收尾回调不受此计时器控制，不能把“100 ms”解释成任何相邻事件都至少相隔 100 ms；`run.rs:227` 已完整 checkpoint/空文件的提前完成甚至不走这两个回调。D02→D03 一次 engine 回调发两个事件，顺序必须保留；D07、D10 不补节流。Tauri sink 不加定时器、合并队列或去重。
- **N25**：`delete.rs:117` 判定 `deleted_directories + deleted_files + failed` 为 0 或 25 的倍数。`delete/batch.rs:215/:283/:301` 应用该判定；顶层失败 :234、SFTP 末尾 :246、命令成功 :159 直接发，不走判定。没有毫秒间隔。删除 command 异步 spawn 后返回 batchId，批次没有接入 `TransferCancelMap`，当前不能宣称支持取消。
- 搜索不是 named event：`search/walk.rs:21–22` 每读完 25 个目录报告一次 Progress（:105），最多并发 8 个目录；Matches 按 find 输出块或目录聚合，没有时间节流。上限 1000；恰好 1000 时未必 truncated，只有下一批超出 room 才设置 truncated；不能擅自改成 `>=` 即截断。
- **W1**：`external/watch.rs:14` 每 1 秒 poll，Tokio interval 保持首 tick 立即与 `MissedTickBehavior::Delay`；一次看见 stamp 变化只置 settling，下一次同 stamp 才读内容（不是固定“保存后 1 秒”）。保留 run_blocking 指纹计算、指纹相同的撤销语义、每次不同保存均可发 Modified，不对相同 status 去重。

### 搜索流：保留 Channel 契约与取消/背压

源清单（不计入 25）：`search.rs:95` 是 `Matches`，`search.rs:101` 是 `Progress`，两者都 `let _ = self.channel.send(...)`；:108 的 search 参数与 :174 的 command on_event 使用 Channel。`search/real_sshd_tests.rs:23` 用 Channel::new 收集 JSON，也是迁移适配测试的入口；前端 `useSftpRecursiveSearch.ts:83–102` 保持原 Channel、onEvent、searchId 与返回 summary。

`ResultSink` 仍负责 room/found/truncated，但字段由 Channel 换成 `Arc<dyn SearchResultSink>`。command 保持 `on_event: Channel<SearchEvent>` 与其他参数原样，仅在边界构造 adapter 注入 search；SearchRequest、SearchSummary、SearchMethod 暂留当前文件（它们不是此次新增 core 服务接口）。enum 的定义路径改变不会改变 IPC 类型或 JSON。

- **取消传递**：仍由 `sftp_cancel_remote_operation(search_id)` 写同一 watch；`with_cancel` 在调用前登记，正常或错误返回后移除。find 的 select 收到取消后仍 `running.stop().await`；walk 的 select 取消后返回，JoinSet drop 中止待处理目录任务。不将 sink 断开隐式变成取消，不新增取消事件，也不改 `cancelled`/`truncated` 的意义。
- **背压现状**：Channel send 是同步提交，没有 UI 消费 ack、容量或 async 等待接口，错误当前被 ResultSink 忽略。因此本卡选同步 trait，Tauri adapter 不额外缓存，直接透传发送结果，ResultSink 继续忽略错误，计数继续增加；MAX_RESULTS 限制匹配条目数，但不限制零匹配扫描的 Progress 总数。不能宣传已有背压，也不能偷偷加入有界队列丢弃或阻塞。
- **未来 GPUI**：可实现同一 trait，把更新立即送入其 UI 队列，显式取消仍走 watch。若要对“队列满”实施可等待背压，应另卡把发送改为可取消的 async future，并对 enqueue 与 watch 作 select；本轮不引入这一行为变化。同步实现不得等待 UI ack，以免阻塞执行取消的同一任务。
- 保留当前取消响应的局限：`host.handles()`、canonicalize、find look_up 的 metadata await 并非全部被 cancel select 包住；“登记从连接开始”不等于所有连接步骤即时可取消。先记录基线，不在事件迁移中修掉这些等待。
