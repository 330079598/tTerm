# P2-03 键盘输入编码

## 结论

部分完成（Windows 11）：GPUI 终端的 keydown 现在先经过 core 应用 keymap，只有挂载的 handler 接受某个动作时才吞掉按键；未绑定、无 handler、handler 拒绝、动作前置条件不满足都会继续走既有终端编码。持久化的 `mac_option_is_meta` 已接到终端视图，且只在 macOS 使用 `EncoderConfig::macos(...)`；其他平台继续使用原有的 Alt 作为 Meta 行为。新增 18 个测试（17 个经注入 session input sink 的端到端测试和 1 个策略测试）和既有编码器测试覆盖了本卡的对照表。

`cargo test --workspace` 仍有一个与本卡无关的既有失败：`terminal_demo::binding::tests::input_and_ctrl_c_bypass_a_saturated_output_parser` 在 Windows 11 主机上 5 秒内等不到 Ctrl+C 结束输出洪峰。把本卡改动 stash 后在 `f69d8c0f` 上单独重跑，同样失败；其余 workspace 测试通过。macOS 与 Linux 本机未运行，按决策 016 记为未验证/推迟。P2 生产窗口已挂载 keymap 路由，但真实动作 handler 由 P3-04 提供，因此当前生产窗口没有可接受的应用动作，所有绑定都会按“无 handler”落到终端；本卡验证的是这条边界和 mount 语义。

### 行为

- 路由顺序：`prefer_character_input` → IME/组合状态 → core keymap → 剪贴板快捷键 → 终端编码。组合中的文本和 `prefer_character_input` 不会被应用快捷键抢先。
- core `dispatch_keydown_event` 的现有契约原样使用：必须有已挂载 handler 返回 `true` 才 `prevented`/`stopped`；否则继续编码。GPUI 侧只在 `dispatch` 返回 `Some(action)` 时吞掉事件。
- 被应用快捷键消费的 keydown 按逻辑键名记入 `consumed_keys`；对应 keyup 被吞掉，Kitty 模式不会发出配对的 release。普通终端按键的 Kitty press/repeat/release 不受影响。
- 启动时读取 `config.keymap` 与 `config.mac_option_is_meta`。`mac_option_is_meta` 只在 `cfg!(target_os = "macos")` 时进入 `EncoderConfig::macos`；Windows/Linux 固定使用非 macOS 的 `alt_sends_escape = true`。
- base `Root` 把 Tab/Shift+Tab 绑定给焦点遍历，GPUI 又在 `on_key_down` 之前分发 key binding。新增 `Terminal` context 的 `NoAction` 绑定让这两个键越过 Root，再由原有编码器发出 `\t` / `\x1b[Z`。

### GPUI 平台数据限制

Pinned `gpui-pre 0.3.11`：

- `src/platform/keystroke.rs:18` 的 `Keystroke` 只有 `modifiers`、`key`、`key_char`。没有物理 `code`、左右修饰键、numpad location、未受修饰的 base key 或独立 Shift 状态。
- `src/interactive.rs:25` 的 `KeyDownEvent` 只有 `keystroke`、`is_held`、`prefer_character_input`；`src/interactive.rs:47` 的 `KeyUpEvent` 只有 `keystroke`。`is_held` 是重复标志，但没有 Kitty 的 press/repeat/release 事件类型数据。
- `src/platform/keystroke.rs:492` 的 `Modifiers` 只有 `control`、`alt`、`shift`、`platform`、`function`，没有左右侧信息。
- 因此：应用小键盘/DECPAM 和 Kitty 的左右修饰键/标点 alternate key 只能在编码器单元测试中验证，正式视图无法完整还原；Tauri 用 `event.code` 优先于 `event.key`，GPUI 只有逻辑键，非 US 布局的物理 code 绑定无法逐项等价。`key_char` 与 `key` 的差异已用于文本编码，但不等于物理 code。

## 偏差

1. 任务说明写分支直接从 `570710d4` 切出；实际 HEAD 起点是 `f69d8c0f`（`570710d4` 之后的 P2-02 报告提交）。本卡没有改动或回退该提交。
2. 为保留 Shift+Tab，新增了 `Terminal` context 下 Tab/Shift+Tab 的 `NoAction` binding。base `Root` 会在 `on_key_down` 之前把这两个键用于焦点遍历；没有这条 binding 时，P0-28 编码器虽有 Shift+Tab 序列，正式窗口也收不到。该改动只影响终端 context。
3. P2 生产窗口按持久化绑定挂载了 keymap，但本卡不实现 P3 的应用动作，因此生产环境没有实际 handler 可接受动作；接受、拒绝、前置条件失败由测试注入 handler 验证。P3-04 负责把动作 handler 挂上；挂上之前，所有绑定都会按“无 mounted handler”落到终端。
4. Tauri 对照表的 Tauri 列是 xterm 6.0.0 源码推导，不是本次实机运行结果。xterm 6.0.0 没有 Kitty 键盘协议；它记录 `applicationKeypad` 但不在 `Keyboard.ts` 中编码 DECPAM，所以小键盘行与 Kitty 行是预期差异，不是本卡回归。
5. `mac_option_is_meta` 在窗口启动时读取一次。P2 没有设置界面，也没有实时重配 keymap/键盘设置的入口；修改配置后需要重启 GPUI 窗口。Tauri 的 `useTerminalConfigSync` 是实时应用。
6. P2-03 实现没有修改 `docs/gpui-migration/status.md`、`pipeline.rs`、`session.rs`
   或 `tterm-terminal` core。分支上的 P2-02 报告只由独立提交
   `f69d8c0f` 更新，内容是协调者提供的最终 release 补测数据。

## 遗留问题

- P3-04 需要挂载真实动作 handler，并决定 Tab/Shift+Tab 的 `NoAction` binding 是否与最终的全局 keymap 组织合并；当前生产窗口没有任何可接受的应用动作。
- macOS 与 Linux 的真实窗口未验证；macOS 的 Ctrl/Cmd、Option 组合和系统输入法需在 macOS 上复跑。Linux 按决策 016 推迟到发布前。
- GPUI 不提供物理 `code`、location、base key、独立 Shift 状态，应用小键盘、Kitty 左右修饰键、Shift 折入标点和物理布局自定义绑定只能做逻辑键近似；需要时应在 GPUI/平台适配层补数据，或登记为长期限制。
- 真实 DECPAM 程序（vttest、xterm）和真实 Kitty 程序仍需实机验证；当前只有编码器表测试和视图 keyup 配对测试。
- `cargo test --workspace` 的 `input_and_ctrl_c_bypass_a_saturated_output_parser` 在 Windows 11 当前主机上稳定失败，需在干净主机/CI 复跑，或另开 P2-02 跟进卡判断是 ConPTY/Ctrl+C 环境问题还是测试时限过紧。
- 全量并行测试曾遇到磁盘空间不足（`target/debug/incremental` 22 GB target 中的 8.2 GB），已清理增量目录；CI 不受本机磁盘状态影响。
