## 热点与测量

### 前端输出与 ack 热路径

1. `src/components/TerminalTab/ptySession.ts:103-156, 278-286`：`Channel<ArrayBuffer>` 收到字节后进入 `handleTerminalOutput`，执行 `decodeOutputChunk`、扫描器、滚动内存、`outputHold.write`；xterm 写入完成回调内才执行 `outputAcker.parsed(channelBytes)`。这是输出从 IPC 到 xterm 解析完成的关键路径。影响是持续输出时每个通道批次都会经过 UTF-8 解码、扫描和 xterm parser；可在 Tauri 版内通过减少重复扫描或调整批次继续优化，当前不修改。
2. `src/components/TerminalTab/outputAck.ts:1-57`：前端按 64 KiB 聚合 ack，小于阈值的余量在 20 ms 定时器触发；`ack_pty_output` 调用是异步的。影响是 ack IPC 次数与解析延迟之间的权衡；可在 Tauri 版内调节，当前不修改。现有测试命令 `pnpm test -- src/components/TerminalTab/outputAck.test.ts` 的原始结果为 `Test Files 174 passed (174)`、`Tests 1294 passed (1294)`（Vitest 配置会运行全套 `src` 测试）；`outputAck.test.ts` 覆盖“满批次立即发送”“小余量 20 ms 后合并”“dispose 后不发送”。
3. `src-tauri/src/terminal/io_batcher.rs:22-34, 42-115, 300-389`：后端 sender 以 8 ms 窗口合并，单消息最多 512 KiB；未确认字节达到 1 MiB 时等待 `ack_pty_output`，5 s 无 ack 则清零 outstanding 后继续。影响是 xterm 跟不上时上游 PTY/SSH 背压，避免 WebView 队列无限增长；这是 Tauri 版可修的 IPC 热点，但本卡不修。
4. `src-tauri/src/core/commands.rs:390-403`：`ack_pty_output` 已是 `async`，只取得异步读锁并调用 `OutputFlow::ack`，没有文件、数据库、钥匙串或加密工作；它是 ack 往返的后端端点。

端到端输出测量尝试：在隔离实例中经 CDP 发送 `Write-Output P004_MARK`，注入 `window.__TAURI__.core.invoke` 包装器并等待 3 s；原始 [ipc-events.json](assets/P0-04/ipc-events.json) 为 `{"events":[]}`，原因是 Tauri IPC 函数由绑定层捕获，替换 JS 对象属性不会拦截真实调用，且本地终端的输出通道不是可从页面脚本重新注入的事件。因此没有把该尝试当作延迟数字。批量输出尝试因相同限制中止，原始 [ack-measurement.json](assets/P0-04/ack-measurement.json) 保留为空结果；不据此声称通过。

后端可复现测量命令：

```text
cargo test --workspace terminal::io_batcher

running 21 tests
...
test terminal::io_batcher::tests::sender_pauses_at_high_watermark_until_acknowledged ... ok
test terminal::io_batcher::tests::stalled_acknowledgements_do_not_wedge_the_sender ... ok
test terminal::io_batcher::tests::rapid_messages_coalesce_into_fewer_chunks ... ok
test result: ok. 21 passed; 0 failed; 0 ignored
```

这些测试提供了 ack 对吞吐的行为证据：无 ack 达到 1 MiB 会暂停；收到 ack 会继续；5 s stall timeout 不会永久卡死；8 ms 窗口会合并 steady stream。它们没有冒充真实 WebView 的端到端毫秒延迟。


审查结果（文件与行号）：

明确发现的“同步 command 中做文件、数据库、钥匙串或加密工作”：**未发现**。所有涉及这些类别的已注册命令均为 `async`，或把工作交给 `run_blocking`；例如 `src-tauri/src/session_log.rs:303-408` 的日志列举、读取、导出、删除和保存命令使用 `run_blocking`，`src-tauri/src/ssh/secret_commands.rs:56-231` 的钥匙串/密码库操作使用 `run_blocking`，`src-tauri/src/config/mod.rs:438-448` 的配置读写为 `async`。

## 偏差

- 任务卡要求 React Profiler 导出，但仓库没有 Profiler/DevTools 接入，依赖规则又不允许为本卡随意增加依赖；没有把普通 CDP trace 冒充 React commit 数据。开发构建启动还受到 Vite watcher 对 `target/debug/deps/t_term_lib.dll` 的 `EBUSY` 影响。
- Windows Tauri 实际配置目录仍由系统 Roaming Known Folder 决定；按 P0-01 约定预创建并使用唯一 `com.stone.tTerm.p004`，从未启动 `com.stone.tTerm` 或 `com.stone.tTerm.dev`。临时配置仅在 `target/`，已删除运行目录。
- 真实 SFTP 抽屉必须有 SSH 会话；按补充规则未连接任何主机，故该项只能标 `[人工]`/未验证。
- 通过页面替换 `window.__TAURI__.core.invoke` 无法拦截绑定层 IPC，端到端测量没有可靠时间戳，保留失败原始输出，不填零、不推算。
- 本轮未进行 macOS/Linux 原生验证；环境清单标记 Linux 桌面缺失，Mac 不在本机。
