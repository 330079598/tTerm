## 2. 设计

### 2.1 AppServices 放在哪里

A2 的目标是 `tterm_core::AppServices`，但大部分字段的类型（`PtyMap`、`TunnelManager` 等）到 P1-09 才移进 `tterm-core`。所以 **P1-07 期间 `AppServices` 定义在 `src-tauri/src/services/`**，P1-09 把它和服务一起移进 core。要让 P1-09 只做移动，P1-07 必须满足以下三条：

- `services/` 下的任何文件都不出现 `tauri::`、`AppHandle`、`State`；
- 字段的类型不是 Tauri 类型。平台能力用 `tterm-platform` 的 trait 对象，事件用 `tterm_core` 的 `EventSink`；
- 服务方法不接受 Tauri 类型，这是任务卡的要求。

### 2.2 骨架

按卡分文件。骨架一次定义出全部字段，a–d 只改读取方，不改 `services/` 下的定义，这样四张卡并行时不会在同一文件冲突：

```rust
// src-tauri/src/services/mod.rs —— 只有组装，没有逻辑
pub mod app;       // P1-07d 的状态
pub mod session;   // P1-07a 的状态
pub mod sftp;      // P1-07b 的状态
pub mod shared;    // 跨卡共享：事件、提示、密钥库、平台能力、运行时句柄

/// Every service the commands and background tasks use. Built once in
/// `setup()` and handed out as `Arc<AppServices>`; it holds no Tauri types so
/// P1-09 can move it into `tterm_core` unchanged.
pub struct AppServices {
    pub shared: shared::SharedServices,
    pub session: session::SessionServices,
    pub sftp: sftp::SftpServices,
    pub app: app::AppLevelServices,
}

// services/shared.rs
pub struct SharedServices {
    pub events: Arc<dyn tterm_core::events::EventSink>,
    pub prompts: Arc<tterm_core::prompts::PromptBroker>,
    pub secrets: SecretStoreState,
    pub runtime: tokio::runtime::Handle,
    pub platform: PlatformServices,
}

pub struct PlatformServices {
    pub badge: Arc<dyn tterm_platform::notifications::AppBadge>,
    pub tray: Arc<dyn tterm_platform::tray::Tray>,
    pub file_drag: Arc<dyn tterm_platform::drag::FileDrag>,
    pub main_window: Arc<dyn tterm_platform::window::MainWindow>,
    pub process: Arc<dyn tterm_platform::process::ProcessControl>,
    pub verification: Arc<dyn tterm_platform::verification::UserVerification>,
    pub updates: Arc<dyn tterm_platform::updates::Updates>,
    pub open: Arc<dyn tterm_platform::open::OpenTargets>,
    pub clipboard: Arc<dyn tterm_platform::clipboard::Clipboard>,
}

// services/session.rs（P1-07a 的数据）
pub struct SessionServices {
    pub ptys: PtyMap,
    pub zmodem: ZmodemMap,
    pub zmodem_armed_send: ZmodemArmedSendMap,
    pub zmodem_manual_detect: ZmodemManualDetectMap,
    pub monitors: MonitorSessionMap,

// services/sftp.rs（P1-07b）
pub struct SftpServices {
    pub pool: SftpConnectionPool,

// services/app.rs（P1-07d，c 也读 tunnels 与 session_log）
```

P1-07c 的模块（config、db、profiles 等）现在没有自己的托管状态，数据库是全局的 `db::` 函数，所以不加分组。c 的工作是让 command 变薄，以及把这些模块里的 `AppHandle` 换成从 `AppServices` 取依赖（主要是事件、密钥库与 `tunnels`）。如果 c 发现需要新的状态，停下报告，不要自己往 `services/` 里加字段。

字段名和类型以骨架实际编译通过的为准，上面的名字是建议。名字定下后写进骨架报告，a–d 照用。

### 2.3 过渡期：同一实例两处可取

骨架不删除任何现有的 `manage`。`AppServices` 里的每个字段，必须和单独托管的那份是**同一个实例**（`Arc` 克隆），不能另建一份。所以骨架要先做一件机械的事：把非 `Arc` 的托管值改成托管 `Arc<T>`。涉及 `PendingMonitorPrompts`、`ExternalEditState`、`SessionLogState`、`TunnelManager`、`CloseBehaviorState`、`QuitState`、`ExitGuardState`、`LaunchDirs`、`TrayState`、`PendingUpdateDownloads`，读取方从 `State<'_, T>` 改为 `State<'_, Arc<T>>`。`State` 解引用到 `Arc`，`Arc` 再解引用到 `T`，所以多数调用点只改类型名。这一步单独提交，`git diff` 里只能看到类型包了一层 `Arc`。

之后 a–d 迁移读取方：

- **只被本卡模块读取**的状态（见 1.1 表的“只 a/只 b/只 d”）：本卡迁移完读取方后，删掉 `lib.rs` 里对应的单独 `manage`。
- **跨卡共享**的状态（`PtyMap`、`SftpConnectionPool`、`SecretStoreState`、`PromptBroker`、`SessionLogState`、`TunnelManager`、平台能力）：各卡只迁移自己模块里的读取方，不删 `manage`。P1-07e 在 a–d 都合并后删除，并迁移 `lib.rs`、`prompt_scope.rs` 等适配层里剩下的读取方。

### 2.4 构造顺序

现在的顺序（`lib.rs` `run()`）：

1. builder 之前：创建各空表；建 tokio `Runtime`；`SecretStoreState::new()`；`ssh::key_vault::install`；`SessionLogState::default()`。
2. builder：插件（single-instance 第一个注册），`manage` 19 项。
3. `setup()`：`app_paths::initialize` → `app_identity::initialize` → `platform::initialize` → `manage(PromptBroker)` → `system_integration::initialize` → `launch_dir::open_from_startup` → 清更新缓存 → 清 WebDAV 下载 → `db::init` → `migrate_legacy_config_files` → `import_legacy_json_files` → `import_settings_files` → `SecretStoreState::initialize` → `remove_retired_files` → 读配置、带宽限制、`session_log.apply_config` → `external::clean_up_on_start` → `spawn_idle_reaper` → `notification::init` → （macOS）预载登录 shell 环境 → 建主窗口 → `background::apply_config` → `system_integration::apply_config`。

改动后：

- 第 1、2 步不变，只是多克隆一份 `Arc` 留给 `AppServices`。这些克隆连同运行时句柄一起 `move` 进 `setup` 闭包。
- `platform::initialize` 改为返回 `PlatformServices`；过渡期它照旧逐个 `manage`，用的是同一批 `Arc`。
- **`AppServices` 在原来 `manage(PromptBroker)` 的位置构造并 `manage(Arc<AppServices>)`**。`PromptBroker` 在同一处创建，放进 `shared.prompts`；过渡期继续单独 `manage`。
- 其余步骤的顺序不变。构造 `AppServices` 只是组装已有实例，没有 I/O，所以 `db::init`、导入、密钥库初始化仍在它之后、原来的位置执行。
- **运行时**：`AppServices` 只持有 `tokio::runtime::Handle`。`Runtime` 本身仍由 `TokioRuntimeState` 托管，不放进 `AppServices`，原因是 `Runtime` 不能在异步上下文里被 drop，而 `AppServices` 的克隆可能被后台任务持有到退出。

### 2.5 退出与回调

- `RunEvent::Exit` 及其他 `RunEvent` 分支里，统一用 `app.try_state::<Arc<AppServices>>()`，取不到就跳过，不 panic。`setup()` 中途失败时应用会直接退出，那时 `AppServices` 可能还没托管。退出时各步骤的顺序不变。
- **Tauri 入口**：可以接受 Tauri 类型的地方只有两类。一是 `#[tauri::command]` 函数。二是交给 Tauri API 的回调，例如托盘与菜单事件、窗口事件、single-instance 回调、`run_on_main_thread` 的闭包。入口只做三件事：取 `Arc<AppServices>`，转换参数，调用服务。入口放在模块的 `mod.rs` 或 `commands.rs`，各卡在报告里列出所有入口。
- **后台任务与线程**：现在捕获 `AppHandle` 的，改为捕获 `Arc<AppServices>` 或它需要的具体 `Arc`。不要在后台任务里 `app.state()`。

### 2.6 剩下的 Tauri 能力

1.2 里的第三种用法（`app.path`、`get_webview_window`、`app.config`、`package_info`、`tray_by_id`、`run_on_main_thread`、`exit`、`default_window_icon`）在 P1-07 中按下面的顺序处理：

1. 路径与应用标识：用 P1-01 的 `AppPaths` / `AppIdentity`。
2. 窗口、托盘、进程：用 P1-08 的平台 trait（`MainWindow`、`Tray`、`ProcessControl` 等）。
3. 现有 trait 缺方法的：可以给已有 trait 加方法，并在 Tauri 实现中补上，每个新方法在报告里列出。**不要新建 trait。**确实需要新 trait 时停下，写进“需要确认”。
4. 只在 Tauri 端存在的做法：留在入口里，报告说明为什么不能挪。

### 2.7 command 变薄的规则

command 只保留四件事：从 `State<'_, Arc<AppServices>>` 取服务；把 IPC 参数转成服务的参数；调用一个服务方法（异步阻塞工作照旧放在 `run_blocking` 里，见 AGENTS.md）；把结果转成 `Result<T, String>`。校验、组合多步操作、发事件等逻辑都放进服务方法。

例（示意，实际以代码为准）：

```rust
// 改前
#[tauri::command]
pub async fn stop_tunnel(app: AppHandle, manager: State<'_, TunnelManager>, id: String) -> Result<(), String> {
    manager.stop(&app, &id).await   // stop 内部 TauriEventSink::new(app.clone())
}

// 改后
#[tauri::command]
pub async fn stop_tunnel(services: State<'_, Arc<AppServices>>, id: String) -> Result<(), String> {
    services.app.tunnels.stop(services.shared.events.as_ref(), &id).await
}
```

服务方法优先接受它具体需要的依赖（`&dyn EventSink`、`&SecretStoreState`、`&PtyMap`），不要整个接受 `&AppServices`，免得隐藏依赖、形成环。只有入口可以拿整个 `AppServices`。

### 2.8 依赖关系

依赖方向（箭头表示“读取”）：

- `session`（a）、`sftp`（b）、`app`（d）都依赖 `shared`。
- d 的 `background` 读 `session.ptys`；d 的 `agent_integration` 读 `sftp.pool`。
- c 的 `profiles`、`sync` 读 `app.tunnels`；c 的 `config` 读 `app.session_log`。
- `shared` 不依赖任何分组。

构造时所有字段都从已经存在的实例组装，没有一个字段需要先有另一个分组才能构造，所以不存在构造环。读取方向上，`shared` 是最底层；`session`、`sftp`、`app` 之间只有 d → a、d → b 两条单向读取，没有环。实施中如果出现 a 或 b 需要读 `app` 的情况，停下报告。

**修订（2026-11-11，P1-07a 第 1 轮提出）：**会话日志是会话输出路径的一部分。core、terminal、ssh、serial 的读线程与后台任务都要调用 `session_log`，计划漏掉了这一点。处理如下：

- `session_log/` 与 `session_log.rs` 从 P1-07d 移到 **P1-07a**，由 a 负责让它不再接受 Tauri 类型。它需要的事件出口、`OpenTargets`、路径都从 `shared` 或 `AppPaths` 取。
- 字段仍然是 `services.app.session_log`，骨架不改。a 读这个字段是允许的。`SessionLogState` 本身不依赖 `session` 分组的任何类型，所以类型层面没有环；分组只是存放位置，P1-09 移进 core 时再决定放在哪里。
- 读线程和后台任务捕获 `Arc<SessionLogState>`（或它需要的其他具体 `Arc`），不捕获 `AppHandle`。
- c 的 `config` 调用 `SessionLogState::validate_config`、`apply_config`。a 改了这两个方法的签名，就由 a 修 `config` 里的调用行（见第 3 节“跨卡改动”）。c 不改 `session_log`。

### 2.9 command 签名不变的自动核对

骨架批次新增 `scripts/migration/command-signatures.mjs`，从 `src-tauri/src` 中解析每个 `#[tauri::command]` 函数，输出排序后的 JSON：名称、模块路径、`rename_all` 等属性、IPC 参数（名称与类型，去掉 `State<…>`、`AppHandle`、`Window`、`WebviewWindow`、`Webview` 这些由 Tauri 注入的参数）、返回类型，以及 `generate_handler!` 的列表。

- 在 `f4b4b779` 上生成的结果提交为 `scripts/migration/command-signatures.json`。
- `node scripts/migration/command-signatures.mjs --check` 与它比较，有任何不同就失败；配一个 `node --test` 测试。
- a–e 每张卡都要跑 `--check`，结果写进报告。这个文件在 P1-07 期间不得修改。真要改，就说明 command 的签名变了，那是需要停下的偏差。
- 前端 `src/` 中的 `invoke` 调用另外用 `pnpm typecheck` 与现有测试保证。

## 4. 怎么证明行为不变

- **签名**：每张卡都跑 `command-signatures.mjs --check`（2.9）。
- **事件**：事件名、target 与 payload 已由 P1-02 至 P1-06 的契约测试覆盖（`prompt_contract_tests.rs`、各 `event_sink/<领域>.rs` 的 `wire` 测试）。各卡把 `TauriEventSink::new` 换成 `shared.events` 以后，这些测试必须照常通过，**不得修改期望值**。
- **同一实例**：骨架的 `Arc::ptr_eq` 测试保证过渡期两处取到的是同一份状态，不会出现“command 改了 A、后台读的是 B”。
- **全部检查**：AGENTS.md “Before you finish” 的全部检查；`cargo test --workspace` 在沙箱外跑。
- **端到端**：a 与 b 各跑一次 OrbStack 容器测试（SSH 连接、ZMODEM、SFTP 上传下载），做法同 P1-05、P1-06 的报告。
- **人工（隔离标识下，`dispatch.md` 第 5 节）**：只在 e 之后做一次，各卡不重复。步骤：
  1. 启动后 `list_profiles` 为空；
  2. 新建本地终端与 SSH 连接（容器）；
  3. 打开 SFTP、上传一个文件；
  4. 开一条隧道；
  5. 打开会话日志；
  6. 关闭到后台、从托盘恢复、退出（有隧道和传输时的退出确认）。
     用完删除临时标识的目录与密钥项。这些项并入 stone 的界面人工验收清单。

## 5. 风险

| 风险                                                      | 防法                                                                                                  |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 过渡期出现两份状态（`AppServices` 里新建了一份）          | 骨架的 `Arc::ptr_eq` 测试；规则写死“只能克隆，不能新建”                                               |
| 初始化顺序变了（例如在 `db::init` 之前读数据库）          | `AppServices` 构造只组装、不做 I/O；setup 中其余步骤的位置不动；评估者对比 setup 的前后 diff          |
| `Runtime` 在异步上下文中 drop 导致 panic                  | `AppServices` 只持有 `Handle`（2.4）                                                                  |
| 退出时 `state()` panic                                    | `RunEvent` 分支一律 `try_state`（2.5）                                                                |
| `blocking_write` 与 async 混用的位置被挪进 async 服务方法 | 服务方法保持原来的同步或异步属性；原来在 `run_blocking` 里的工作照旧在里面；不把同步锁跨 `await` 持有 |
| 测试原来用 `tauri::test::mock_app` 取状态                 | 服务方法不再接受 `AppHandle`，测试直接构造服务；原有 mock 测试改写时断言不变，报告列出改写的测试      |
| 四张卡改同一文件                                          | 骨架一次定义全部字段；各卡不改 `services/`；共享 `manage` 留到 e                                      |
| 托盘与菜单回调里拿不到服务                                | 回调属于 Tauri 入口，可以 `app.state::<Arc<AppServices>>()`（2.5）                                    |

## 6. 任务卡没有考虑到的地方

1. **适配层不在 a–d 的模块表里。**`prompt_scope.rs` 归 a，`lib.rs` 与平台适配层归 e；窗口类 command（1.3）不变薄。
2. **P1-07c 没有托管状态。**它的工作量主要是让 command 变薄、换掉 `AppHandle`，比表面看起来小。如果 c 先完成，可以接着做 e 的一部分，前提是 a、b、d 已经合并。
3. **`TokioRuntimeState` 不并入 `AppServices`**（2.4），P1-09 再决定 core 怎么拿运行时。
4. **单独托管要到 e 才全部删除。**任务卡的“共同验收”中“负责模块中除 command 外不再出现 `tauri::`”在 a–d 各自验收；“全仓只剩 `AppServices`”到 e 才成立。
