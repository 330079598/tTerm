### crate 划分

| crate | 内容 | 理由 |
| --- | --- | --- |
| `tterm-terminal` | `ThemeColors`、`PaletteText`、`OptionalText`、`THEME_COLOR_KEYS`、`TERMINAL_PALETTE_KEYS`、`Hsl`、`HslRgb`、`Rgba`、`TerminalPalette`、颜色解析/混色/HSL/亮度/对比度、`js_*` 辅助函数 | 绘制终端和关键词高亮都需要这些颜色类型；`tterm-terminal` 不能依赖 `tterm-core`，所以共享类型放在被依赖的一方。 |

### 前端颜色字符串到 xterm

TS 侧不是把 `PaletteText` 直接画出来，而是把它交给 xterm.js 6.0.0：

- `src/components/TerminalTab/useTerminalTheme.ts` 先用 `withWindowBlur` 处理主题的 `terminal`，再补 `overviewRulerBorder: "#00000000"`；
- `src/components/TerminalTab/openTerminal.ts` 把它作为 `new Terminal({ theme: themeRef.current, allowTransparency: ... })` 的初始主题，`src/components/TerminalTab/useTerminalConfigSync.ts` 之后更新 `term.options.theme`；
- xterm 的 `browser/services/ThemeService.ts::_setTheme` 逐字段调用 `css.toColor`。`common/Color.ts` 先处理 `#rgb[a]`、`#rrggbb[aa]` 和逗号分隔的 `rgb()`/`rgba()`；HSL 与具名颜色走 canvas，canvas 结果 alpha 不是 255 时抛错，`ThemeService` 回退该字段的默认值；
- 默认值分别是黑色背景、白色前景/光标、黑色 `cursorAccent`、xterm 的 16 个默认 ANSI 色和 `rgba(255, 255, 255, 0.3)` 选择背景；不透明选择背景会被 xterm 改成 30% alpha，光标和 `cursorAccent` 会与背景做 `color.blend`。

`PaletteText::to_terminal_palette` 复现的是这条链的**最终绘制值**，不是 CSS 字面值；因此 `hsl(207 100% 40% / 0.24)` 会得到默认的选择背景 `#ffffff4d`，而 `#rrggbb00` 的模糊背景会保留 RGB 和零 alpha。`allowTransparency` 只控制 xterm 是否允许透明绘制，不改变颜色解析结果。测试证据为 `css-colors.json` 的 162 个 xterm 值、112 个字段组合，以及 4 个生成调色板值。

有三处是等价的非正则实现，而不是绕过 ECMAScript 差异：

- `color_to_hex` 的 3/6 位 hex 分支和 `hex_to_rgb` 使用 `js_trim` 后逐字节检查 ASCII hex；TS 的对应表达式只包含 ASCII 字符类，因此 `is_ascii_hexdigit` 与 `/^[\da-f]{3}$/i`、`/^[\da-f]{6}$/i` 的结果相同。
- `import.rs` 的 `parse_color` 先按 TS `^['"]|['"]$` 去掉一个首尾引号，再检查 `#`/`0x` 后 6 或 8 位 ASCII hex；这与 TS 的 `^(?:#|0x)?([\da-f]{6})(?:[\da-f]{2})?$` 对主题文件可能出现的值等价，且所有格式的 oracle 用例都经过这条路径。
- `themeDerivation.ts` 的 `!/black|white/i` 在 Rust 里展开为固定 ANSI 键列表；这个键列表直接用 TS 常量顺序写出，不涉及字符集或大小写折叠，因此无需正则引擎。

## 偏差

1. **时钟注入。** `createCustomThemeFromPreset` 和 `normalizeCustomThemes` 在 TS 中直接调用 `Date.now()`（同一对象内调用两次）；Rust 改为接收 `now: i64`，由一个值同时填入 `createdAt`/`updatedAt`。测试用 oracle 中的固定 `1700000000000`；真实调用方传当前毫秒即可。这样可测且不引入系统时钟依赖。
2. **目录加载是同步静态数据。** TS 的 `loadThemeCatalog` 返回 `Promise`，通过动态 `import()` 做代码分割，失败时把缓存置空以便重试。GPUI 原生端不需要 WebView 的代码分割，Rust 用 `include_str!` 在编译期嵌入目录，`load_theme_catalog` 同步返回 `Result<&'static [CatalogTheme], &'static str>`；编译期错误不能运行时重试。目录内容仍是同一份 `src/assets/themes/catalog.json`，695 个主题的 digest 已核对。
3. **懒派生颜色用 `OnceLock`。** TS 的 `colors` 是对象 getter；Rust 的 `CatalogTheme::colors()` 返回 `&ThemeColors`，首次调用派生并缓存。TS 测试里的 `Object.getOwnPropertyDescriptor(...).get` 断言没有 Rust 对应物，改为指针身份 + 值相等；派生结果本身逐字节一致。
4. **导入结果的 JSON 字段顺序。** `ImportedScheme` 的字段名、可选字段省略和值都与 TS 完全一致；但 TS 的特殊颜色属性顺序取决于主题文件里首次出现的行序（例如 Alacritty 用例先写 `text` 再写 `cursor`），Rust 结构体按固定的“name、palette、background、foreground、cursor、cursorText、selectionBackground、selectionForeground”序列化。JSON 对象消费方不依赖键顺序，导入结果也不会直接写入数据库（`ThemeImportDialog` 先用它派生调色板）；持久化的自定义主题顺序另有逐字节测试。
5. **未知命名键的顺序。** `serde_json` 的 `preserve_order` 在 workspace 里原本由 `gpui-pre` 打开，而单独构建 `tterm-core` 时不会打开，曾导致同一份代码在不同构建方式下写出不同的未知键顺序。现在 `tterm-core` 与 `tterm-terminal` 都显式启用 `preserve_order`，`Cargo.lock` 未变化；`normalizedExtraOrderJson`、`normalizedShuffledJson`、`mergedExtraOrderJson` 以及单独运行 `cargo test -p tterm-core` 的键顺序测试都对此有断言。数字索引键仍按 JS 的枚举规则排在最前。
6. **非声明类型的成员。** TS 的 `normalizeCustomTheme` 只检查 `id`/`name`/`colors` 的真值，因此会保留数字 `description`/`baseTheme`、小数 `createdAt` 和字符串 `updatedAt`；Rust 现在用 `OptionalText::Json` 和 `Value` 原样保留这些值，见 `normalizedUnexpectedJson`。数字 `id`/`name` 仍会被丢弃：`src-tauri/src/themes.rs::theme_id` 要求非空字符串，真实数据库路径不会接受数字 id；`name` 也只由主题编辑器/导入路径写入字符串。若手工把数字 name 塞进旧数据库，TS 会显示它，而 Rust 会丢弃这个主题，这是对损坏数据的已记录收紧。
7. **字符串展开的代理对。** JS `{ ..."😀" }` 产生两个属性，值是孤立代理项 `"\ud83d"`/`"\ude00"`；Rust 字符串无法表示孤立代理项，`spread_entries` 用 U+FFFD 代替这两个单元，但键的数量和顺序仍按 UTF-16 单元计算。中文、组合字符等 BMP 输入与 TS 逐字节一致（见 `normalizedStringJson`）。孤立代理项的 JSON 也无法被后端 `serde_json` 读回，因此这类数据本来就不能持久化。
8. **`mergePresetThemeWithOverride` 的非规范覆盖。** 正常覆盖完全一致；若覆盖来自一个含 `null`/未知键的损坏自定义主题，Rust 合并时使用其类型化的 `colors`/`terminal`（`null` 变成默认值，未知键保留在类型侧），不会像 TS 的展开那样把 `null` 原样复制到合并结果。预设主题不持久化，且损坏数据不会由前端产生。
9. **`ThemeColors`/`PaletteText` 反序列化是严格形状。** `ThemeColors` 表示已解析的 28 个字符串 token，`PaletteText` 的必需字段也要求字符串；保存的主题必须通过 `normalize_custom_themes` 读取，后者接受缺字段、显式 `null` 和未知键（`PaletteText` 的 `cursorAccent`/`selectionForeground` 仍可显式 `null`）。这样避免了把“部分颜色”误当成完整主题。
10. **`catalogThemeFromScheme` 的 `name` 三种状态。** TS 模板字符串对缺失 name 得到 `"catalog:undefined"`，对显式 `null` 得到 `"catalog:null"`；Rust 的 `OptionalText::{Missing, Null, Value}` 分别复现这两种结果，已由 `createdFromSchemeMissingName`/`createdFromSchemeNullName` 覆盖。目录 JSON 的每个主题仍有字符串 name，这两种输入只在手写或旧数据中出现。
11. **`rgb_to_hex` 的 NaN。** 该函数在主题模块内只接收正则/有限数学产生的数字；TS 对 `NaN` 会输出 `#NaNNaNNaN`，Rust 的 `as u8` 会输出 0。这里明确把 NaN 排除在契约外，边界测试覆盖了负数、超过 255 和半整数。
12. **非法调色板转绘制形式。** `PaletteText::to_terminal_palette` 不再统一回退黑色，而是按 xterm `ThemeService` 的逐字段默认值处理：背景黑、前景/光标白、`cursorAccent` 黑、ANSI 使用 xterm 默认 16 色、选择背景回退 `rgba(255,255,255,0.3)`；非法选择前景得到 `None`。透明/半透明 canvas 颜色按 xterm 的 `alpha !== 255` 规则回退，因此生成主题里的 `hsl(207 100% 40% / 0.24)` 不会成为半透明选择色。
13. **本机编译修复不在任务卡范围内。** `311f80d2` 给 `objc2-foundation` 加 `NSEnumerator` feature，否则本机 `tterm-platform` 的默认构建无法编译 `Retained<NSArray<NSURL>>::iter`。这是独立提交，不改变主题行为，也没有改动 `src/` 或 `src-tauri/`。
14. **`Theme` 的 `Custom` 变体被装箱。** 这是 clippy `large_enum_variant` 的修复，`Theme::Custom(Box<CustomTheme>)` 不改变 JSON 字段或 API 语义；只在 Rust 内部减少枚举大小。`bc452af1` 的测试初始化重构同理，不改变期望值。

## 遗留问题

- Windows/Linux 的真实 GUI 主题应用与系统外观切换属于 P3-05；本轮只验证了纯逻辑和 macOS 本机构建/测试。
- 本轮未修改 `src-tauri`，因此没有通过真实 Tauri command 做数据库往返；持久化形状用 TS 的真实 `JSON.stringify` 与后端的 `serde_json::Value` 形状对齐，待 P1-07/P3-05 接线时再做端到端检查。
- 内置主题目录是 `src/assets/themes/catalog.json` 的编译期副本；主题库更新后需要重新编译，`the_catalog_digest_matches_the_oracle` 会提醒 digest 变化。
- 64 个被忽略的 zmodem/sshd 互操作测试需要真实 `sz`/`rz`/sshd，本轮没有为本机安装这些外部二进制。
