# P0-23 供 agent 使用的界面自动化与截图

## 结论

完成。GPUI 原型增加了只在 `automation` feature 且 debug 构建中编译的回环控制接口，提供窗口/焦点查询、受限按键、状态读写和 PNG 截图；脚本已在本机 Windows 11 从启动到退出跑通。

## 改动

- `crates/tterm-gpui/src/terminal_demo/automation.rs`：开发专用 TCP 接口、随机令牌、请求校验、按键白名单和窗口截图。
- `crates/tterm-gpui/src/terminal_demo/window.rs`：注册接口，并提供自动化状态切换与查询。
- `crates/tterm-gpui/Cargo.toml`：增加 `automation` feature；`image` 只作为该 feature 的可选依赖；Windows 复用固定 `windows 0.62.2` 的 Cryptography feature。
- `scripts/gpui-automation.py`：可复制运行的启动、状态切换、读回、截图和清理脚本。
- `crates/tterm-gpui/AUTOMATION.md`：启动方式、协议、限制和系统对话框禁止清单。

## 安全性

接口绑定 `127.0.0.1:0`，端口每次随机分配；每次启动生成 32 字节操作系统随机令牌。令牌写到独立的 `com.stone.tTerm.gpui-dev` 状态目录（或显式的 `TTERM_GPUI_AUTOMATION_TOKEN_FILE`），Unix 设置为 `0600`。缺少或错误令牌在进入请求队列前拒绝。Windows 使用 `BCryptGenRandom`，Unix 使用 `/dev/urandom`。接口不执行命令、不读写任意文件、不接受路径参数，也不做网络转发。按键只接受白名单，并在发送前检查原型窗口处于激活状态。

## GPUI 无头截图核实

- Windows 本机：`gpui-pre 0.3.11` 的 `HeadlessAppContext` 与测试平台源码存在，但 Windows 测试平台的文本系统是占位实现；本卡采用示例 `crates/tterm-gpui/examples/terminal_view.rs:224-289` 所示的真实窗口、屏幕外位置和 `Window::render_to_image` 路径。Windows 实测成功生成 20,731 字节 PNG。
- macOS、Linux：源码确认，未运行验证。`crates/tterm-parity/src/capture.rs:40-55` 使用 `HeadlessAppContext::with_platform` 和 `current_headless_renderer`；`gpui-pre-0.3.11/src/app/headless_app_context.rs` 提供无头上下文，`src/window.rs:3092` 提供 `render_to_image`，但发布版 API 仍受 test-support 条件限制。
- 相关遗留：P0-25 报告第 9、10 项确认 `debug_selector` 和 `capture_screenshot` 在发布版不可用；本接口不依赖它们，使用窗口级 `render_to_image`。

## 偏差

任务卡要求设置页，但当前原型只有终端视图，没有设置页。按任务卡已知出入，使用标题状态作为替代，没有新建设置页。建议后续 P3 设置页完成后，把脚本的 `action=toggle-title` 换成真实设置状态，协议保留 `state`/`screenshot` 契约。

GPUI 依赖通过 `gpui-kit 0.9.0` 带入固定的 `gpui-pre 0.3.11`；没有增加 git 依赖或版本升级。没有修改 `tterm-terminal-view`、`tterm-ui` 或 `tterm-parity`。

## 遗留问题

- Windows 的真实窗口截图依赖窗口系统和 GPU 驱动；本机已验证，Linux/macOS 仅源码确认，未运行验证。
- 接口目前按 TCP 文本协议工作，后续若评估环境需要同时运行多个原型，可在不扩大能力面的前提下增加实例发现文件；当前端口与令牌已足够单实例脚本使用。
- 任务卡要求的真实设置页验收留给设置页出现后的后续卡，不在本卡新增产品 UI。
