# P2-02 输出管线与背压

- 执行者：Codex
- 当前分支：`codex/P2-02-output-pipeline-backpressure`，基于 `5b757b1d`
- 实现提交：`70b73bf6`
- 本机：Windows 11，使用仓库固定的 Rust 与 pnpm 工具链

## 结论

**完成（Windows）。** GPUI 端输出现在由后台解析线程分批写入模型；解析队列和
`OutputFlow` 共同限制持续输出时的排队量。视图来不及消费输出时只会保留一个待处理的刷新，
不可见会话继续解析并确认，但不再请求快照或绘制。背压确认发生在对应输出已经写入
模型并处理完解析意图之后；普通输入和 Ctrl+C 直接走会话写入路径，不等待输出队列。

三项验收均通过：持续输出期间队列高水位固定在 `589,824` 字节；真实本地 PTY 输出洪峰
期间，普通输入写入为 `21.5µs`，Ctrl+C 写入为 `400ns`，从写入 Ctrl+C 到进程退出为
`51.9113ms`；30 个后台解析器持续输出时，前台准备的帧耗时 p95 为 `467.7µs`，低于
`16.667ms` 的 60 FPS 帧预算。前台 p50 从 `253.6µs` 升到 `283.0µs`，增加约 `11.6%`；
本文保留原始数值，不据此声称帧率完全不变。

### 行为变化

- 核心 `OutputFlow` 送来的块先按最大 `64 KiB` 切分，再进入容量为 8 块的同步队列。
  队列计数还把正在等待槽位的发送块计算在内，封顶为 9 × 64 KiB，即 `589,824`
  字节。解析线程当前批次最多 64 KiB，并最多保留一个 64 KiB 的待处理块；解析阶段
  自身因此有固定上限，不随输出总量增长。
- 解析线程不再等待凑满一批。它取到数据后只在队列已有数据时合并，批次达到上限就
  释放模型锁。这样一次大输出不会让界面快照等待整个 512 KiB 核心 IPC 块解析完。
- 每个 ACK 对应一个真实模型批次，并在模型写入和所有解析意图处理完之后发出。关闭
  代次拒收的迟到批次也会 ACK，避免读取线程永久卡在不再绘制的数据上。
- `RefreshSignal` 使用一个原子待处理位合并唤醒。视图在开始处理刷新时确认该位；
  持续解析不会堆叠 watch 通知。新订阅会清除无接收者期间留下的待处理位，避免重附着
  后下一条输出被旧位抑制。
- 隐藏会话仍解析和 ACK，模型内容与回滚区保持最新，但不发送输出刷新。重新进入标签
  时主动请求一帧以显示隐藏期间积累的内容；新会话继承标签当前的可见状态。
- `ViewStats` 增加每帧快照数，`Terminal` 增加快照数、等待锁时间、持锁总时间和最大
  持锁时间。计时只覆盖获取公平锁和复制可见行，不包括排版、字体测量或绘制。

## 验收

任务卡验收原文：

> P0-01 的持续输出负载下内存有界；输入与 Ctrl+C 在持续输出时仍能及时响应（报告给出延迟数据）；30 个后台会话同时输出时，前台终端帧率不明显下降。

| 验收条件                         | 结果 | 证据                                                                                                                                                                                                                                                                                                                                                       |
| -------------------------------- | ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 持续输出下内存有界               | 通过 | `sustained_output_keeps_the_queue_bounded_and_applies_every_byte` 验证 128 块持续输出全部解析、回滚区受配置上限约束且队列不超过 `MAX_QUEUED_BYTES`。`a_blocked_acknowledgement_stops_the_producer_within_the_memory_bound` 在 ACK 被阻断时测得 `producer_progress=589824 bytes`、`queued_high_water=589824 bytes`、`limit=589824 bytes`；放行后 8 MiB 输出全部发送并逐字节确认。 |
| 输入与 Ctrl+C 及时响应           | 通过 | Release 模式真实本地 PTY 洪峰测试 `input_and_ctrl_c_bypass_a_saturated_output_parser`：`input=21.5µs`、`ctrl_c_write=400ns`、`ctrl_c_to_exit=51.9113ms`。普通输入写入预算是 100 ms，Ctrl+C 到进程退出预算是 5 s。                                                                                                                                        |

## 偏差

1. **帧指标来自 GPUI 测试窗口，不是合成器 FPS。** 基准直接重复准备并渲染 120 个前台帧，
   同时运行 30 个真实解析线程和隐藏模型。它衡量前台帧准备/绘制成本和后台解析器争用，
   没有运行 30 个实际标签、窗口管理器和 GPU 合成器，也不等同外部帧率采集。
2. **输入数据是写入与被中断延迟。** `21.5µs` 和 `400ns` 是调用会话输入到写入 core 的耗时，
   `51.9113ms` 是 Ctrl+C 写入后到真实 PTY 进程退出、退出行进入模型的耗时；不是键盘事件到
   屏幕像素的端到端延迟。
3. **内存证据使用结构性上限和队列高水位。** 测试验证 `OutputFlow`、解析队列、模型批次和
   固定回滚区都不会随持续输出增长，没有用整进程 RSS 作为平台无关的通过条件。窗口线程和
   图形后端自身分配不计入解析队列指标。
4. **64 KiB 切分可能跨越 UTF-8 或转义序列边界。** Alacritty 解析器按流保存跨写入状态；
   本卡的分块只限定每批持锁工作量。P2-01 已有的普通、中文和转义输出测试保持通过。
5. **当前窗口仍是单标签原型。** 可见性接口已经按每个 `TabBinding` 同步，30 会话性能测试
   直接创建 30 个会话解析器；真实多标签 UI 仍属于后续窗口/标签工作。
6. **与 Tauri 的对比是同一核心实现和源码路径对比。** 本次没有同时运行 Tauri 与 GPUI 的
   端到端基准，因此帧与输入数字只描述 GPUI 路径，不宣称原生版在所有场景更快。
