# W0-04 界面对齐工具链

## 结论

完成。工具链两端已经跑通：`vite --mode parity` 用夹具替换 `invoke`、事件与 `Channel`，Playwright WebKit 按清单截参考图并导出布局 JSON；`crates/tterm-parity` 用 GPUI 无头 Metal 渲染同一夹具构建的屏幕，导出同格式布局，再由 `compare` 输出布局差、颜色差、SSIM、热力图、HTML 报告与 `result.json`。

示例屏幕 `example.button-input.default`（一个按钮加一个输入框）通过：布局最大偏差 0.25 像素，整屏 SSIM 0.998504，遮文字 SSIM 1.000000。把 GPUI 按钮内边距从 16 改成 17 像素后工具退出 1 并指名 `example.button`；改回后再次通过。同一输入连续两次的 `result.json` 与热力图 SHA-256 完全相同。

未验证项见[遗留问题](#遗留问题)，主要是 Windows/Linux 的自动/人工对照、Playwright WebKit 与真实 Tauri WKWebView 的交叉核对，以及 125% 缩放、浅色等组合。

### 净室与来源

- 只读取了 GPUI 源码（`gpui-pre-0.3.11`、`gpui-kit-0.9.0`）与 tTerm 自己的代码；Zed 的 `terminal`、`terminal_view` 等 GPL crate 没有读取或引用。
- 没有从任何仓库复制实现代码。Playwright、`image`、`serde`、`serde_json` 都是 crates.io/npm 官方来源；GPUI 版本仍由 `pins.md` 的 `=0.9.0` / `=0.3.11` 固定。
- 参考端实现是 tTerm 自己的 React 组件，不是复制品；`debug_selector` 的替代方案依据 GPUI 的公开 API 编写。

## 偏差

1. **起点提交不是 `c42a888`。** 开始前 `git rev-parse GPUI` 是 `527f247`（P0-28 的收尾提交），命令里的 `c42a888` 与集成分支实际不一致。分支从 `527f247` 切出；没有切换或合并 `GPUI`。建议在后续卡里以 `git rev-parse GPUI` 为准。
2. **worktree 路径与创建方式。** 任务要求 `git worktree add ../tTerm-<任务ID>`。第一次执行时沙箱只允许写仓库内，创建失败但 git 已经建好分支；放宽到 `danger-full-access` 后用同一分支完成创建，路径仍是 `../tTerm-W0-04`。随后会话文件策略改为不限制，工作树没有再移动。
3. **`debug_selector` 的替代。** GPUI 只在 `cfg(any(test, all(debug_assertions, feature = "test-support")))` 下把 `debug_selector` 的边界写入 `rendered_frame`（`gpui-pre-0.3.11/src/elements/div.rs:2579`），而读取它的 `VisualTestContext::debug_bounds`（`src/app/test_context.rs:1031`）属于 test-support，`HeadlessAppContext` 没有暴露读取入口。本工具改用 `Div::on_children_prepainted`（`src/elements/div.rs:1862`）记录单个子元素的 border box，并用 `parity_text` 记录文字元素自身边界；任何构建模式都可用，不依赖 `debug_assertions`。代价是每个标记元素必须只有一个子元素（示例屏幕与 README 都写明了这一约束），且 `debug_selector` 仍然没有被本工具验证。若 P0-25 最终给出可用的无头读取 API，可以替换 marker 实现而不改 JSON 契约。
4. **布局 JSON 是 5.1 节字段的超集。** 在“位置/尺寸、背景、边框、圆角、字体族/字号/字重/行高/文字颜色”之外，增加了 `sizing`（`fixed`/`text`）、`padding`、`textRegions` 与 `invokedCommands`。`padding` 参与比较（容差 0.01px），这比 5.2 节更严格，是为了让“1px 内边距”在文字尺寸元素的 2px 宽度容差内仍然被判失败。`invokedCommands` 只在参考端存在，比较时忽略。
5. **字体族归一化。** React 的 `-apple-system` 与 GPUI 的 `.SystemUIFont` 是同一个 macOS 系统字体，但字符串不同。两端都归一成 `system-ui` 后再逐字比较；没有把完整字体栈写进 JSON，因为 Windows/Linux 的回退栈不同，写死反而会误判。
6. **示例屏幕的样式覆盖。** 示例屏幕用真实的 `Button` 与 `Input`，但额外设了 `lineHeight: "16px"`、`rounded-[4px]`、`shadow-none`、`dark:bg-transparent`。原因分别是：GPUI 把行高取整到像素、CSS 允许小数；`rounded-md` 在 `--radius: 0.25rem` 下的计算值容易随 Tailwind 版本变化；`Input` 默认的 `shadow-xs` 与 `dark:bg-input/30` 会把阴影和半透明叠色带进比较。这些覆盖只存在于 parity 示例屏幕，不改变产品组件。
7. **界面缩放只开放 100%。** 清单校验会拒绝其它 `uiScalePercent`，避免用 100% 的 token 截 125% 的图。浅色与深色在 GPUI 侧都接了 token，但本轮只验证了 dark 100%；125%、浅色、孤岛风格、窗口模糊是 W0-05 的组合。
8. **参考缓存键是“最后一次改动前端输入的提交”，不是任意 `HEAD`。** 路径列表见 `crates/tterm-parity/src/reference.rs` 的 `FRONTEND_PATHS`；`parity/README.md` 与 `docs/` 不在其中（`4cbc067` 修正）。这样只改文档不会让参考图失效。`compare` 在缓存缺失时自动生成，`UPDATE_REFERENCE=1` 强制重新生成；参考 PNG 不进 git。
9. **参考端用 Playwright WebKit，不是 Tauri 窗口。** 与 ui-parity 5.1 节一致；macOS 上是同一引擎与 CoreText。没有做“真实 Tauri 窗口与 Playwright 并排”的交叉核对，见遗留问题 3。
10. **GPUI 截图是无头 Metal 渲染，不是 `screencapture`。** 本环境没有屏幕录制权限；`HeadlessAppContext` + `current_headless_renderer()` 输出的是同一场景的实际像素，W0-04 的示例屏幕没有窗口级效果需要真实窗口。真实窗口效果留给后续屏幕的 `[人工]` 步骤。
11. **Playwright 固定 1.54.0 而不是最新版。** 1.54.0 对应 WebKit revision 2191，本机缓存已有该构建；升级 Playwright 会同时换 WebKit，不在本卡范围。浏览器下载与 npm 安装是两步，README 已写明。
12. **报告与证据路径。** 任务卡的“产出”写的是 `parity/README.md`，执行说明要求 `docs/gpui-migration/parity/README.md`；完整说明放在后者，前者保留一个 9 行指针。参考 PNG 不进 git；提交的是布局 JSON、GPUI 实际截图、热力图与结果 JSON 的副本，均在 `docs/gpui-migration/reports/assets/W0-04/`。

## 遗留问题

1. **W0-05 的全部屏幕与 `data-parity`。** 本卡只做了一个独立示例屏幕；真实产品组件上的 `data-parity`、`screens.md`、`exceptions.md`、每个状态的夹具与参考图都还没做。W0-05 应复用 `parity/screens.json`、`scripts/parity`、`ScreenView` 和 `LayoutSink`，不要另起一套。
2. **Windows 与 Linux。** 自动出图只在 macOS 验证；Playwright WebKit 在 Windows/Linux 的字体回退与 macOS 不同。ui-parity 5.3 要求每个大类至少一屏人工并排检查，本卡没有做。布局 JSON 的三平台生成路径已经具备，但 CI 还没有接入。
3. **Playwright WebKit 与真实 Tauri WKWebView 的交叉核对。** ui-parity 5.1 要求每个大类抽一屏用真实 Tauri 窗口截图（`screencapture -l`）核对一次，证明两者没有系统性偏差。本卡只有示例屏幕，且该环境没有屏幕录制权限，未做；建议 W0-05 或 P0-24 用真实分类屏幕补 `[人工]` 证据。
4. **125% 缩放、浅色/孤岛风格、窗口模糊。** 本轮只验证 dark 100% 的普通控件；组合矩阵、元素级模糊（第 4 节替代项）与圆角裁剪都没有进入工具。W0-05 的清单需要把这些组合列出来，并在 `exceptions.md` 登记不可比区域。
5. **`debug_selector` 仍是更直接的方案。** 当前 marker 依赖“一个子元素”的约定，真实组件（按钮内部有图标与文字、输入框有前后缀）需要额外包装层；W0-05 要评估包装层会不会改变布局。如果 GPUI 后续公开无头读取 debug bounds 的 API，建议替换并删除包装约束。
6. **alpha 颜色在非均匀背景上的比较基准。** 现在把半透明元素叠在屏幕左上角像素（示例是纯色页面背景）上比较；嵌套在卡片、选中行或渐变上的半透明元素会不准确。W0-05 需要把父元素背景带进布局 JSON，或按区域取背景。
7. **SSIM 是工具自己的实现。** 16×16 不重叠窗口、遮罩窗口剩余不足 32 像素就跳过；阈值按 5.2 节，但数字不能与其它 SSIM 实现直接对比。真实屏幕文字更多时，整屏 SSIM 可能被文字拉低到 0.97 以下，需要按 5.2 的例外机制处理，而不是放宽门槛。
8. **参考缓存与 CI。** 参考图在本地 `target/`，没有接入 CI 缓存；干净评估环境第一次 `compare` 需要下载 WebKit 并重新截参考图（本机约几秒，干净环境取决于浏览器下载）。W0-05 若要批量 1200–1400 张，需要把参考生成拆成可缓存的步骤。
9. **`ERR_PNPM_IGNORED_BUILDS`。** 本机 pnpm 对 esbuild 的安装脚本给出该提示；没有通过配置绕过。若 CI 或其它机器因此失败，应作为独立的环境问题处理，不要把它混进 W0-04 的检查结论。
10. **示例按钮宽度 0.25px 差异。** 来自 CoreText 在 WebKit 与 GPUI 中的文字宽度取整差异，文字尺寸元素允许 2px，因此通过；如果后续屏幕对像素级宽度更敏感，需要把文字测量差异记录到例外或调整元素分类。
