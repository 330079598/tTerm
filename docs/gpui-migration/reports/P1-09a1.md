### 依赖倒转与调用顺序

#### 1. ZMODEM transfer wire（`afe004a6`）

- 改前：`ZmodemReceiveDriver` → `event_sink::zmodem::transfer_wire` →
  `serde_json`。
- 改后：`ZmodemReceiveDriver` → `zmodem::wire::transfer_wire` →
  `serde_json`；`event_sink::zmodem` 与 `event_sink::serial` 反过来调用这个
  中性函数。
- `TransferEvent` 的 wire 形状没有变化，既有
  `event_sink::p1_03_tests::transfer` 测试通过。

#### 2. io_batcher 测试 sink（`3f9d2a8c`）

- 改前：`test_sink` → `tauri::test::mock_builder` → `TauriSessionSink`。
- 改后：`test_sink` → `RecordingOutputSink`（`TerminalOutput` +
  `tterm_core::session::recording::RecordingSessionSink`）。
- `send_bytes` 同时传给输出通道和记录 sink；`state_changed`、`exited`、
  `ack_output`、`close_output`、`note_input` 与 `answers_input` 的调用顺序
  保持原样。生产代码没有变化。

#### 3. PTY 拆除 helper（`bd4fd9c7`）

- 改前：`core/commands/create.rs` → `core::commands::stop_pty_session`
  （在 command 文件内的私有函数）→ PTY map、ZMODEM map 和 supervisor。
- 改后：`core/commands/create.rs` → `core::session::stop::stop_pty_session`
  → 同一组状态和 supervisor；函数体只移动，没有改顺序。

#### 4. SFTP 上传与删除 helper（`4211c60b`）

- 上传改前：`upload::commands::sftp_check_upload_conflicts` →
  `commands/operations.rs` → `commands::collect_upload_conflicts`；
  `upload::items` → `commands::resolve_upload_target`。
- 上传改后：同一 command → 同一 service →
  `upload::targets::collect_upload_conflicts`；`upload::items` →
  `upload::targets::resolve_upload_target`。
- 删除改前：`delete::commands::operations` →
  `delete::commands::delete_directory_recursive`。
- 删除改后：同一 service → `delete::recursive::delete_directory_recursive`。
- 两处都是同一实现的搬运，冲突决策和递归删除的调用顺序未变。

#### 5. external edit 路径（`330984b4`）

- 改前：`sftp_external_edit_open` command 接收 `AppHandle` →
  `app_paths::get(&app)` 返回 `Result<AppPaths, String>` → service；
  `start_session` 在下载前才把该 `Result` 解包。
- 改后：command 从 `services.shared.paths` 克隆
  `Arc<AppPaths>` → service → `start_session` 直接接收 `&AppPaths`。
- AppPaths 的解析时点因此从 service 内的 `start_session` 前移到
  command 构造依赖时；路径值和后续下载顺序不变。移走的是注入的
  `AppHandle`，不是 IPC 字段，`command-signatures` 检查仍然通过。旧路径
  在路径未初始化时会返回错误；现在读取 `AppServices` 中同一个已初始化
  的 `Arc<AppPaths>`，正常启动下两者等价。

#### 6. 已符合方向、无需额外倒转的项

- `sftp/internal/api/search.rs`：服务函数本来接收
  `Arc<dyn SearchResultSink>`，`TauriSearchResultSink` 在 command 内构造；
  本次只把 command 搬到 `search_commands.rs`。
- `session_log/mod.rs`：`load_terminal_log_recording_service` 与
  `load_terminal_log_text_service` 本来就返回 `Result<Vec<u8>, String>`，
  `tauri::ipc::Response` 只在 command 内包装；本次没有改服务返回类型。

## 偏差

1. **三个适配文件不需要搬运。** `ssh/known_host_commands.rs`、
   `ssh/secret_commands.rs`、`zmodem/commands.rs` 原本就是 command-only，
   起始图也没有把它们列为阻断项；本卡没有把它们的内部服务 helper 再拆
   文件。
2. **`core/blocking.rs` 是文档命中。** 文件里只有文档注释提到
   `#[tauri::command]`，没有 Tauri 类型或调用；本卡未改它，最终图也没有
   可移动文件依赖它。
3. **search 与 session log 没有额外倒转。** 这两处已经在迁移前满足
   “逻辑接收中性参数/返回中性类型、command 负责 Tauri 包装”的方向；
   本卡只移动 command，没有改服务接口。
4. **`zmodem/commands.rs` 仍含内部 service helper。** 它没有被可移动文件
   引用，所以不属于本卡的规则 3 触发项；若后续要求所有 command 文件只
   保留 command 与胶水，可在 P1-09b 前单独清理。
5. **起始编译曾遇到增量缓存 ICE。** 克隆来的 `target/` 在首次
   `cargo check` 时报 stale incremental fingerprint；执行
   `cargo clean -p tTerm` 后重跑通过，后续所有提交和最终检查均正常。
   这是本地缓存问题，不是代码失败。
6. **未运行 Tauri 版。** 按决策 017，本卡不需要启动 Tauri 版；没有读写
   `com.stone.tTerm` 或 `com.stone.tTerm.dev` 的数据目录。

### 修正

#### 1. 失效的文档链接

- `ssh/auth.rs:191` 的 ``[`respond_ssh_auth_prompt`]`` 改为普通文本
  `` `respond_ssh_auth_prompt` ``，不再指向已经移到

  [cargo-doc-private-round2.txt](P1-09a1-evidence/cargo-doc-private-round2.txt)。

#### 2. SFTP command 模块统一由父模块声明

`sftp/internal/api.rs` 现在直接声明六个 command 模块；六个逻辑模块删除了
`#[path = "..._commands.rs"]`。command 文件仍与逻辑模块同级，模块路径
从 `api::<domain>::commands` 改为 `api::<domain>_commands`：

| 文件                                        | 改前模块路径                 | 改后模块路径                |
| ------------------------------------------- | ---------------------------- | --------------------------- |
| `sftp/internal/api/base_commands.rs`        | `api::base::commands`        | `api::base_commands`        |
| `sftp/internal/api/archive_commands.rs`     | `api::archive::commands`     | `api::archive_commands`     |
| `sftp/internal/api/download_commands.rs`    | `api::download::commands`    | `api::download_commands`    |
| `sftp/internal/api/edit_commands.rs`        | `api::edit::commands`        | `api::edit_commands`        |
| `sftp/internal/api/permissions_commands.rs` | `api::permissions::commands` | `api::permissions_commands` |
| `sftp/internal/api/search_commands.rs`      | `api::search::commands`      | `api::search_commands`      |

`lib.rs` 的 15 条 `generate_handler!` 路径同步更新。现在
`rg '#\[path = ".*_commands\.rs"\]' src-tauri/src` 和
`rg 'api::(archive|base|download|edit|permissions|search)::commands' src-tauri/src`
都没有输出。

command 文件成为逻辑模块的兄弟后，`base/operations.rs` 等文件里的
`pub(super)` 只对各自的父模块可见，command 文件无法读取相关 service、
Input 与 Dependencies 类型。因此：

- 六个逻辑模块里的 `mod operations;` 改为 `pub(super) mod operations;`；
- 六个 `operations.rs` 中 153 处项或字段的 `pub(super)` 改为
  `pub(crate)`；
- command 文件的 `use super::operations::...` 改为
  `use super::<domain>::operations::...`。

这是本次结构调整唯一超出“路径与 `mod` 声明”的改动，只放宽了 crate 内
可见性，没有改函数签名、字段顺序或逻辑。

#### 3. 文档注释

- `zmodem/wire.rs` 的 `transfer_wire` 增加文档注释，说明它把
  `TransferEvent` 序列化成 Tauri ZMODEM 与串口传输事件使用的 JSON
  payload。
- `core/session/stop.rs` 为 `StopPtyContext`、它的两个字段和
  `stop_pty_session` 增加文档注释，说明该结构标识要停止的会话，函数负责
  取消 prompt、关闭输出并移除 ZMODEM 与 supervisor 状态。
