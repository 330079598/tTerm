# P0-09 终端模型（官方 Alacritty）

## 结论

完成。`crates/tterm-terminal` 现在封装官方 `alacritty_terminal 0.26.0`：写入 UTF-8 字节、resize、回滚容量、可见区域快照（行、单元格语义色、光标、模式、显示偏移、选区）、损坏行、版本号，以及以“意图”形式交出的标题、响铃、剪贴板与需要回写 PTY 的应答。模型不依赖 GPUI、Tauri 或 `tterm-ui`，不持有 PTY 写端，不做绘制与输入。45 个测试全部通过，其中包含 10 万组抗崩溃测试与“快照拷贝量与可见行数成正比”的测试。

### 净室声明

本人（本卡执行者）**未阅读 Zed 的终端源码**（`terminal`、`terminal_view` 等 crate），也没有把其中的代码、注释、类型名或测试带进 tTerm。设计依据只有 [`terminal-design.md`](../terminal-design.md)、官方 `alacritty_terminal 0.26.0` 的文档与源码，以及 tTerm 自己的代码。实现中的类型与命名均为 tTerm 自有（`Terminal`、`Snapshot`、`Damage`、`Intent`、`GridSize` 等）；与 Alacritty 的交互只使用其公开接口，没有复制文件，因此无需登记到 `third-party.md`。

### 抗崩溃测试的输出

`cargo test -p tterm-terminal --lib -- --nocapture`：

```text
hostile input crash test: seed=0xe09202611050001 groups=100000 elapsed=2.83s grid=GridSize { columns: 37, screen_lines: 5 }
test tests::absorbs_a_hundred_thousand_hostile_inputs_without_panicking ... ok
```

该测试的行为：

1. 定种子的进程内 SplitMix64（测试文件里 20 行，不新增依赖，没有用 proptest）。
2. 每组的分布：1/10 随机 resize（1–40 列、1–12 行、任意单元格像素尺寸），1/10 随机滚动/选区，3/10 从手写边界语料取一条，5/10 随机字节流（1–96 字节）。随机字节的字母表刻意偏向 `ESC [ ] P p 0-9 ; : ? < > = \ 0x07 0x9b 0x9c`、无效 UTF-8 字节与中英文混合字符。
3. 手写边界语料 45 条：截断的 CSI（`ESC`、`ESC[`、`ESC[1;`、`ESC[?`）、未终止的 OSC/DCS、坏 base64 的 OSC 52、超长参数（`ESC[999999999999999999999999m`）、越界的 `38;5;999`/`58;5;300`、越界的光标定位与滚动区域、`ESC[?2026h` 同步更新、备用屏幕切换、鼠标模式、坏 UTF-8（`0xff 0xfe 0x80`、被截断的 4 字节序列、代理项 `0xed 0xa0 0x80`）、C1 控制字节等。
4. 每 1024 组取一次快照，并断言帧形状：行数等于网格行数、单元格数等于 `行 × 列`、每行长度等于列数、光标列在网格内。
5. 另外两个测试覆盖手写语料本身：`boundary_sequences_are_absorbed` 把 45 条序列各写两遍（整批一次、逐字节一次，模拟会话读取的任意切分），`overlong_parameters_and_strings_are_absorbed` 写入 20 万个参数的 CSI、20 万字节未终止 OSC 与 20 万字节未终止 DCS。

这次抗崩溃测试抓到一个上游问题：把历史里含宽字符的终端 resize 到 **1 列** 时，Alacritty 0.26.0 的重排没有在 60 秒内结束（同一进程在 group 429 的 `33×4 → 1×11` resize 处停住；把同一 seed 的 resize 下限改成 2 列后，10 万组 2.83 秒跑完）。模型因此在 `GridSize::MIN_COLUMNS` 里把列数下限固定为 2，见“偏差”第 1 条。

### 快照拷贝量的输出

`cargo test -p tterm-terminal --lib snapshot_copy_volume -- --nocapture`：

```text
snapshot copy: 1000 history lines held with a 1000-line cap vs 11977 with a 100000-line cap; 960 cells copied from each
test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 41 filtered out; finished in 0.03s
```

测试设置：两个终端都是 24 行 × 40 列可见，回滚容量分别为 1 000 与 100 000 行；写入同样的 12 000 行输出。断言：

- 两个会话实际持有的历史分别是 1 000 行与 11 977 行（相差约 12 倍，容量相差 100 倍）；
- 两帧的 `cell_count()` 都是 `24 × 40 = 960`，即同样 24 行可见行拷贝的单元格数完全相同；
- 两帧的行数与可见文本逐行相等；
- 把大回滚会话滚到顶部后再取快照，仍然只拷 960 个单元格，行数仍是 24，`screen_row` 仍然把绝对行映射到 0–23。

代码层面的依据：`take_snapshot` 只调用 `Term::renderable_content()` 的 `display_iter`（视口起点开始、共 `screen_lines × columns` 个单元格），`copy_rows` 用 `take(columns)` 按行收集；`history_size` 由 `total_lines - screen_lines` 一次减出来。回滚区只在 `scroll_display` 改变显示偏移后才会出现在视口里。

### 损坏行的行为

| 测试                                              | 断言                                                                                               |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `in_place_updates_damage_only_their_rows`         | 不滚动屏幕时，只有被写的行带列范围，未被碰的第 1、2 行不在损坏列表里                               |

## 偏差

1. **模型把列数下限固定为 2（任务卡未要求）。** 设计说明 5.1 只要求视图把最小宽度钳到两个单元格，理由是 Alacritty 在一列宽时渲染某些 emoji 会出错。P0-09 的抗崩溃测试发现更严重的问题：把历史中含宽字符的终端 resize 到 1 列后，Alacritty 0.26.0 的重排在 60 秒内没有结束（同一 seed 在 group 429 的 `33×4 → 1×11` 处停住；把下限改成 2 列后 10 万组 2.83 秒跑完）。因此 `GridSize::MIN_COLUMNS = 2`，`GridSize::new` 与 `Terminal::resize` 都会把 1 列提到 2 列，并有回归测试 `a_one_column_grid_is_raised_to_two`。建议：设计说明 5.1 补一句“模型层同样保证两列下限，视图直接使用快照里的列数”，并在 P0-10/P0-12 沿用同一常量；这样任何调用方都不会触发上游的重排问题。
2. **视图命令是立即应用，而不是排队到取快照时统一应用。** 设计 3.1 第 6 步与 8.4 描述“视图把命令排队，模型在下一帧取快照前按入队顺序应用”。P0-09 还没有视图与命令队列，`scroll`、`select`、`extend_selection`、`resize`、`set_scrollback` 都在调用时立即在锁内执行；同一线程的顺序由调用顺序决定，跨线程的顺序由锁的获取顺序决定。这样接口简单、每个命令都能单独测试，但“同一帧内先滚动再取快照”的语义要靠调用方保证。建议 P0-12 在需要时加一个 `apply` 队列（可以包在现有方法外面，不必改快照接口），并在设计说明里写清 P0-09 的过渡形态。
3. **搜索匹配没有进入快照。** 设计 4.1 把“匹配的网格范围、活动匹配、版本”列为快照内容；任务卡第 3 条只要求“先用 Alacritty 自带的能力，接口按 P2 的需要设计”。P0-09 提供 `Search` 与 `Terminal::find_next`，返回网格范围；匹配集合、活动匹配与失效规则留给 P2-07。建议 P2-07 在模型里加搜索状态（版本号可复用 `Snapshot::version` 或单独一个），并在快照里带上可见匹配。
4. **与 Tauri 版的内建应答不同。** 旧版在 `src-tauri/src/terminal/ssh_query_handler.rs` 里拦截并回答 DA1（`ESC[?64;1;2;4;6;9;15;21;22c`）、CPR（固定 `1;1`）、OSR 与 XTGETTCAP（`Co`/`Ms`）；新模型用 Alacritty 的内建应答：主 DA 为 `ESC[?6c`，CPR 报告真实光标，XTGETTCAP 不回答。这不是设计与实现的偏差，但会让程序看到不同的终端身份和不同的光标位置。建议 P2-12 决定唯一应答方时明确保留哪一套，并把 XTGETTCAP 的 `Ms`/`Co` 处理移到 core 或模型；P0-15 的兼容性冒烟应与 xterm.js 版逐项对比。
5. **`history_size` 的语义是“当前持有”，不是“容量”。** 设计 4.1 的“回滚总行数”没有区分两者。快照里给的是当前持有的历史行数（滚动条几何需要它），容量由 `Terminal::scrollback()` 提供。建议设计 4.1 把两者分开写，避免 P0-12 把容量当成长度画滚动条。

### 与设计说明核对一致、无需修改的点

- 4.3 “每次屏幕滚动报整屏损坏、逐行损坏只出现在原地修改”：两个测试分别验证（见“损坏行的行为”）。
- 4.3 “光标所在行每次都会出现在损坏范围里”：`the_cursor_row_is_damaged_in_every_frame` 验证。
- 4.5 “翻看历史时新输出报整屏损坏，显示偏移同步增加”：`output_while_scrolled_back_is_fully_damaged` 验证。
- 4.1 “颜色保留语义色”：`colors_keep_the_semantic_form_the_application_asked_for` 验证命名色、索引色与真彩色都原样保留。
- 4.2 “屏幕行 = 绝对行 + 显示偏移”：`screen_rows_follow_the_display_offset` 覆盖负行、顶部、底部与视口外。

## 遗留问题

1. **P0-12 的回滚锚定尚未实现。** 模型只提供 `display_offset`、`history_size`、`scroll` 与 `screen_row`；写满后淘汰造成的锚点漂移、视口内容比对或行身份方案都还没有。P0-12 应基于 `output_while_scrolled_back_is_fully_damaged` 的场景扩展测试。
2. **P0-10 的绘制与行级缓存。** 快照目前每帧为每行分配一个 `Vec<Cell>`，接口已经暴露损坏行与列范围，但行级写时复制没有做。设计 4.3 推荐的行级 CoW 可以在 P0-10 按测量结果再加，不影响现有接口。
3. **P2-07 的搜索状态。** 现在的 `find_next` 在整个调用期间持锁；大回滚区的后台分块扫描、取消与结果版本要等 P2-07。
4. **P2-12 的单一应答方。** 见“偏差”第 4 条：DA1/XTGETTCAP/CPR 与旧版不同，OSC 10/11 的颜色查询需要 core 提供调色板值，OSC 52 的读写策略需要与会话设置接线。
5. **唤醒粒度。** 模型不告诉调用方“这一批是否改变了可见内容”；会话层目前应在任意批次后唤醒视图，由视图取快照时拿到损坏信息。设计 3.3 的“没有变化就不唤醒”是优化项，P0-10/P2 若测到无效帧再补。
6. **未验证：Windows 与 Linux。** 本机只跑了 macOS 27.2；crate 没有平台相关代码，CI 在三平台运行同一组检查，但本次没有本机证据。
7. **沙箱的 `openpty` 失败。** 见“检查”一节；它不是本分支引入的，也无法在沙箱里修复。
8. **抗崩溃测试的边界。** 随机输入按字节生成，没有模拟会话层的分片策略；分片由 `boundary_sequences_are_absorbed` 的逐字节写入覆盖。若后续发现某类序列值得专门构造，应加进 `BOUNDARY_SEQUENCES` 语料而不是调大迭代次数。
