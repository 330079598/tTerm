# P1-10 WebView 本地存储迁入后端

## 结论

完成。WebView 里属于用户数据的 9 个 localStorage 键已经改由 `app_meta` 保存；首次启动只补后端缺少的键并保留 localStorage 原值，后端已有的合法值优先，此后每次成功写入后端都会把同一值按 0.8.x 的格式双写回 localStorage，并用每键指纹识别“回退到旧版后又改过”的数据并重新导入。启动加载失败时会话退回 localStorage；降级会话中导入备份会先按导入值重试迁移，失败则继续保持降级到重启。备份和同步前恢复备份里的前端状态改由后端读取同一个存储。备份格式没有变化，旧备份可以导入。

这项改动必须随一个正式的 Tauri 版本发给用户，并在用户机器上至少成功运行一次；GPUI 版读不到 WebView 的 localStorage。按 P5-03 的两级升级，建议用 0.9.0 作为过渡版、保留原值到 0.10.0，并在切到 GPUI 版之前留出足够的升级时间，不能假设用户会立即升级。若用户跳过过渡版，GPUI 版只能按 P5-03 的约定提示恢复默认或先安装过渡版。

`app_meta` 里的迁移标记是 `frontend.migrated`，值为 `{"version":1,"migratedAt":<Unix 毫秒>}`。每个用户数据键还有一行 `frontend.synced.<键名>`，内容是最后一次成功同步到 localStorage 的规范化 JSON 文本，例如 `frontend.synced.recent_commands`。命令白名单仍只接受 9 个用户数据键；`frontend.synced.*` 与 `frontend.migrated` 只由后端内部读写。

首次启动还没有标记时，后端已有的合法行优先，只从 localStorage 补缺少的键，然后写入标记和这些值的指纹。标记已存在时，后端把每个合法 localStorage 值与指纹比较：一致时后端为准；不一致时以 localStorage 为准重新导入并更新指纹；localStorage 缺失或损坏时跳过该项，不覆盖后端。写后端、写 localStorage、记指纹是三个有序步骤；只有 localStorage 写成功才记新指纹，避免 localStorage 写失败后旧副本在下次启动反而覆盖新数据。

## GPUI 版必须遵守的约定

1. 不删除 `frontend.*` 行。要清空某个键，就写入形状相同的空值：数组键写 `[]`，允许为空的 `sftpColumnWidths`、`sftpView`、`replayView` 写 `null`，两个 composer 布尔键写 `false`；其余值的形状必须与本卡列出的 TS 类型一致。
2. GPUI 不写迁移标记 `frontend.migrated`，也不写任何 `frontend.synced.*` 指纹。只写标记而不写匹配的指纹，会让指纹与 localStorage 不一致；以后回到 Tauri 时，启动逻辑会把旧 localStorage 当作旧版本的新改动重新导入。
3. 迁移标记存在时，如果后端某一行缺失或无法解析，回到 Tauri 会从 localStorage 重新导入这个键（`4e5bec18` 的行为）。因此 GPUI 要清空数据时必须写空值，不能删行，否则旧 WebView 数据会被重新带回来。

启动读/迁移失败的处理：本次会话完全不使用后端，继续按 0.8.x 的方式读写 localStorage；React 挂载后只显示一次读失败提示，下一启动重新尝试迁移。

写失败的处理：缓存先采用新值，后台按顺序写 `write_frontend_state`；写入失败不撤回界面状态，显示一条可见错误。连续失败只提示第一次，直到之后有一次后端写入成功才重新允许提示。下一次启动或导入后重新读取后端最后一次成功写入的值。

在 0.8.1 里清除 WebView 数据不会清掉后端 `app_meta` 里的数据；下次启动 Tauri 过渡版时，localStorage 没有值的键会以后端为准，并重新镜像回 0.8.x 的键。

9. 备份验证：在旧版导出一份包含“设置”的备份，升级后导入；最近命令、快速连接、连接最近记录、SFTP 列宽和视图应恢复到界面。再导出新备份，用解压工具查看 `payload.json` 的 `frontendState`，应仍然只有原来的 5 个字段：`recentCommands`、`recentQuickConnections`、`recentProfiles`、`sftpColumnWidths`、`sftpView`。
10. 回退验证：在过渡版里再执行一条独特的最近命令并改动 SFTP 视图，退出后用同一测试标识重新安装旧版并启动；由于双写，旧版应看到这些最新改动，而不是第 3 步的旧快照。
11. 回退后再升级：保持旧版运行，再产生一组可辨认的新数据（例如再执行两条独特命令、改变快速连接最近顺序）。退出旧版，重新启动过渡版。启动日志应出现从 localStorage 重新导入这些键的记录，界面应显示旧版里的最新数据，`app_meta` 的对应值和 `frontend.synced.*` 指纹也应更新。
12. 如启用 WebDAV 同步：让一次同步产生恢复备份，解压恢复备份，确认 `frontendState` 的 5 个字段来自当前后端存储；同步文档本身不携带这 5 个字段。
13. 在 0.8.1 里清除该 WebView 的站点数据或 Local Storage，确认旧版界面回到默认，然后重新启动过渡版；之前的用户数据应从后端恢复，localStorage 的旧键也应重新出现。清除 WebView 数据本身不会清掉后端 `app_meta`。

## 偏差

1. 任务卡把“串口发送历史与回显设置”都列为用户数据。实际串口发送历史已经在 `serial_sends` 表里（由现有 `record_serial_send` 写入），localStorage 只保存“哪些连接隐藏回显”的 per-device 设置；本次只迁移了这个设置，历史表未改。
2. 任务卡要求备份格式保持不变。因此新增到后端的 `serialSendEcho`、`commandComposerOpen`、`commandComposerLineByLine`、`replayView` 没有加入 `BackupFrontendState`；备份仍只有原来的 5 个字段。这 4 项在备份/恢复后不会跨设备恢复，报告在“遗留问题”中列出。
3. WebDAV 同步实际不把前端状态作为同步集合传输；`run_sync` 只用它创建同步前的恢复备份。本次把恢复备份的读取改到后端，没有改同步文档格式或同步集合。
4. 为遵守“现有 command 名与参数不改，只新增”，`export_backup` 的 `options.frontendState`、`run_due_automatic_backup` / `run_webdav_backup` / `run_sync` 的 `frontendState` 参数仍保留，但后端不再读取，前端也不再发送。这样旧调用方仍能调用新后端。
5. 过渡版版本号按 0.9.0、删除 localStorage 原值按 0.10.0 记录，这是建议计划，不是任务卡给定的版本号；发布前需要按 P5-03 的更新器安排确认。
6. `custom-themes` 是已有迁移：它在导入数据库后删除 localStorage 原值，与本卡“保留一个版本”的规则不同；本卡没有改它，以免改变既有行为。
7. 旧版的 `restoreFrontendState` 在只选择“主题”时也会恢复备份里的最近记录和 SFTP 视图，而第一轮后端只在选择“设置”时应用这些字段。第 2 轮恢复了旧行为：选择“设置”或“主题”都会应用 `frontendState`，只导入主题时的失败回滚快照也包含这些 `app_meta` 键；其余设置仍只随“设置”导入。

## 遗留问题

1. 前端写入是异步的：缓存先更新，数据库写入在后台串行执行。如果用户写完立刻强制退出，最后一次写入可能来不及落盘；目前没有在退出流程里等待写队列。需要时可另开卡增加“退出前 flush”。
2. 4 个新迁移的用户数据（串口回显、命令编写器两项、日志回放）没有备份字段，无法随备份或同步跨设备恢复。出于“备份格式不变”的硬性要求，本卡没有扩展格式；建议后续单独开卡设计兼容的扩展。
3. `[人工]` 升级/回退验证未执行，因此没有真实设备上的录屏和数据对照。
4. 过渡版必须让用户运行一次，且要留出升级时间；这部分发布与更新器工作属于 P5-03，不在本卡范围。
5. 后端写入成功后若 localStorage 双写失败（例如配额满），后端数据仍然安全，本次不会记新指纹；旧副本会在下次启动时因“指纹一致”而让后端胜出，直到下一次成功双写。失败会写前端日志，不额外弹窗，因为用户数据已经保存到后端。

## 第 2 轮

1. **启动加载失败会永久丢数据（高）**：`8c714d8f` 让 `migrate_frontend_state` 失败时清空内存快照并保持未 hydrate 状态，本次会话按 0.8.x 读写 localStorage，后端收不到任何写入；启动错误只记录一次待提示。原 `starts in defaults when the backend cannot be read` 改为 `keeps the whole session on localStorage when the backend cannot be read`，覆盖读写回退、零后端写入和下次启动重试。`a_stored_value_that_no_longer_parses_is_replaced_by_the_legacy_value` 和 `4e5bec18` 的 `an_unreadable_stored_value_is_reimported_after_the_migration_marker_exists` 覆盖首次迁移及标记已存在两种情况下，后端坏值都不会永久挡住 localStorage 的重新导入。
2. **升级、回退、再升级**：`cfa5e081` 实现双写和指纹。每次后端写入成功后，前端马上写同一个值到 0.8.x 的旧键（布尔 composer 仍写 `"1"`/`"0"`），localStorage 写成功后再调用 `acknowledge_frontend_state_sync` 记录规范化 JSON 指纹；启动时按指纹判断旧版是否改过该键，改过就重新导入，没改过或旧值损坏时后端为准。测试覆盖回退后修改、指纹一致不导入、未回退后端不被覆盖、损坏值不覆盖、双写后 9 个键都能被 0.8.x 读取。报告结论和手工步骤 10、11 已补“回退后再升级”。
3. **写失败反复弹提示（中）**：`e56d315c` 在缓存层记录“本次失败已提示”，同一轮连续失败只通知一次，任何一次后端写入成功后才复位；`reports repeated write failures once until a write succeeds again` 覆盖两次失败、一次成功、再失败。
4. **旧备份夹具说法不实（中）**：`d20d8e17` 把报告改成“按 0.8.1 归档结构手工生成的精简夹具，只含 5 个 `frontendState` 字段”，并写明 manifest、payload 和 SHA-256 的生成方式；新增 `custom_themes_and_recent_records_in_one_backup_both_import`，确认同一备份里的主题和最近记录都导入。
5. **导入行为变化未说明**：核对旧 `restoreFrontendState` 后确认，旧版只导入主题时也恢复最近记录；`5b5b2ca0` 恢复该行为，选择“设置”或“主题”都会应用 `frontendState`，且只选主题时也把相关 `app_meta` 放进失败回滚快照。测试为 `importing_only_themes_restores_frontend_state_and_keeps_rollback`，偏差第 7 条已记录。
6. **导入后 React 状态过期**：`f1972d26` 给缓存增加“导入已重新加载”通知，新增 `useFrontendStateRefresh` 并用在 `useCommandLibraryActions`、`useProfileRecents`、`useQuickConnect`；导入后三处立即从缓存重读，下一次命令保存不会把旧数组写回去。`useFrontendStateRefresh.test.tsx` 覆盖最近命令、连接最近记录和快速连接三类值。

## 第 3 轮

1. **降级会话导入会把会话切到后端并清掉 localStorage（中高）**：`905c3636` 让 `reloadFrontendState` 在未 hydrate 时改为调用迁移模块注册的重试：先把备份结果里的 `frontendState` 按 0.8.x 格式写回 localStorage，再用整份当前 localStorage 调 `migrate_frontend_state`；迁移成功才 hydrate，失败则继续降级到重启。`DataMigrationSettingsTab` 把 `result.frontendState` 传入。测试覆盖只含主题的备份、含最近记录且同时保留备份外键、重试仍失败三种情况。

## 评估

结论（2026-11-12，Claude）：通过（macOS 自动化），共三轮，执行者使用 DeepSeek v4.1 flash，已合进 `dev`（只合并到本地，未推送）。人工项留给 stone，见上文的验证清单。Windows 与 Linux 由 CI 跑。

- 第 1 轮需修改：启动时加载失败后，会话仍然把空的缓存写进后端，下次迁移就会跳过这些键，localStorage 里的最近记录因此永久丢失。另一个问题是升级、回退、再升级这个过程中，旧版里做的改动会丢掉。
- stone 于 2026-11-12 决定：过渡版同时写 localStorage（格式与 0.8.x 相同），并给每个键记下指纹；迁移标记已存在而指纹对不上时，以 localStorage 为准重新导入。
- 第 2 轮完成了这套做法，复核时又发现两处问题：降级会话里导入备份，会切换到后端并清空 localStorage；首次迁移时 localStorage 覆盖了后端已有的值（这些值来自 GPUI，或者来自降级会话中的导入）。
- 第 3 轮全部修正：降级会话导入时先重新迁移，再决定后续怎么读写；首次迁移时后端已有的值优先，localStorage 只补缺失的键；启动时的镜像会补上确认。报告里写明了 GPUI 版必须遵守的约定：不删除 `frontend.*` 行，不写迁移标记，也不写指纹。
- 复核：独立审查按顺序推演了全新安装、升级、回退再升级（有改动和无改动两种）、各个时间点崩溃、配额写满、单实例等情况，确认都没有问题。评估者在沙箱外重跑了 dev 版 AGENTS.md 的全部检查，都通过：Rust 854 项，前端 1316 项。评估者删掉了三轮留下的原始测试日志，只保留 `localStorage-grep.txt`；正文里引用这些日志的地方，以本节的数字为准。
- 发布：这次改动必须随一个正式的 Tauri 版本发出（P5-03 的过渡版），而且要留出足够的升级时间；GPUI 版正式发布之前，用户必须至少运行过一次这个版本。
- 遗留：退出时还在队列里没写完的数据会丢失，最多丢掉最后一次输入，已经记录。导入后，其他视图的 React 状态以前就要重启才能更新，这次只修了三个 hook。
