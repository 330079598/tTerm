## 第一批

### Switch（评估者实现，2026-11-09）

执行者第 2 轮（`9296b0a9..90af176e`）已做好交互、四元素标记和图标脚本，这些保留。但它把剩余的 2039 个超限像素归因于“focus ring 与 disabled thumb 的抗锯齿/透明度合成”，这个结论不对。决策人随后要求评估者自己修，提交 `9a0d4548`、`6863a57d`。逐像素查下来，实际原因有四个：

1. **thumb 右移了 1px。** React 的 thumb 是 `inline-flex items-center` 容器里的 flex 子项，位于 1px 透明边框以内，从 border box 的 x=1 开始，checked 时 `translate-x-4` 右移到 17。GPUI 端用 `absolute().left(2 / 18)` 定位，结果落在 2 与 18。thumb 没有被标记，所以布局比较发现不了。现改为 flex 子项加相对偏移，`Toggle` 默认的居中用 `justify_start()` 覆盖；thumb 的位置在 `SwitchStyle::thumb_offset` 里给出，绘制与记录都取这个值。
2. **ring 的几何不对。** `surface()` 把圆角写死为 6（只适合 Button 与 Input），Switch 又把边框宽度当作 0 传进去，ring 于是围着 padding box 画，外圆角 9。现在 `surface()` 增加 `radius` 参数，ring 的外圆角按 CSS Backgrounds 3 的 spread 规则计算（`spread_radius`）。Switch 传入边框 1、圆角 10，外圆角为 13。
3. **disabled 的不透明度。** CSS 的 `opacity` 是先把整个元素合成为一组，再整体变透明；GPUI 的不透明度却逐个图元生效，disabled 时轨道颜色会透过 thumb，checked 的 thumb 因此偏蓝。轨道和 thumb 都不透明，所以新增 `css_group_color`：先把两者分别按 0.5 合成到背后的底色上，再以不透明度 1 绘制，结果与 CSS 完全一致。底色默认取主题背景，放在 card 一类非底色容器里时由 `SwitchState::backdrop` 传入。
4. **缺少 `shadow-xs`。** Tailwind v4 的定义是 `0 1px 2px 0 rgb(0 0 0 / 0.05)`，GPUI 端没有画，switch 下沿缺一道浅灰。新增 `shadow_xs()`：GPUI 的 `blur_radius` 是高斯 σ，CSS 的模糊半径是 2σ，所以 CSS 的 2px 对应 GPUI 的 1px。

工具方面（`6863a57d`）：`layout.mjs` 把被标记元素内部带 `data-slot` 的部件（这里是 `switch-thumb`）记为 `<id>.<slot>`。GPUI 端的 `parity_child_with_parts` 按 `thumb_offset` 和 `thumb_size` 记录同一个部件。这样 thumb 的位置也会被比较，它的圆形边缘也按元素边缘带处理。这是把已有的元素边缘规则用到更多元素上，没有新增遮罩种类，也没有改门槛。`layout.test.mjs` 修好了模拟元素缺 `querySelectorAll` 的问题，并新增部件记录的测试，用 `node --test scripts/parity/layout.test.mjs` 运行，两项都通过。

## 结论

2026-11-09 返工第 3 轮结论：**完成待评估（本轮 Button/Input 范围）**。按决策人 2026-11-09 决定，比较工具把 focus ring 外轮廓两侧各 1 个物理像素纳入边缘遮罩，ring 中间填充仍比较。macOS 沙箱外重新生成参照，四屏深浅主题 **8/8 全部通过**，屏幕颜色超限均为 0；spread=2 的反向探测失败并指名 focus 按钮，恢复 spread=3 后通过。空心 ring 绘制保留，未加 WebKit 不透明背景特判，颜色与 SSIM 门槛数值不变，未登记例外。Windows 仍为未验证（需 Windows），其余六个组件仍按用户要求留待下一批。完整 Rust 测试重现的终端字形失败为 GPUI 分支既有失败，评估者已确认，另开卡。

第 2 轮历史结论：**需要确认**。本轮只将 focus ring 改为外扩 3px、外圆角 9px 的空心边框，并增加透明/半透明按钮的绘制测试。重新生成参照并在沙箱外比较后，仍为 6/8 组合通过；第 1 组接缝仍有差异，不能把剩余问题全部归为第 2 组抗锯齿。严格空心边框要求与本机 WebKit 对不透明背景的实际裁剪行为存在差异，详见“focus ring 第 2 轮”。终端测试为 **GPUI 分支既有失败，评估者已确认，另开卡**，本轮不处理。

以下为第 1 轮历史结论：**需修改，阻塞**。本轮已修复 macOS headless 初始化、CSS 主题选择、disabled 变体颜色、透明背景与快照、outline 边框/hover，并增加真实渲染的主题隔离测试。macOS 沙箱外已跑通深浅主题的四屏捕获与比较：8 个组合中 6 个达到第 5.2 节门槛，`ui.button.variants` 两种主题仍因 focus ring 外圆角的少量颜色像素超限而失败；没有调整门槛、掩码或登记新例外。完整 Rust 测试还存在本卡范围外的 macOS 主线程测试失败，因此不宣称完成。

Button 使用 tterm-ui 令牌自绘；Input 仅保留 gpui-component 的编辑状态机，外观由 tterm-ui 绘制。组件接收包含 id 与颜色的局部 `Theme`，不覆盖 gpui-component 全局主题。所有修正来自生产 CSS 的令牌、变体规则和 8 位预乘 alpha 合成，不按 macOS 单个颜色读数设置常量；同一实现也供 Windows 通道使用，Windows 实测仍需补做。

## 首次尝试与改走自绘

首次尝试封装 gpui-component：默认主题使 outline/secondary 变成白底黑字，Button 仅一行 6 个控件，未覆盖 React 的 8 种尺寸、图标按钮和状态；首次深色结果 Button full SSIM `0.763262`、masked SSIM `0.843661`，Input full SSIM `0.813599`、masked SSIM `0.857887`。放弃理由是默认主题与生产 CSS 差异过大，逐项覆盖代价高且会影响其他组件。

自绘实现直接使用 tterm-ui 的 HSL 令牌绘制尺寸、内边距、圆角、边框、颜色、字重和 focus/hover/disabled 状态；Input 的文字编辑仍由 gpui-component InputState 提供。Windows 真实窗口和 macOS headless 捕获现在都调用 `initialize_gpui`，其中统一执行 `gpui_kit::init(cx)`；初始化全局状态与覆盖全局主题是不同操作。

## 主题隔离

`rendering_local_themes_does_not_mutate_global_theme` 在 `TestAppContext` 中先初始化 gpui-component，序列化读取全局 `Theme`；同一窗口渲染深色与浅色两个 Input 和一个使用局部颜色的 Button，调用 `window.render_frame`，再读取全局 `Theme`，断言序列化内容完全相同。该测试验证局部颜色渲染不会改变供其他组件使用的全局主题。

同一个窗口上下文里分别构造深浅主题的实际 Input 元素，断言两者文字样式不同；构造第二个后，第一个元素的完整 style 保持相等。Button 的 `style_reads_the_selected_theme_without_shared_state` 遍历全部六个主题后断言默认主题结果不变；`dark_variant_matches_css_theme_selector_rule` 覆盖六个内置主题和一个亮背景自定义主题。组件没有写全局主题的路径。以上测试均通过，见 [Rust 范围测试输出](assets/P0-24/checks/scoped-workspace-test.txt)（tterm-ui 15 项）。这些证据覆盖全局主题未被改写与同窗局部主题互不干扰，不代表已验收本轮范围外的六个组件。

### 偏差：严格空心要求与参照实际行为

直接透明黑填充边框会产生着色器插值暗边，已用相同 RGB、alpha 0 的填充修正；这是绘制原因明确且已修正的部分。但重新生成的真实参照仍不符合“裁掉整个 border box 内部后沿同一圆弧叠加”的预期：浅色 `(72,736)` 普通按钮为 `[136,188,231]`，focus 为 `[67,149,217]`，接近普通按钮覆盖后叠加完整 ring 的结果；严格空心 GPUI 为 `[98,167,223]`。这意味着参照在此并非严格互补覆盖。

辅助源码证据：[WebKit BackgroundPainter.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/rendering/BackgroundPainter.cpp) 的 `paintBoxShadow`：`shouldInflateBorderRect` 在背景不透明且 CTM 存在缩放时返回 true；后续注释明确说明为避免圆角 subpixel gaps，将裁剪轮廓向内缩进 1 个 layout unit（`adjustedBorderShape.inflate(-1_lu)`）。DPR 2 输出符合这种不透明背景优化的表现。该链接是 WebKit main 的机制证据，不宣称与本机 revision 2191 的源码逐字一致；最终判断仍以本次真实截图为准。GPUI `gpui-pre-apple-0.3.11/src/shaders.metal` 的 `quad_fragment` 是透明黑插值问题的源码依据；没有复制外部源码进入生产实现。

本轮明确要求 3px 空心边框且不改变上一轮已复核的背景绘制。继续用不透明背景特判扩大 ring 内沿会偏离该要求，改变按钮背景的圆角光栅也会扩展到已复核的非 focus 绘制。因此按“任务卡与代码/参照不符时停下”的规则写明偏差，请评估者确认如何处理；没有自行加逐点常量、扩大遮罩、放宽门槛或登记例外。**本次不是“第 1 组已清零，仅剩第 2 组”的交付。**
