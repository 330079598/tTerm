# P0-24 UI 原语还原验证

## 结论

2026-11-09 返工第 1 轮结论：**需修改，阻塞**。本轮已修复 macOS headless 初始化、CSS 主题选择、disabled 变体颜色、透明背景与快照、outline 边框/hover，并增加真实渲染的主题隔离测试。macOS 沙箱外已跑通深浅主题的四屏捕获与比较：8 个组合中 6 个达到第 5.2 节门槛，`ui.button.variants` 两种主题仍因 focus ring 外圆角的少量颜色像素超限而失败；没有调整门槛、掩码或登记新例外。完整 Rust 测试还存在本卡范围外的 macOS 主线程测试失败，因此不宣称完成。

Button 使用 tterm-ui 令牌自绘；Input 仅保留 gpui-component 的编辑状态机，外观由 tterm-ui 绘制。组件接收包含 id 与颜色的局部 `Theme`，不覆盖 gpui-component 全局主题。所有修正来自生产 CSS 的令牌、变体规则和 8 位预乘 alpha 合成，不按 macOS 单个颜色读数设置常量；同一实现也供 Windows 通道使用，Windows 实测仍需补做。

## 首次尝试与改走自绘

首次尝试封装 gpui-component：默认主题使 outline/secondary 变成白底黑字，Button 仅一行 6 个控件，未覆盖 React 的 8 种尺寸、图标按钮和状态；首次深色结果 Button full SSIM `0.763262`、masked SSIM `0.843661`，Input full SSIM `0.813599`、masked SSIM `0.857887`。放弃理由是默认主题与生产 CSS 差异过大，逐项覆盖代价高且会影响其他组件。

自绘实现直接使用 tterm-ui 的 HSL 令牌绘制尺寸、内边距、圆角、边框、颜色、字重和 focus/hover/disabled 状态；Input 的文字编辑仍由 gpui-component InputState 提供。Windows 真实窗口和 macOS headless 捕获现在都调用 `initialize_gpui`，其中统一执行 `gpui_kit::init(cx)`；初始化全局状态与覆盖全局主题是不同操作。

## 主题隔离

`rendering_local_themes_does_not_mutate_global_theme` 在 `TestAppContext` 中先初始化 gpui-component，序列化读取全局 `Theme`；同一窗口渲染深色与浅色两个 Input 和一个使用局部颜色的 Button，调用 `window.render_frame`，再读取全局 `Theme`，断言序列化内容完全相同。该测试验证局部颜色渲染不会改变供其他组件使用的全局主题。

同一个窗口上下文里分别构造深浅主题的实际 Input 元素，断言两者文字样式不同；构造第二个后，第一个元素的完整 style 保持相等。Button 的 `style_reads_the_selected_theme_without_shared_state` 遍历全部六个主题后断言默认主题结果不变；`dark_variant_matches_css_theme_selector_rule` 覆盖六个内置主题和一个亮背景自定义主题。组件没有写全局主题的路径。以上测试均通过，见 [Rust 范围测试输出](assets/P0-24/checks/scoped-workspace-test.txt)（tterm-ui 15 项）。这些证据覆盖全局主题未被改写与同窗局部主题互不干扰，不代表已验收本轮范围外的六个组件。
