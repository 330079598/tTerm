`scripts/migration/core-move-graph.py` 补两条边，回应 b2 报告“遗留问题 5”：

- **`mod` 父子边。** 可移动文件里的 `mod name;` 声明把它绑到被声明的子文件上：两者必须同批移动，否则父文件会留下没有文件的声明。只对两端都“可移动”的声明加边——声明一个留在 Tauri 的 command 模块（例如 `commands`）仍然合法，父文件移走后删掉那一行即可。

## 偏差

1. **128 个可移动文件里有 32 个是“桩”，没有内容可移。** 工具按“非测试、不碰 Tauri”判定可移动，但 `config/mod.rs`、`ssh/mod.rs`、`backup/mod.rs` 这类文件在 b1/b2 与本轮搬走内容后只剩命令模块声明。把它们整体移走会让 Tauri 失去声明 `#[tauri::command]` 文件的地方；b2 报告说的“删掉桩”需要同时把命令文件改名到 Tauri 根（例如 `profiles_commands.rs`）并改 `generate_handler!` 的路径，那不是移动提交。因此保留 34 个 4–8 行的桩，名单在 [`batches-end.txt`](P1-09b3-evidence/batches-end.txt)（`sftp` 6 个、`serial` 3 个、`ssh` 2 个、`background` 2 个，其余一域一个）。
2. **7 个逻辑文件在 core 上移一层**（见上表）。不这样做的话，core 必须新建与 Tauri 同名的 `commands` 模块文件来声明它们，评审时容易误判为命令文件被移动。
3. **16 个 `mod.rs` 是合并而非整文件重命名。** 处理方式与 b2 相同：内容移进 core 的同名模块，Tauri 留桩；`git diff -M` 因此只显示删除/新增，需要并排比较两个文件。
4. **`use` 语句被展开重排。** 原因与 b2 相同：一个 `use crate::{…}` 里可能同时有 core 与 Tauri 的项。语义不变，`cargo fmt` 之后合法。
5. **新增两个 SFTP 桩文件**（`delete/mod.rs`、`upload/mod.rs`）。`delete.rs`、`upload.rs` 移走后，命令模块 `delete/commands`、`upload/commands` 需要父模块；用 4 行的 `mod.rs` 保持模块路径不变，`generate_handler!` 的路径因此一个字都没改。
6. **批次顺序与派工时不同。** 补了 `mod` 边之后 `config` 排到第一、`db` 排到最后；实际执行顺序是“profiles → terminal → serial → sftp → config → tunnel → monitor → agent_integration → core → services → background/notification/tunnel → profiles → services → 入口适配 → backup/sync → db”。任务要求的各块（services、sftp、agent 集成、profiles、serial、core、backup/sync、db legacy import、收尾）都在这条序列里，只是前后顺序按依赖关系调整。
7. **依赖增减。** core 新增 `regex`、`zip`（都是移动过来的代码原本就在用的）；Tauri 删掉 38 个依赖。`Cargo.lock` 因此少掉一批边，但没有新包或新版本，符合计划 4.3。
8. **计划 4.3 的“README 或 p1-core.md 的现状一节”未改。** 本轮要求不改 P1-09 相关文档，Tauri 包剩余内容写在本报告里；建议评估者在 U-02 更新任务卡时把这一段搬过去。
9. **`window_state` 留在 Tauri。** 计划的 2.1 节第 4 条把它列为“只有 Tauri 才有的能力”（窗口几何），工具也只把它算作适配文件；`window_state/tests.rs` 与 `prompt_contract_tests.rs` 同理。
