## 偏差

1. **第 2 批不做。** `db/mod.rs` 与 `db/legacy_import.rs` 互相依赖，后者是工具的第 55 批。细节与三种可选做法见附录 C 第 1 节。工具把 `db/mod.rs` 放进第 2 批，是它只看 `use` 和带 `crate::`/`super::` 前缀的路径造成的盲区：调用点是表达式位置的裸路径 `legacy_import::…`。
2. **第 1 批文件数与计划第 4.0 节的“约 115”对得上，但与逐项相加的 113 不同。** 工具这次输出第 1–31 批共 113 个条目（不含随文件一起移的测试文件）；第 1 批 8 个条目，实际移动 9 个文件（`config/keyword_highlight/tests.rs` 是 `keyword_highlight.rs` 用 `#[cfg(test)] mod tests;` 声明的测试）。

4. **`sftp` 的合并需要提前确认。** 计划第 2.1 节说 Tauri 的 `sftp` 并进 core 现有的 `sftp` 模块、两边 `mod.rs` 合成一个。第 8 批的 `sftp/mod.rs` 里有内联 `pub mod internal { … }` 块，而 `internal` 下的多数文件在第 32、39 批；届时 core 的 `sftp/mod.rs`（已有 `conflict`/`entry`/`search`）与 Tauri 的 `sftp/mod.rs` 要各留一半声明。第 8 批到之前需要评估者确认按“部分移动”处理，即 core 的 `sftp/mod.rs` 增加 `store` 与内联 `internal` 中已移的子模块，Tauri 保留其余。

## 附录 C：批次阻塞分析

### 1. 第 2 批（`db`）——工具没看到的依赖

**文件**：`src-tauri/src/db/mod.rs`（工具第 2 批）。
**依赖项**：`src-tauri/src/db/legacy_import.rs`（`db::legacy_import` 模块，工具第 55 批）。
**谁在用**（`db/mod.rs` 的非测试代码，4 处，都是裸路径）：

```
src-tauri/src/db/mod.rs:102  .and_then(legacy_import::legacy_json_imported)
src-tauri/src/db/mod.rs:109  legacy_import::import_settings_files(get()?, &ensure_config_dir()?)
src-tauri/src/db/mod.rs:115  read(legacy_import::imported_at).ok().flatten()
src-tauri/src/db/mod.rs:122  .and_then(|directory| legacy_import::import_legacy_json_files(database, &directory));
```

反向也断不开：`db/legacy_import.rs` 用 `use super::{Database, sql_error}` 取 `Database`，用 `super::meta::get` 取元数据，也就是又指回 `db/mod.rs`；两者必须同时移动。而 `db/legacy_import.rs` 自己引用 `crate::profiles`、`crate::sftp`、`crate::ssh`、`crate::tunnel`、`crate::app_state`、`crate::session`、`crate::config::window_background`、`crate::backup`、`crate::sync`，所以计划第 1 节把它排在最后（第 55 批）。

工具看不到的原因：工具只跟 `use` 与带 `crate::`/`super::` 前缀的路径，表达式里的裸 `legacy_import::…` 不算边。

**可选做法**（需要评估者决定）：

1. 把 `db` 三件套推迟到 `db/legacy_import.rs` 之后（第 55 批之后），第 2 批空出来；
2. 把 `db/legacy_import.rs` 与它的依赖整体提前（等于把第 54、55 批提到最前，会一次带上 50 多个文件）；
3. 把 `db/mod.rs` 里那 4 个 legacy 转发函数搬进 `db/legacy_import.rs`（或 `db/legacy_import/mod.rs`），作为一个独立的 `:recycle:` 提交，之后 `db/mod.rs` 就能按原批次单独移动。这条改动最小，但属于“改结构”，不在“只做移动”的提交里，需要明确同意。

### 5. 偏差

1. **`db/mod.rs` 等 13 个 `mod.rs` 留在原地。** 它们是本轮移走的领域的模块根，另一半（command 文件、`legacy_import`、`sftp` 的连接层等）还在 Tauri 包里，要等第 21 批的环。任务卡第 2 步的做法是：core 新建只含已移子模块的 `mod.rs`，Tauri 保留其余声明，两边在 b2 合并成一个文件。
2. **`terminal/io_batcher/pty_fixture.rs` 在 core 里暂时由 `terminal/io_batcher/mod.rs` 声明。** 它的父模块 `io_batcher.rs` 还在 Tauri 包，所以 core 侧先建了一个只声明它的目录模块；`io_batcher.rs` 在 b2 移过来时，把这条声明并进 `io_batcher.rs`、删掉 `io_batcher/mod.rs` 即可。同类的还有 `sftp/internal/api/mod.rs` 与 `sftp/internal/api/external/mod.rs`（父文件 `api.rs`、`external/mod.rs` 还在 Tauri 包）。
3. **`sftp` 按部分移动处理**（任务卡同意）：core 的 `sftp/mod.rs` 加上 `store` 与 `internal`，`internal/mod.rs` 只声明 `api`、`paths`、`transfer`；原来的内联 `pub mod internal { … }` 按任务卡建议先单独移成 `sftp/internal/mod.rs`（`ee6a388d`，纯移动）。
4. **签名基线删掉一条 `run_blocking`。** `scripts/migration/command-signatures.mjs` 用 `#\[tauri::command` 正则找命令，不跳过注释；`core/blocking.rs` 的文档注释里写着 “A synchronous `#[tauri::command]` runs on the main thread…”，于是扫描器把紧随其后的 `pub async fn run_blocking` 当成命令，基线里因此多出一条从来不是命令的条目。本轮 `core/blocking.rs` 移进 `tterm-core`，扫描器只走 `src-tauri/src`，这条就必须跟着消失；重新生成后是 210 个命令、210 个 handler，只有那一条被删掉（[`command-signatures-diff.txt`](P1-09b1-evidence/command-signatures-diff.txt)）。真正的 IPC 契约没有变。工具的这个小毛病留给评估者决定要不要单独修（见遗留问题）。
5. **`TransferOutcome::transferred` 的 `expect(dead_code)` 删掉了。** 它在 core 里变成导出字段以后，clippy 报 `unfulfilled_lint_expectations`；按 AGENTS.md 的规则删掉，而不是改成 `allow`。
6. **`SessionSink`/`TerminalOutput` 一类的测试辅助**：`io_batcher` 新增的 `recording_output` 标 `#[cfg(test)]`，`Database::open_in_memory`、`ZmodemEngine::is_done`、`WebDavClient::delete_directory` 改为 `#[cfg(any(test, feature = "test-support"))]`，因为 Tauri 包的测试要在依赖里用到它们（计划 2.3 节的做法）。
7. **`rustfmt` 折行。** 路径变长后有几十行被 rustfmt 拆成多行，附录 E 里归为 “fmt”。

### 6. 遗留问题

1. **签名扫描器会把注释里的 `#[tauri::command]` 当成属性。** 建议单独一张小卡：`parseCommands` 先去掉 `//`、`///`、`//!` 与块注释再匹配，基线随之重新生成（会少掉那条 `run_blocking`，与本次结果一致）。
2. **b2 的 114 文件环**：`ssh` 35、`terminal` 14、`profiles` 11、`sftp` 8、`proxy` 8、`serial` 7、`session_log` 8、`core` 6、`monitor` 6、`config` 5、`zmodem` 4，加上 `prompt_scope.rs` 与 `system_integration`。移动时要注意本轮留下的 `mod.rs` 与之合并，以及 `sftp/internal/api.rs`、`external/mod.rs` 两个父文件与 core 侧目录模块的合并。
3. **`terminal/io_batcher/` 的目录模块**（第 2 条）合并后要删掉 `crates/tterm-core/src/terminal/io_batcher/mod.rs`，否则与 `io_batcher.rs` 冲突。
4. **Windows 与 Linux 未在本机编译。** 本轮移动了 `terminal/console_reset.rs`（`#[cfg(target_os = "windows")]`）与 `terminal/shell_integration.rs` 的资源，`with_console`、`write_sequence` 按调用方放宽到 `pub`；Windows 目标上有 `rusqlite` 的 `bundled` 需要 MSVC 工具链，本机跑不了 `cargo check --target x86_64-pc-windows-msvc`，由 CI 覆盖。
