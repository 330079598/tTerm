### 线程、通道与锁

```text
PTY 读端 ──读取线程──> 有界字节队列（8 个读块，每块最多 8 KiB；满时读取线程阻塞）
                              │      ↑ 退出监视线程：程序自行结束时排入 [Process exited]
                              ▼
                         解析线程 ── 每批：取出已排队的字节（最多约 64 KiB，不等凑满）
                              │       → Terminal::write（持有模型的 FairMutex，批间释放）
                              │       → drain_intents → 应答排入有序写入通道
                              │       → 唤醒通道（容量 1，满了就不再发）
                              ▼
GPUI 界面线程：收到唤醒 → TerminalView::notify_output → 下一帧取一次快照（持锁 O(可见行)）
               有新标题时让根视图重绘以设置窗口标题
用户输入 ──> 有序写入通道（Bytes / Close）──写入线程──> PTY 写端
```

| 锁或共享状态                           | 持有者                                                    | 持有多久                                   |
| -------------------------------------- | --------------------------------------------------------- | ------------------------------------------ |
| 模型的 `FairMutex`（`tterm-terminal`） | 解析线程；界面线程取快照                                  | 一批字节的解析；拷贝可见行                 |
| `size: Mutex<WindowSize>`              | resize 回调写；解析线程读                                 | 赋值或拷贝一个小结构                       |
| `title: Mutex<Option<String>>`         | 解析线程写；根视图读并取走                                | 赋值或取走一个字符串                       |
| `master: Mutex<Option<MasterPty>>`     | resize 回调；关闭时取走                                   | 一次 resize 调用                           |
| `child: Mutex<Child>`                  | 退出监视（每 50 ms 一次 `try_wait`）；关闭时 kill 与 wait | `try_wait` 与 kill 不阻塞；wait 在后台线程 |

关闭顺序（`Session::shutdown`，在根视图的 `Drop` 中调用）：标记停止输入 → kill 子进程 → 取出并 drop master（Windows 上这一步关闭 ConPTY，读取线程随后读到结束）→ 向写入通道发 `Close` → 在后台线程 wait 子进程并 join 四个线程。界面线程上只做前四步，都不阻塞。

查询应答：设备属性、光标位置等由模型直接给出字节（`WriteToPty`）；颜色查询用默认调色板回答；文本区尺寸查询用最近一次 resize 记下的尺寸回答，不在解析线程上取快照（取快照会取走损坏行，界面就会漏画）。所有应答在解析线程上按意图顺序生成，与用户输入走同一条写入通道。


### 持续输出与内存

命令（Windows PowerShell 不停地输出 100 个字符左右的行）：

```powershell
tterm-gpui --exec "$env:SystemRoot\System32\WindowsPowerShell\v1.0\powershell.exe" -NoProfile -Command "`$s = 'x' * 90; `$i = 0; while (`$true) { `$i++; [Console]::Out.WriteLine('line ' + `$i + ' ' + `$s) }"
```

每 10 秒用 `Get-Process` 采样一次原型（debug 构建）：

| 秒  | 工作集 MB | 私有内存 MB | 原型累计 CPU 秒 | 输出程序累计 CPU 秒 |
| --- | --------- | ----------- | --------------- | ------------------- |
| 10  | 133.5     | 148.5       | 23.7            | 6.0                 |
| 30  | 133.4     | 148.6       | 60.6            | 14.6                |
| 60  | 133.8     | 149.5       | 115.1           | 27.8                |
| 90  | 133.8     | 149.6       | 169.4           | 41.2                |
| 120 | 133.8     | 149.6       | 223.1           | 54.0                |
| 150 | 133.7     | 149.0       | 276.3           | 67.2                |
| 180 | 133.5     | 148.7       | 329.1           | 79.7                |

（完整 18 个采样点都在 130.7–133.8 MB 之间。）两个 CPU 时间持续增长，说明输出一直在产生并被处理；内存不增长。原型 CPU 偏高是 debug 构建，性能对比留给 P0-21。

为什么有上限：字节队列最多 8 个读块（测试 `the_byte_queue_holds_a_fixed_number_of_reads`）；模型的回滚区为 10,000 行（测试 `the_pipeline_applies_every_byte_and_the_history_stays_bounded` 送入 20 万行后断言历史行数等于上限）；意图每批清空、标题只保留最后一个（测试 `intents_are_drained_and_only_the_last_title_is_kept`）；唤醒通道容量为 1。

### 关闭窗口

用 `Process.CloseMainWindow()` 关闭窗口，然后检查关闭前的子进程是否还在：

| 场景                                       | 关闭前的子进程                                  | 关闭 3–5 秒后      |
| ------------------------------------------ | ----------------------------------------------- | ------------------ |
| 默认 shell                                 | conhost、OpenConsole、pwsh                      | 原型退出，全部不在 |
| 持续输出中                                 | conhost、OpenConsole、powershell                | 原型退出，全部不在 |
| shell 中的子程序（`cmd /c ping -n 120 …`） | conhost、OpenConsole、cmd、PING（cmd 的子进程） | 原型退出，全部不在 |

自动化：`closing_the_session_ends_the_program_without_blocking` 在真实 PTY 中运行一个 60 秒的程序，断言 `shutdown` 在 2 秒内返回、后台的等待在 20 秒内完成；`a_program_that_ends_by_itself_leaves_the_exit_notice_and_stops_input` 断言程序自行结束后终端显示 `[Process exited]` 并停止接受输入。这两个测试在 CI 的三个平台上都会运行。

## 偏差

1. **评估者参与了实现。** 第一轮评估后，应决策人要求由评估者完成修改。后半部分的代码没有经过独立评估，建议合并前由决策人完成下文的人工验证；如需独立审查，可以让另一个 agent 只读审查 `d9acf849..HEAD`。
2. **增加了 library target。** 截图功能需要 GPUI 的 `test-support` 特性，它只在 dev-dependencies 中开启；clippy `--all-targets` 与 `cargo test` 会合并特性，所以检查都通过，单独构建二进制却失败。拆出库后，二进制只有原型，example 保留 P0-10 的工具。这推翻了计划执行中“不拆 library target”的决定。
3. **删除了 P0-08 的 Hello 窗口及其测试**（`17082d80`）。原型取代了它的入口，P0-23 不依赖它。
4. **增加了 `--exec`。** 任务卡只要求系统 `ssh`。`--exec` 让 P0 的卡不用在窗口里打字就能跑固定负载（本卡的内存采样、vim 与 tmux 截图；以后 P0-15、P0-21 也需要）。`--ssh` 现在是 `--exec ssh` 的简写；Codex 加的 `TTERM_GPUI_SSH_*` 环境变量删除了。
5. **颜色查询用默认调色板回答**，不是计划中“会话持有一份与视图同步的副本”。原型从不更换调色板，结果相同。
6. **`CursorBlinkingChanged` 被丢弃**：视图从每个快照读取光标闪烁状态。
7. **空标题显示默认标题。** Alacritty 把空的 OSC 0 报告为一个空标题，不是重置；没有标题的窗口在任务栏里无法分辨。
8. **修正了 `pnpm-workspace.yaml`**（`ff846e8c`）。P0-10 的提交 `03c27276` 误提交了 pnpm 自动写入的占位文字 `esbuild: set this to true or false`，新 worktree 中 `pnpm install` 因此失败，所有 pnpm 检查都无法运行。改为 `esbuild: false`：esbuild 的二进制由可选的平台包提供，不需要它的安装脚本，前端测试全部通过。这个修正与本卡无关，单独一个提交，合并后其他卡的 worktree 也受益。
9. **`[Process exited]` 的位置。** 退出通知排在已经读到的输出之后；Windows 上程序结束后管道里可能还有未读的少量输出，它们会出现在通知之后。

## 遗留问题

- **人工验证（Windows，已完成）：** stone 于 2026-11-07 完成，结果没有问题，未附截图。内容为：与 Tauri 版对照。在两边分别运行同一条命令（例如 vim 打开同一个文件，或输出 256 色与真彩色测试），各截一张图，核对颜色与重排；以及在原型窗口里实际打字、输入 `exit` 看到 `[Process exited]`、调整窗口大小。
- **macOS、Linux 未验证。** CI 会在两个平台上编译并运行包括真实 PTY 在内的测试，但窗口、vim、tmux 需要在真机上运行 `cargo run -p tterm-gpui`。Linux 可以与 P0-16 一起做。
- **macOS 的登录 shell 环境。** Tauri 版在 macOS 上会补全登录 shell 的 PATH（`apply_macos_login_shell_env`），原型没有照做；从 Finder 启动原型时 PATH 可能不全。P1-12 改用 core 的会话服务时一并解决。
- **shell 集成**（提示符标记、工作目录报告）没有接入，属于 P2。
- **剪贴板读取（OSC 52 查询）不应答，剪贴板写入与响铃被忽略**，留给 P2。
- **Zed 阅读声明：** Codex 与评估者都没有阅读 Zed 的终端源码，没有可列出的 Zed 提交或文件；实现依据为 `terminal-design.md`、现有 tTerm 代码与 Tauri 版、GPUI 与 portable-pty 的公开接口，没有复制 Zed 的代码、注释、测试或私有标识符。
