### ConPTY 加载方案

portable-pty 0.9.0（`src/win/psuedocon.rs` 的 `load_conpty`）在第一次创建 PTY 时用 `LoadLibrary("conpty.dll")` 按文件名加载，结果缓存在 `lazy_static` 中；找不到时静默退回 `kernel32.dll` 中的系统 ConPTY。Windows 按文件名加载时，如果进程里已经有同名模块，就直接返回那个模块；`conpty.dll` 从自己所在的目录启动 `OpenConsole.exe`。因此不复制任何文件，做法如下：

1. 在第一次创建 PTY 之前，用完整路径加载 `src-tauri/resources/conpty/conpty.dll`（路径由 `CARGO_MANIFEST_DIR` 定位，只用于源码树中的原型），加载后不释放。不在运行时向构建目录写文件，不提交 DLL，不改 Tauri 版的行为。
2. 该目录由既有 `src-tauri/build.rs` 调用 `scripts/prepare-conpty.ps1` 准备，并被 `.gitignore` 忽略；新 worktree 里没有，单独运行 `cargo run -p tterm-gpui` 也不会生成。缺少 `conpty.dll` 或 `OpenConsole.exe` 时，打印一条清楚的提示：说明退回了系统 ConPTY，以及怎样准备（运行 `scripts/prepare-conpty.ps1`，或先构建一次 Tauri 包），然后继续用系统 ConPTY 运行。
3. 创建 PTY 之后，按 `src-tauri/src/terminal/pty.rs` 的 `log_conpty_source` 的判定方式（`GetModuleHandleW`）输出实际来源。
4. 非 Windows 跳过以上步骤。

验证：贴出来源日志，以及 `Get-Process OpenConsole | Select-Object Id, Path` 的输出，证明运行的是 `src-tauri\resources\conpty\OpenConsole.exe`；再把该目录临时改名运行一次，贴出退回系统 ConPTY 的提示。路径解析的纯逻辑（两个文件都在、缺一个）有单元测试。该逻辑在 P1-12 由 core 会话服务替换，代码注释标明“待 P1-12 替换”。

### 线程、通道与锁

计划采用以下关系，最终报告会配一张同等内容的 ASCII 图并记录每把锁的持有者和最长持有范围：

```text
PTY reader thread
  └─ bounded byte queue (Vec<u8>, blocking send when full)
       └─ parser thread (one per session, fixed byte/time budget)
            └─ Terminal model fair lock, held only while applying one batch
                 └─ merged wake channel (capacity 1) ──> GPUI task
                                                        └─ snapshot lock, O(visible rows)
                                                             └─ layout/paint without lock
PTY writer thread <── ordered write channel <── user input (GPUI thread)
                                           <── query replies (parser thread)
```

- 读取线程只做阻塞读取和向有界字节队列入队，不做 UTF-8 边界拼接：本地 PTY 已是 UTF-8，跨批次的半个字符由解析器自己保留状态处理，拼接反而可能改动二进制数据。队列满时等待，绝不丢数据。
- 解析线程每批最多处理 16–64 KiB 或约 2–4 ms 的字节。这是上限，不是凑批：队列里有多少就立即处理多少，不为凑满一批而等待，否则按键回显会变慢。按批取得模型的公平锁，更新终端后释放；解析完成即形成消费确认，不等待绘制。
- 解析线程每批最多发送一次唤醒，容量为 1 的唤醒通道合并重复通知；GPUI 每帧最多取一次快照。
- 快照锁只覆盖应用少量视图命令、消费损坏行和复制可见行与元数据；字体测量、排版、颜色解析和绘制都在锁外。
- 写入由独立的写入线程完成，界面线程只把字节送进有序写入通道，从不阻塞在 PTY 写端上（大段粘贴而程序不读输入时界面不能卡住）。用户输入不排在输出队列之后。

### 意图与查询应答

现有演示从不调用 `Terminal::drain_intents()`，意图会一直累积：vim、tmux 等发出的设备属性、光标位置、颜色查询得不到应答，持续输出时意图列表还会无限增长。本卡补上消费：

- 解析线程每批解析之后、释放锁之前或之后立即调用 `drain_intents()`，按顺序处理，不跨批累积。
- 需要写回的应答全部在解析线程上按意图顺序生成，送进与用户输入相同的有序写入通道（`terminal-design.md` 3.3 节：两个应答不能由不同路径写回而颠倒顺序）：
  - `WriteToPty`：原样写回。
  - `ColorRequest`：用会话持有的一份调色板颜色副本解析颜色，调用 `ColorFormatter::format`；视图更换调色板时同步更新这份副本。
  - `WindowSizeRequest`：用快照的 `window_size()` 调用 `WindowSizeFormatter::format`。
- `Title`、`TitleReset`：只保留最新的标题，随唤醒交给界面线程设为窗口标题，不排队。
- `ClipboardRead`：P0 中不应答，在报告中写明，留给 P2。`ClipboardStore`、`Bell`：P0 中忽略并在报告中写明。
- `CursorBlinkingChanged`：视图已从快照读取闪烁状态时丢弃；否则随唤醒通知视图。实现时核对后在报告中写明是哪一种。

### 关闭与退出

Windows 上 shell 退出后，ConPTY 的读取端不会结束，要等 `ClosePseudoConsole`，也就是 drop `MasterPty` 之后，读取线程才会读到结束。因此：

- **关闭窗口：** 结束 shell → drop master（关闭 ConPTY）→ 关闭写入通道 → 等待 shell 退出 → join 读取线程、解析线程与写入线程。等待与 join 不在 GPUI 界面线程上阻塞，放到后台线程完成。验证 shell 及其子进程（例如 shell 中启动的 `vim`）都退出。
- **shell 自己退出（输入 `exit`）：** 照 Tauri 版（`src/components/TerminalTab/ptySession.ts` 收到 `pty-exit` 后的本地分支）的行为：在终端中输出黄色的 `[Process exited]`，窗口保持打开，之后的输入不再写入；关闭窗口时按上一条清理。这一行为有自动化测试。

## 偏差

1. `P0-14` 任务卡描述的是“原型直接用 portable-pty”，而现状已有一套位于 `examples/terminal_view.rs` 的真实 PTY 输入/resize 实现；本计划以其为基础，避免并行实现，并把移动单独成提交。
2. 任务卡要求 `cargo run -p tterm-gpui` 作为日常原型，但当前包的默认入口仍是 P0-08 程序；计划将入口接到终端 demo，行为变更列入独立提交。
3. P1-12 将替换本卡直接调用 portable-pty 和系统 ssh 的捷径；本卡不扩大到 `AppServices` 或 core 会话服务。
4. 修订计划第 3 个提交指定验证命令 `cargo test -p tterm-gpui --lib`，但当前 `tterm-gpui` 清单没有 `[lib]` target，只有 binary target。执行该命令得到原始错误 `error: no library targets found in package 'tterm-gpui'`。实现已停止等待评估者决定改用 `cargo test -p tterm-gpui --bin tterm-gpui`，或先拆出 library target；未自行扩大范围。
5. `ColorRequest` 使用默认调色板而不是会话持有的副本；演示从不更换调色板，结果相同，P1-12 由会话服务提供真实副本。
6. `CursorBlinkingChanged` 被丢弃，因为视图从快照读取闪烁状态；该行为已在代码和本报告中标记为 P0 限制。
