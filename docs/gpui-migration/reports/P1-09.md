# P1-09 代码移入 tterm-core：设计与拆分计划

- 作者：评估者（Claude），2026-11-12，基于 `GPUI` 的 `56ab5308`（P1-07、P1-08 已合并）
- 适用：P1-09s（准备）、P1-09a1 与 P1-09a2（拆出适配层）、P1-09b（移动，分批派）
- 实施：Codex 按本计划逐卡实施。计划与代码对不上时停下，写进各卡报告的“偏差”，不要自行改设计。
- 工具：`scripts/migration/core-move-graph.py`（随本计划提交）。它按 `use` 与 `crate::`/`super::` 路径建文件级依赖图，`adapters`、`cycles`、`batches` 三个子命令分别用于第 2、3、4 节。它只是近似，最后以编译器为准。

## 1. 现状

`src-tauri/src` 有 437 个 `.rs` 文件，约 9.2 万行（含测试），`tterm-core` 约 6 千行。工具的统计（不含测试文件）：

- 77 个文件碰 Tauri（`tauri::`、`AppHandle`、`#[tauri::command]`、`State<'`、`Manager`、`Emitter`），叫**适配文件**；另有一组整体留在 Tauri 包的文件（工具里的 `STAY`：启动、事件与会话出口、平台适配、窗口胶水，见 2.1）。其余 247 个是**可移动文件**。
- **106 个可移动文件依赖适配文件**，依赖落在 43 个适配文件上。原因几乎都一样：P1-07 之后 command 已经很薄，但它和类型、服务函数写在同一个文件里（例如 `config/mod.rs` 既有 `AppConfig` 又有两个 command，被 23 个文件引用）。这些文件不拆开就一个也搬不走。
- **模块之间有环。** 按领域看，17 个领域（`backup`、`command_library`、`config`、`core`、`db`、`monitor`、`notification`、`profiles`、`prompt_scope`、`proxy`、`serial`、`sftp`、`ssh`、`sync`、`terminal`、`tunnel`、`zmodem`）互相依赖成一个环；按文件看，最大的环是 37 个文件（`ssh` 13、`sftp` 5、`core` 4、`proxy` 4、`serial` 3、`zmodem` 2、`monitor` 2、`profiles` 2、`terminal` 1、`prompt_scope.rs`），其余都只有 2 到 4 个文件。所以任务卡“每个领域一个只做移动的提交”做不到：同一个领域要分几批移动，37 个文件的环只能在一个提交里一起移动（第 4 节）。
- 按领域顺序移动也不行：`db/legacy_import.rs` 引用了几乎所有领域的存储函数，第一批移 `db` 就会把 105 个文件一起拖走。这个文件放到最后移动。

另外几处会在移动时出错，必须专门处理（第 5 节）：

- `src-tauri` 是 edition 2021，`tterm-core` 是 2024。代码换 edition 后，`if let` 与尾表达式里临时值的析构时机会变，锁的释放时间也可能跟着变。
- `config/update_channel.rs` 用 `env!("CARGO_PKG_VERSION")` 决定更新通道。移进 core 后，它读到的版本会变成 `tterm-core` 的 `0.1.0`。
- `include_str!` 的相对路径：`db/migrations.rs` 与 `proxy/approval.rs` 引用 `../../migrations/*.sql`；`terminal/shell_integration/`、`monitor/metrics/collect.sh`、`agent_integration/` 的 `hook_input.awk`、`opencode_tui.js`、`pi_extension.ts`；`config/tests.rs` 引用 `../../../src/lib/terminalFont.ts`。
- 6 个测试用 `env!("CARGO_MANIFEST_DIR")` 读 `src-tauri/src/event_sink/fixtures/*.json`，`#[path = …]` 指向测试文件的有 12 处。
- `scripts/migration/command-signatures.json` 记录了每个 command 所在的模块路径和 `generate_handler!` 的完整路径。command 换文件后，基线就对不上了。
- 名字冲突：Tauri 包的 `session`（标签页恢复数据）与 core 现有的 `session`（会话输出接口，P1-06）同名；两边都有 `sftp`。

## 2. 目标形态

### 2.1 什么留下，什么移走

P1-09 结束时，`src-tauri/src` 只剩：

1. `lib.rs`、`main.rs`、`migrate.rs`；
2. `STAY` 中的适配层：`platform/`、`event_sink*`、`session_sink*`、`app_paths.rs`、`app_identity.rs`、`main_window.rs`、`window_blur.rs`、`ime_focus.rs`、`clipboard_files.rs`、`drag_out/`；
3. 每个领域的 command 文件，里面只有 `#[tauri::command]` 函数，以及只为它们服务、必须碰 Tauri 的胶水（构造 `TauriEventSink`、`tauri::ipc::Response`、托盘菜单与窗口操作等）；
4. 只有 Tauri 才有的能力：`background/` 中的托盘菜单与窗口关闭处理、`updater.rs` 中调 `tauri-plugin-updater` 的部分、`window_state/` 中读写窗口几何的部分、`launch_dir.rs` 中转发到窗口的部分、`notification/` 与 `system_integration/` 中的 Tauri 部分。它们的状态类型与纯逻辑移进 core（GPUI 版也需要退出确认、隧道托盘状态、待安装更新等状态），胶水留下。

其余全部移进 `crates/tterm-core/src/`，**模块路径保持不变**：`src-tauri/src/ssh/client.rs` 移到 `crates/tterm-core/src/ssh/client.rs`，core 内部的 `crate::ssh::client` 引用不用改。例外有两个：

- Tauri 的 `session`（`session/mod.rs` 与 `session/scrollback.rs`）改名为 core 的 `session_restore`，避开 P1-06 的 `tterm_core::session`。
- `sftp` 并进 core 现有的 `sftp` 模块。core 的 `sftp/mod.rs` 现有 `conflict`、`entry`、`search` 三个子模块，文件名与 Tauri 包这边不冲突；`sftp/mod.rs` 两边的内容合并成一个。

`core` 这个模块名会变成 `tterm_core::core`。名字是重了，但改名会让大约 200 个文件的 `use` 跟着变，所以不改。

### 2.2 `AppServices`

`services/` 整体移进 core，成为 `tterm_core::services::AppServices`（P1-07 计划 2.1 节就是这样预定的）。`services/app.rs` 现在引用 `background`、`launch_dir`、`updater` 里的状态类型（`CloseBehaviorState`、`QuitState`、`ExitGuardState`、`TrayState`、`LaunchDirs`、`PendingUpdateDownloads`），这些类型由 P1-09a2 从适配文件里拆出来（第 3 节），随 `services` 一起移进 core。`scripts/migration/services-no-tauri.test.mjs` 的检查目录相应改成 `crates/tterm-core/src/services`。

### 2.3 可见性

- 移动的代码保留原来的 `pub(crate)`、`pub(super)`。只有被 Tauri 包（或 `tterm-gpui`）引用的项才改成 `pub`，以编译器报错为准，不要整片放宽。
- 每个移动提交在报告里列出“`pub(crate)` → `pub`”的项数，评估者会抽查每一项在 Tauri 包里都确实被引用。
- 不加 `pub use` 转导出（AGENTS.md）。Tauri 包从定义处导入：`use tterm_core::ssh::client::…`。
- 测试辅助代码（例如 `core/channel_test_support.rs`、`ssh/test_sshd.rs`）如果被 Tauri 包的测试使用，用 `#[cfg(any(test, feature = "test-support"))]`；这个 feature 已经存在，Tauri 包的 dev-dependencies 已经开启了它。

### 2.4 依赖

- 移进 core 的文件用到哪些 crate，就把哪些加进 `crates/tterm-core/Cargo.toml`。版本按 pins.md 第 2 条用 `=` 固定，固定到 `Cargo.lock` 里现在锁定的版本，features 与 `src-tauri/Cargo.toml` 一致；平台专属依赖放进对应的 `[target.'cfg(…)'.dependencies]`。
- `Cargo.lock` 里不能出现新的包或新的版本：`git diff Cargo.lock` 应该只有 `tterm-core` 的 `dependencies` 列表变长。
- Tauri 包里已经没人用的依赖在 b3 收尾时删掉；删的时候同样要求 `Cargo.lock` 里不出现新的包或版本（只会少掉 `tTerm` 的依赖边）。

## 3. P1-09a：把适配文件拆开（Tauri 包内部的移动）

目标是让 `python3 -I scripts/migration/core-move-graph.py adapters` 以状态 0 退出：没有任何可移动文件依赖适配文件或 `STAY` 文件。这一步不跨 crate，只在 `src-tauri/src` 里面移动代码，每个提交都必须能编译、测试通过。

### 3.1 规则

1. **逻辑留在原文件，Tauri 部分搬出去。** 这样引用类型和服务函数的 200 多个文件不用改 `use`，a1、a2 两张卡并行时也只会在 `lib.rs` 的 `generate_handler!` 里碰到一起。
2. Tauri 部分搬到哪里：
   - 来自 `D/mod.rs` 的，搬到 `D/commands.rs`；`D/commands.rs` 或 `D/commands/` 已经存在时，合并进去。
   - 来自 `D/name.rs` 的，搬到 `D/name_commands.rs`。已经有现成的同类文件时（`ssh/known_host_commands.rs`、`ssh/secret_commands.rs`、`zmodem/commands.rs`），合并进去。
   - 新文件由原来的父模块声明（`pub(crate) mod commands;`），`lib.rs` 的 `generate_handler!` 改成新路径。
3. **反过来的情况：command 文件里放着逻辑**，又被可移动文件引用。下面这些要把逻辑项搬出 command 文件，放进同目录里按内容命名的模块（类型优先放进现有的 `types.rs`、`models.rs`），引用方的 `use` 跟着改：
   - `command_library/commands.rs`：`SaveCommandInput` 放进 `models.rs`。
   - `profiles/commands.rs`：`TestConnectionResult` 放进 `types.rs`。
   - `tunnel/commands.rs`：大部分是逻辑（`TunnelManager`、`TunnelContext`、`start_rule`、`start_unattended`、各 `*_service`），整个文件 `git mv` 成 `tunnel/manager.rs`，8 个 command 搬进新建的 `tunnel/commands.rs`。
   - `core/commands/mod.rs`：`stop_pty_session` 只被 `core/commands/create.rs` 用到，两者都是 command 层，保留不动。如果工具在 a1 做完之后还把它列为阻塞，就把它放进 `core/session/`。
   - `sftp/internal/api/upload/commands/mod.rs`（`UploadBatch`、`collect_upload_conflicts`、`resolve_upload_target`、`run`）与 `sftp/internal/api/delete/commands/mod.rs`（`delete_directory_recursive`）：逻辑搬进同目录的 `batch.rs` 或新建一个按内容命名的模块。
4. **逻辑依赖 Tauri 专属能力的地方**，依赖方向要倒过来，不能把 Tauri 类型带进逻辑：
   - 调 `app_identity::get()`、`app_paths::get()` 的逻辑（`backup/mod.rs`、`backup/remote.rs`、`sftp/internal/api/external/mod.rs`）：改为从 `AppServices` 的 `shared.identity`、`shared.paths` 取。
   - `config/save.rs` 保存配置后调用 `background::apply_config`、`system_integration::apply_config`、`TrayContext`：把这几步副作用挪到保存配置的 command 里，在服务函数返回之后执行。执行顺序保持原样，报告里写出改前改后的调用顺序。
   - `sftp/internal/api/search.rs` 在逻辑里构造 `TauriSearchResultSink`：改为由 command 构造，作为参数传进去。函数原本就接受 `ResultSink`，见工具输出。
   - `tunnel` 用 `background::tray::TrayContext` 刷新托盘：改为调用 `shared.platform.tray`（P1-08 的 `Tray` trait）。trait 里如果没有对应的方法，**停下报告**，不要往 trait 里加方法。
   - 以上没有列到、又不能只靠挪动解决的，停下报告，写清是哪个项、谁在用。
5. **状态类型从适配文件里拆出来**（2.2 节）：`background/mod.rs` 的 `CloseBehaviorState`、`background/quit.rs` 的 `QuitState`、`background/exit_guard.rs` 的 `ExitGuardState`、`background/tray/mod.rs` 的 `TrayState`、`launch_dir.rs` 的 `LaunchDirs`、`updater.rs` 的 `PendingUpdateDownloads`、`window_state/mod.rs` 的 `Bounds`。按规则 1 处理：类型和纯逻辑留在原文件，Tauri 部分搬出去。原文件如果只剩 Tauri 部分，就反过来，把类型移到新文件 `D/state.rs`，这时引用方的 `use` 跟着改。
6. **测试**：`terminal/io_batcher.rs` 文件末尾有一个 `#[cfg(test)] fn test_sink`，用 `tauri::test::mock_builder` 构造 `TauriSessionSink`，所以工具把整个文件算成适配文件。改为使用 core 的记录型 sink `tterm_core::session::recording::RecordingSessionSink`（`test-support`）；如果有测试断言的是 Tauri 事件的 wire 格式，就把它移到 `session_sink/tests.rs`。这条在 a1 里做，因为它决定 `io_batcher.rs` 能不能算可移动文件。
7. 一个领域一个提交（例如 `:truck: split the config commands out of config/mod.rs`），提交里只有代码的移动与必要的 `use`、路径改动。规则 4 的倒转单独提交，用 `:recycle:`。

### 4.1 每个移动提交

1. `git mv` 文件（以及同目录下的测试文件、`include_str!` 引用的资源）到 `crates/tterm-core/src/` 的同一路径（`session` 例外，见 2.1）。
2. 在 core 的父模块里加 `mod` 声明，在 Tauri 包的父模块里删掉对应的声明。
3. 改引用：Tauri 包里的 `crate::x::y` 改成 `tterm_core::x::y`；core 内部的引用不变。
4. 按 2.3 节只放宽编译器要求放宽的可见性，按 2.4 节补依赖。
5. 提交前跑 `cargo check --workspace --all-targets`（`CARGO_BUILD_JOBS=3`）。每批跑一次完整测试代价太高，每移完一个领域，或每 5 个提交，跑一次 `cargo test --workspace`。

**移动提交的 `git diff -M` 只能有这些变化：** 路径、`use` 与 `crate::` 路径、`mod` 声明、可见性修饰符、`Cargo.toml`、`include_str!` 与 `#[path]` 的相对路径。其他改动（为了能编译而改的逻辑、倒转依赖）都单独提交，并在报告里说明。评估者先看 `git show -M --stat <提交>`，确认每个文件都是重命名且相似度在 90% 以上；再看 `git show -M -U0 <提交> -- '*.rs' | grep -E '^[-+][^-+]' | grep -vE '^[-+]\s*(use |pub|mod |#\[cfg|#\[path|\}|crate::|tterm_core::|include_str!)'`，剩下的每一行都要能用上面这几类变化解释。

   - 然后 `cargo fmt --all`（style edition 2024 的 import 排序不一样），单独一个提交，只有格式变化。
   - `cargo fix` 只会提示、不会自动改的 lint 要逐个看：`tail_expr_drop_order` 与 `if_let_rescope`，重点是持有锁（`Mutex`、`RwLock` 的 guard）或 `RefCell` 借用的位置。报告列出每一处：文件、行号、析构顺序变了会怎样、如何处理（保持原顺序就显式 `drop` 或改成 `match`，并写明理由）。
   - 其他 2024 变化：`std::env::set_var`/`remove_var` 要 `unsafe`（检查测试代码）、`impl Trait` 捕获规则、`unsafe extern`、`#[unsafe(no_mangle)]`、never 类型回退、`gen` 关键字。工具自动改的列出数量，手工改的逐个说明。
2. **`command-signatures` 不再比较模块路径。** IPC 契约只看 command 的名字、属性、参数和返回类型；`generate_handler!` 的列表只比较最后一段名字。修改 `scripts/migration/command-signatures.mjs` 的比较逻辑，基线里也去掉 `module` 字段，同时在 `command-signatures.test.mjs` 里加两条测试：只换模块路径时检查通过；参数类型改变时检查失败。
3. **把迁移检查接进 `pnpm test`**：在 `package.json` 的 `test` 后面加 `node --test scripts/migration/*.test.mjs`，让 P1-07 留下的三项检查（command 签名、托管状态、services 不碰 Tauri）在 CI 里跑起来。如果某项检查现在就失败，停下报告，不要修改基线。
4. **记录测试基线**：`cargo test --workspace -- --list` 按包统计 `: test` 的数目，ignored 的测试单独用 `-- --ignored --list` 统计，写进报告。P1-09 的验收“测试数量不少于移动前”以这里为准。
5. **`update_channel` 不再读编译期版本**（2026-11-12 修订）：调用方是 `AppConfig::default()` 和 serde 的 `default`，两处都拿不到 `AppServices`，所以改为由客户端在运行时安装版本。`tterm_core::identity` 用进程级的 `OnceLock` 提供 `install_app_version` 与 `app_version`；Tauri 版在 `run()` 最开头，第一次加载配置之前，安装 `env!("CARGO_PKG_VERSION")`。没有安装时返回 `"stable"`。不能让 core 自己读版本：`release-dev-beta.yml` 只在构建时改写 `src-tauri/Cargo.toml` 的版本号。测试只覆盖纯函数 `update_channel_for_version`。

## 7. 风险

- **edition 升级。** 析构顺序的变化在测试里不一定看得出来，所以 5.1 要求逐处说明，评估者会逐处复核持锁的位置。
- **37 个文件一起移动。** 这个提交很大，但只是移动。评估者用 `git diff -M` 的过滤结果审它，不逐行读。
- **合并冲突。** P1-11 的几组卡同时往 `crates/tterm-core/src/lib.rs` 加模块，只会在 `mod` 那几行冲突，好解决。真正的风险在 `dev`：在 `dev` 上改 `src-tauri/src` 的提交（例如 P1-10），合进 `GPUI` 时文件已经搬走了。U-03 同步前先看 `dev` 动了哪些后端文件，冲突按新位置解决。
- **工具的盲区。** 宏生成的路径、通配导入（`use super::*`）、`#[path]` 指向的文件，工具都看不到。它报 0 不代表一定能编译，编译通过才算数。
