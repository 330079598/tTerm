# P1-01 应用路径注入（macOS）

## 结论

完成工作 1 至 3，待评估。`AppPaths` 放在 tterm-core；原生构造使用 Tauri 已锁定的 `dirs 7.0.0`，Tauri 适配构造使用真实 PathResolver。应用标识由调用者传入，目录、子目录及持久化格式不变。Windows 待补（决策 016），Linux 推迟（决策 016）。

### 两种构造的比较依据

可以使用 `tauri::test`，无须降级为仅对照源码规则的测试。锁定版本为 Tauri 2.12.5；本机 registry 源码前缀是 `~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/`：

- `tauri-2.12.5/src/path/desktop.rs:9`：`PathResolver<R>` 对所有 Runtime 共用实现，没有 mock 专用目录；`:239`、`:251`、`:265`、`:278`、`:296` 为应用目录；`:119` 下载、`:313` 临时目录。
- `tauri-2.12.5/src/test/mod.rs:109` 创建可配置 Context，`:166` 创建 MockRuntime builder；Tauri 自身 `path/desktop.rs:368` 的测试也用这个构造。
- `tauri-2.12.5/Cargo.toml:160` 依赖 `dirs 7`。本卡直接复用锁文件内 `dirs 7.0.0`，三平台基础路径都交给同一个目录库处理。
- macOS：config/data/local_data 为 `~/Library/Application Support/<标识>`，cache 为 `~/Library/Caches/<标识>`，诊断日志为 `~/Library/Logs/<标识>`。
- Windows：config/data 为 RoamingAppData，local_data/cache 为 LocalAppData，诊断日志为 local_data 下的 `logs`。
- Linux：config/data/cache 遵循 dirs 的 XDG 规则；local_data 与 data 相同；诊断日志在 local_data 下 `logs`。相对 XDG 值不作绝对目录使用。
- 终端录制日志仍为 **config/logs** 或用户配置目录，不能改用 app_log_dir，否则会改变现有目录位置。
- `tauri_directory_override_remains_authoritative` 另外验证 Tauri 的 root override，包括 `caches` / `logs` 子目录。原生默认构造不声称实现 Tauri 特有的 override 配置；需要自定义目录的调用者可显式构造 AppPaths。

比较测试不启动生产应用、不注册生产 setup、不读写三个真实标识的应用目录；只求值 PathBuf。Linux 的 dirs::download_dir 可能读取 XDG 用户目录配置文件，属于系统用户目录解析，不读取应用连接。

## 评估：第 2 轮修正（2026-11-10）

第 1 轮的路径设计、构造比较、路径清单和隔离启动证据获评通过；本轮只修复未注册 AppPaths 时 `state()` 会 panic 的问题。提交摘要为 `:bug: Return an error when application paths are not initialized`（本节所在提交），没有修改初始化位置、目录规则、command 或持久化格式。

### 改动与回归测试

- `src-tauri/src/app_paths.rs:37` 改为泛型 Runtime 的 `get`，通过 `try_state` 返回 `Result<State<'_, AppPaths>, String>`；未注册时返回 `Application directories are not ready yet`。泛型使同一个生产访问函数可以直接接受 MockRuntime 测试。
- 5 个 Result 调用点使用 `?`：`updater.rs:304`、`migrate.rs:73`、`system_integration/mod.rs:319`、`sftp/internal/api/external/local.rs:94`、`ssh/secret_store/mod.rs:450`。
- `launch_dir.rs:139` 的 Option 调用点使用 `.ok()?`，路径状态不可用时返回 `None`，不创建缓存目录或标记文件、不打印错误。
- `app_paths::tests::paths_before_initialization_return_an_error` 创建未调用 initialize、未注册 AppPaths 的 mock 应用，直接调用生产 `get` 并断言错误文本。若发生 panic 测试会失败；测试不访问真实应用目录。生产改动没有添加 unwrap/expect、allow/ignore 或新的 panic。

### single-instance 与 launch_dir 的先后关系

源码核对结论：**不能假定 single-instance 回调一定晚于 initialize；当前 second-launch 回调没有调用 marker_path。**

1. `src-tauri/src/lib.rs:91` 最先注册 single-instance 插件；`:135` 的 `LaunchDirs` 用 Builder.manage 注册。Tauri 2.12.5 `src/app.rs:2425` 将 builder state 交给 AppManager，`:2607` 在 build 内初始化插件；应用 setup 是之后 `Ready` 时的 `src/app.rs:1442` 调用 `:2688` 的 setup，最终在 `:2697` 调用项目 setup。源码位置均相对于第一轮已记录的 registry 前缀。
2. `tauri-plugin-single-instance-2.5.2/src/platform_impl/macos.rs:22` 的插件 setup 在 `:35` 启动监听，`:100` spawn 异步任务，`:111` 收到连接后直接调用 callback，没有等待项目 initialize 的同步屏障。因此 macOS 第二次启动请求可以早于项目 setup 到达。Linux 的 `platform_impl/linux.rs:36` 在插件 setup 注册 D-Bus 服务，`:24` 直接调用 callback；Windows 的 `platform_impl/windows.rs:57` 在插件 setup 注册接收窗口，`:166` 在窗口消息处理器调用 callback；也不应把 AppPaths 注册当成插件回调的前置条件。本轮没有在 Windows/Linux 真机运行时序实验。
3. 本项目的回调顺序为 `lib.rs:92` → `launch_dir::open_from_second_launch`（`launch_dir.rs:61`）→ `requested_dirs` → `queue`（`:126`），再调用 `background::show_main_window`。这条路径不调用 `marker_path`、不读取 AppPaths；LaunchDirs 在 builder state 内，已经早于插件初始化注册。主窗口尚未创建时，`background/mod.rs:96` 的窗口查找返回 None，不执行窗口操作。因而不能说“当前 second-launch 会因 AppPaths 未就绪而失败”，它仍然排队目录并发出原事件。
4. `lib.rs:360` 的 initialize 用 `?` 成功返回后，下一行 `:361` 才调用 `launch_dir::open_from_startup`，其中 `:48` 调用 marker_path；这条常规启动路径一定先注入路径。另一个 marker_path 调用是 `launch_dir.rs:71` 的 forget_startup_dir，由 `lib.rs:442` 的退出事件调用；不依赖其时序保证安全，本轮 `.ok()?` 已覆盖未就绪情况。
5. 如果 marker_path 在 initialize 前被调用，新的处理会安静地返回 None：forget_startup_dir 随即返回；open_from_startup 则跳过标记检查/写入，继续 queue。这与改动前 **路径解析失败时** 的 `.ok()?` 分支一致，不会崩溃或因标记失败丢弃启动目录。需要准确区分：改动前 Tauri resolver 在 setup 前也可能成功；本轮不会提前解析或初始化路径，因此“未初始化就返回 None”是新增状态下的安全回退，并不声称所有 setup 前调用都与旧版成功解析的情况完全等价。当前 second-launch 不走该分支，常规启动也在 initialize 后，未改变现有正常调用链的结果。
