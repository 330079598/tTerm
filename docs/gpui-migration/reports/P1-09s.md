#### `tail_expr_drop_order` 逐处审查

`cargo fix` 没有自动改写 `tail_expr_drop_order`：日志里 lib 生成 81 条、lib test 生成 92 条（其中 81 条与 lib 重复），按 `文件:行:列` 去重后为下表 81 个位置。`if_let_rescope` 本身为 0 条；下表中少数 `if let`/`while let` 的 scrutinee 重排仍由 `tail_expr_drop_order` 报出。下表的行号来自 `cargo fix` 运行时的 2021 源码，发生在 `cargo clippy --fix` 和 `cargo fmt` 之前，因此与当前文件行号有偏移；路径相对于 `src-tauri/src`。

### 2. command-signatures 去掉模块路径

`parseCommands(source)` 现在只解析源码，不再接收文件路径，也不再产生 `module` 字段。`parseHandlers` 先找到 `tauri::generate_handler!` 的 `[`，用新增的 `findMatchingBracket` 找到配对的 `]`，从而不会在第一个 `#[cfg(...)]` 的 `]` 处截断；每项去掉属性后取 `::` 的最后一段，排序后与基线比较。基线重新生成后为 211 个 command、210 个 handler。

新增的两条测试在 `scripts/migration/command-signatures.test.mjs`：

- `moving a command to another file keeps its signature`：把同一段 command 放进“旧文件”和“另一个文件”的内存源码，`parseCommands` 结果相同。
- `changing a command parameter type changes its signature`：把参数类型从 `u16` 改成 `u32`，结果不同。

### 5. `update_channel` 改为接受版本参数

现状与调用点：

```text
src-tauri/src/config/update_channel.rs:5:  pub(super) fn default_update_channel() -> String

src-tauri/src/config/mod.rs:121:               pub update_channel: String
```

`rg` 显示它只有这两个调用方：

- `AppConfig::default()`（`src-tauri/src/config/defaults.rs:253` 起）直接调用 `default_update_channel()`。`Default::default()` 没有参数，拿不到 `AppServices`。
- 配置文件反序列化时，`#[serde(default = "update_channel::default_update_channel")]` 要求一个无参数、返回 `String` 的函数，同样拿不到 `AppServices`。

`AppServices.shared.identity.version` 本身存在（`src-tauri/src/services/shared.rs:13`，`AppIdentity` 在 `src-tauri/src/app_identity.rs:12` 初始化），但只能通过 `AppHandle` 的 `try_state::<Arc<AppServices>>()` 或已构建的容器取得；配置默认值在容器可用之前就要决定 `update_channel`，没有可用的注入点。因此按任务卡的硬性规则停下：没有改 `update_channel`，没有改配置加载顺序，也没有用编译期版本或前端默认值凑。现有测试已经覆盖 `0.8.0-beta.1 -> beta-dev`（`src-tauri/src/config/update_channel.rs:28`），如果后续改变注入方式，可以复用该测试。

建议另开一张卡，明确“版本从哪里进入配置默认值”：例如在 `AppServices` 建好之后对配置做一次归一化，或把版本作为 `AppConfig` 构造参数传入；这需要设计决定，本卡不自行选择。

## 偏差

- **旧基线 handler 被解析器截断。** 旧 `command-signatures.json` 的 `handlers` 只有 52 项，其中 1 项是 `#[cfg(any(...))` 这样的属性片段，实际有效 handler 为 51 项；原因是旧解析器用正则 `\[([\s\S]*?)\]`，在第一个 `#[cfg(...)]` 的 `]` 处截断。新的括号配对解析器恢复了 159 个此前漏掉的 handler，得到 210 项。去掉 `module` 后 211 个 command 与旧基线完全相同，旧 51 个有效 handler 也全部保留；因此任务卡“去掉 module、截短 handler 后完全相同”的要求对 command 成立，对 handler 集合不成立，旧基线本身不完整。建议保留新基线，不修改设计。
- **edition 提交里包含 87 处 clippy 自动改写。** 2024 的 let-chain 让 clippy 报出 86 个 `collapsible_if` 和 1 个 `let_and_return`；为了在不用 `allow` 的前提下通过 `-D warnings`，在 edition 提交里运行了 `cargo clippy --fix`（61 个文件、87 处），随后 clippy 通过。任务卡说 edition 提交里只应有 `cargo fix` 和逐处处理的改动；这些是 2024 引发的机械改写，但确实超出了字面范围，需评估者确认是否接受，或要求拆成单独提交。
- **第 5 项未完成。** `update_channel` 的唯一调用方是 `AppConfig::default()` 与 serde `default`，两者都拿不到 `AppServices`。按硬性规则没有改代码、没有用别的办法凑；建议另开卡调整配置默认值的注入方式。
- **测试基线包含 64 个 ignored 测试。** 它们是源码中已有的 `#[ignore]`，不是本轮用 `--skip` 跳过的；本报告按任务卡要求单独统计，未运行。
- **平台验证按决策 016 未做。** Windows 与 Linux 的代码只在文本层面审计，没有编译或运行；详见平台表。
- **Tauri 版未运行。** 按决策 017，本轮不运行 Tauri，也不读写 `com.stone.tTerm` 或 `com.stone.tTerm.dev` 的数据目录。
