## 参照行为调查

### xterm.js 6.0.0

本 worktree 的 `node_modules/@xterm/xterm/package.json` 为 `6.0.0`。滚动和淘汰的关键路径如下：

- [`common/services/BufferService.ts:64-121`](../../node_modules/@xterm/xterm/src/common/services/BufferService.ts) 的 `scroll` 在 `scrollTop === 0` 时检查 `buffer.lines.isFull`（80 行）。未满时增加 `ybase`，只有用户没有向上滚时才增加 `ydisp`（93-99 行）；已满且用户正在滚动时不增加 `ybase`，而执行 `buffer.ydisp = Math.max(buffer.ydisp - 1, 0)`（100-105 行），注释明确说明这是为了在顶部淘汰时保持文字稳定。用户不在滚动状态时仍把 `ydisp` 置为 `ybase`（115-119 行）。
- [`common/services/BufferService.ts:131-151`](../../node_modules/@xterm/xterm/src/common/services/BufferService.ts) 将用户滚动位置钳在 `0..ybase`；到达底部时清除 `isUserScrolling`。因此 `ydisp` 是视口起点，越接近 0 越靠近最旧内容；当 `ydisp` 已为 0 时继续淘汰无法再补偿，锚定行被淘汰后视口必然向新内容移动。
- [`common/CircularList.ts:108-136`](../../node_modules/@xterm/xterm/src/common/CircularList.ts) 的满环形缓冲 `push`/`recycle` 淘汰一个首行并触发 `onTrim`；[`common/CircularList.ts:188-199`](../../node_modules/@xterm/xterm/src/common/CircularList.ts) 的 `trimStart` 同样从头部移除并发出淘汰数量。
- [`common/buffer/Buffer.ts:221-233`](../../node_modules/@xterm/xterm/src/common/buffer/Buffer.ts) 在 resize 缩短容量时从顶部 trim，并同时把 `ybase`、`ydisp`、保存的光标位置减去淘汰量并钳制。这个路径说明 xterm.js 把“坐标整体前移”与“视口位置调整”作为同一操作处理。

结论：xterm.js 并不是靠内容比对找行。回滚区未满时用户上翻，`ydisp` 不跟着 `ybase` 增长；回滚区已满时，每淘汰一行把 `ydisp` 减一，直到 `ydisp == 0`。只有锚定行已被淘汰，才接受视口内容移动。它的滚动条位置使用 `ydisp/ybase`，而缓存/标记若持有绝对索引，必须响应 `onTrim` 的淘汰数量。

## 回滚区写满后的锚定候选

现有设计和模型使用同一坐标关系：

```text
screen_row = absolute_line + display_offset
absolute_line = screen_row - display_offset
```

因此，任何候选方案都必须在模型中保存旧视口的锚点 `A = old_screen_row - old_display_offset`。如果输出后能在新快照第 `S` 行找到同一锚点，新的显示偏移应计算为 `new_display_offset = S - A`，再按 `[0, history_size]` 钳制；找不到锚点时必须走候选方案定义的确定性失败路径。不能在视图层单独保存“第几行”，因为淘汰会改变它指向的绝对内容。

### 候选 A：比对视口内容推算移动行数

在写满边界附近保存可见行的完整内容指纹（列数、字符、宽字符标志和语义样式，必要时再保存相邻多行窗口）。输出并取新快照后，在旧/新可见行之间寻找最长连续匹配，优先使用多行窗口而不是单行。对旧锚点所在行，按上面的坐标式得到 `A`；若匹配窗口把它定位到新屏幕行 `S`，将偏移设为 `S - A`。等价地，也可以先得到视口移动量 `d = S - old_S`，再使用 `new_display_offset = old_display_offset + d`，但最终仍必须通过绝对行换算和边界钳制校验。

优点是无需改 Alacritty，能够在锚点仍出现在新视口时保持用户正在阅读的内容，并可直接测试“历史不丢失、不跳行”。但调查证明 Alacritty 已经在模型内部完成了这件事，因此在 tTerm 再做内容比对是重复逻辑。失败情形还包括重复行/空行造成多个匹配、同内容但不同样式的行误配、宽字符或组合字符序列规范化差异、输出批次大于可见窗口导致没有重叠窗口，以及指纹碰撞。除非未来更换没有原生 display offset 的内核，否则不推荐此候选。

### 候选 B：接受与 xterm.js 一致的退化行为

不推算移动行数，也不改变 Alacritty 内核。输出后直接采用模型读到的 `display_offset` 和 `history_size`，把偏移钳制到 `[0, history_size]`，仍用 `absolute_line = screen_row - display_offset` 做全部绘制、选区和搜索换算。锚点未被淘汰时，普通输出沿用模型已经增加的偏移；锚点被淘汰时不伪造行身份，接受视口按钳制后的坐标发生确定性位移，并把整屏标记为失效。该路径的测试应固定“淘汰发生在哪一批、旧锚点不可用时显示哪一行”，以便与现有 xterm.js 版本逐项对照。

优点是实现和内核边界清楚，不会因为重复内容把用户带到错误的历史行，也不需要内容指纹。若只照字面“什么都不做”，则会丢掉上层缓存、选区、搜索标记和滚动条标记所需的淘汰信息；因此需要下面的 B+ 修订。

### 推荐 B+：沿用 Alacritty 原生偏移，显式传播淘汰元数据

B+ 不再比对视口内容，也不改 Alacritty。模型保留 `display_offset` 的现有语义，并在每次主屏滚动/历史淘汰时产生单调的淘汰世代或 `evicted_lines` 元数据。快照把该世代、历史容量和显示偏移一起交给视图：

1. 锚点仍在历史中时，沿用 Alacritty 已经完成的 offset 增加；视口内容保持不变，三类回归测试应断言首行/末行内容而不是只断言 offset。
2. 淘汰发生时，按 `evicted_lines` 让选区、搜索匹配、滚动条搜索标记和任何 retained row 缓存的绝对坐标整体前移，或按世代使其失效；不能用“history_size 是否变化”作为唯一失效条件，因为容量已满时它保持不变。
3. 当锚定行已经淘汰（本实验中的 `L07`→`L08`），接受与 xterm.js 相同的确定性退化：offset 保持上限、视口随新内容移动、整屏刷新；同时保留“有新输出”状态，避免把坐标失效误判成空白帧或拼接快照。
4. 滚动条滑块继续用 `display_offset/history_size` 计算；历史满容量后滑块总几何不因 `history_size` 数值变化而跳动，搜索标记等绝对坐标则按淘汰世代重定位或清除。选区/搜索若跨过最旧行，按模型已有的范围裁剪规则变为部分可见或失效，并有测试固定结果。

B+ 与 xterm.js 的逐项差异：

| 项目 | xterm.js 6.0.0 | B+ 目标 | 差异处理 |
| --- | --- | --- | --- |
| 用户上翻时持续输出 | 满缓冲每淘汰一行把 `ydisp` 减 1；到 0 后内容移动 | Alacritty 每次 `scroll_up` 把 `display_offset` 加 1；到 `max_scroll_limit` 后内容移动 | 坐标方向相反但视觉行为一致，测试比较内容序列 |
| 绝对行/标记 | `CircularList.onTrim` 提供淘汰数量；Marker 随 trim 减行并在越界时销毁（`Buffer.ts:627-634`） | Alacritty 不公开淘汰计数；B+ 新增模型快照元数据/世代 | 这是 tTerm 真正需要补的接口 |
| 缓存失效 | xterm 的 buffer/viewport 直接读当前环形行，避免按旧绝对行拼接 | B+ 在世代推进时重定位或失效 retained rows、搜索和标记 | 覆盖 nyaterm #923/#1043 的 stale cache/flicker 风险 |
| 锚定行被淘汰 | `ydisp == 0` 后接受视口前移 | `display_offset == max_scroll_limit` 后接受视口前移 | 覆盖 nyaterm #985 的明确退化边界 |

推荐采用 B+，而不是原候选 A 或“什么都不做”的 B：内核已经给出正确的可保持阶段，缺口是把淘汰事件传到上层坐标和缓存，而不是再次猜测行移动。

## 偏差

1. 本轮开始时本机直接访问 nyaterm GitHub URL 曾失败，原始错误为：`The SSL connection could not be established, see inner exception.` 评估者随后提供了三个 issue 的原文文件，本轮已读取并按“nyaterm issue 对照”归纳；没有把最初的联网失败继续当作未读阻塞。
2. 任务卡的“搜索标记”在现有 GPUI 原型中没有独立标记数据结构或绘制入口；本轮只完成滚动条几何和淘汰世代失效，没有扩展 P2-07 搜索功能。建议后续把搜索标记的视觉/交互对齐拆到搜索卡，并以本报告的 `scrollback_generation` 作为失效依据。
3. 真实窗口拖拽、滚动条截图、快速输出无闪烁的视觉证据尚未执行；按环境规则标为 `[人工]`，不能由模型测试替代。
4. 代码路径与 2026-11-01 卡片行号已有变化：当前滚动模型位于 `crates/tterm-terminal/src/terminal.rs` 与 `snapshot.rs`，视图滚轮位于 `crates/tterm-terminal-view/src/view/scroll.rs`、`wheel.rs`；本轮未因路径变化扩大工作范围。
