# 验收协议

> 日期：2026-11-05。评估者：Claude。决定权：任务卡的“通过”由评估者给出；关卡 G1–G4 由评估者给出建议，最终由你确认。
> 本文把 [README 第 7 节](README.md#7-评估方式)的评估方式落成可执行的规则和数字。

## 1. 角色

| 角色   | 谁         | 做什么                                                         |
| ------ | ---------- | -------------------------------------------------------------- |
| 执行者 | agent 或你 | 按任务卡实现，写报告，附证据                                   |
| 评估者 | Claude     | 复跑检查、核对证据、给结论；不在被评估的分支上改代码           |
| 验证人 | 你         | 执行 `[人工]` 步骤：真实设备、输入法、远程桌面、签名、安装升级 |
| 决策人 | 你         | 确认关卡结论；批准第 4 节以外的界面例外；批准放弃某个功能      |

评估者不能替代验证人：输入法候选框位置、无 GPU 机器上的手感、安装包在真实系统上的表现，只能由验证人在设备上做，评估者根据录屏、日志和数据判断。没有这些证据的项记为“未验证”。

## 2. 每张卡的评估步骤

评估者按以下顺序检查，前一步不通过就不再往下：

1. **范围。** 改动只涉及任务卡列出的内容；没有夹带的重构或行为变化；纯移动的提交里没有修改（`git diff -M --stat` 与逐提交检查）。
2. **检查。** 在干净的检出中重跑 AGENTS.md 的全部检查（cargo 命令改为在仓库根加 `--workspace`）。没有新增的 `allow`、`expect`、`eslint-disable`，大小基线没有新增或上调。
3. **验收条件。** 逐条核对任务卡的验收条件，每条都有可复现的证据：命令与输出、测试名、截图或录屏路径。
4. **界面对齐**（含界面的卡）。运行 `tterm-parity compare`，按 [ui-parity.md 第 5.2 节](ui-parity.md#52-通过门槛macosdpr-2)的门槛判定。
5. **行为对齐**（功能卡）。`feature-matrix.md` 中对应行更新为“对齐”，证据列有对照测试或录屏；从 React 测试移植来的用例全部通过。
6. **第三方代码。** 复制的文件有来源头注释，已登记到 `third-party.md`，许可兼容。
7. **报告。** 未完成和未验证的部分如实列出。

结论只有三种：

| 结论   | 条件                                                                     | 之后                               |
| ------ | ------------------------------------------------------------------------ | ---------------------------------- |
| 通过   | 全部验收条件满足；“未验证”项都不属于该卡的必需平台                       | 合并；更新 `status.md`             |
| 需修改 | 有可以在同一分支修好的问题                                               | 列出具体条目，执行者在同一分支继续 |
| 驳回   | 做法本身不对（违反架构约定、改了持久化格式、绕过检查），或范围偏离任务卡 | 说明原因，重新领卡或先改卡         |

## 3. 通用门槛

除任务卡自身的条件外，以下门槛对所有卡生效：

- **测试是行为测试。** 新增测试断言用户可见的结果或对外接口；只断言内部字段的测试不计入覆盖。
- **界面线程不阻塞。** 文件、数据库、钥匙串、加密、网络在后台执行；评估者抽查新增的事件处理函数。
- **空闲不重绘。** 含动画或定时刷新的视图，窗口空闲且没有动画时帧数为零（用 GPUI profiler 或 `renderer_probe` 记录 10 秒）。
- **文案。** 所有用户可见文字经过 `tterm-i18n`；en 与 zh 都有对应的键（复数后缀归一化后比较）。
- **数据隔离。** 开发版只读写 `com.stone.tTerm.gpui-dev`。

## 4. 关卡标准

关卡结论由评估者写在 `decisions/` 中，你确认后生效。

### G1 技术验证通过，进入 P1

- P0 中 G1 必需的卡全部通过，包括新增的 P0-24、P0-25、P0-26。
- 原型在三平台都能运行 vim、tmux、htop 和一个 AI TUI，无错乱。
- 输入法：macOS 与 Windows 系统中文输入法全部场景通过；Linux 四个组合中至少 X11+fcitx5 与 Wayland+fcitx5 通过，没通过的写明是否阻塞 Linux 发布。
- 无 GPU 环境：空闲 CPU < 2%；持续输出时的 CPU 不高于 Tauri 版的 1.5 倍；不满足时要有确定的结论：做降级方案，或明确不支持该环境。
- 8 个 UI 原语达到界面对齐门槛。
- Tauri 版能自动升级到 GPUI 程序，三平台都有证据。
- 重新估算的工期写入 P0-22。

### G2 终端可以日常使用

- 迁移计划第 9 节终端相关场景全部有数据，P95 帧耗时 ≤ 16.7ms（60Hz，约定的硬件与负载）。
- 持续输出 30 分钟内存有界；回滚区写满后浏览历史不闪烁、不跳行（nyaterm #1043 的场景）。
- 终端查询只有一个应答方，有测试证明。
- 旧版 SerializeAddon 快照可以恢复显示。
- 终端区域的界面对齐全部通过。

### G3 工作区可以日常使用

- 标签、分屏、拖动、快捷键、主题与工作区恢复在功能矩阵中全部“对齐”。
- 工作区相关屏幕全部达到界面对齐门槛。
- 你用 GPUI 版连续日常使用 3 个工作日，记录的问题没有阻塞级。

### G4 正式切换

- `feature-matrix.md` 中没有“未开始”或“进行中”；“明确放弃”的每一项都有你的确认。
- `screens.md` 中全部屏幕达到门槛，例外都已登记并获批准。
- 性能：迁移计划第 9 节的指标与 P0-01 基线对比，主要指标没有显著退化（劣于基线 10% 以上视为退化），至少一项核心收益达到 P0-22 约定的幅度。
- 数据：从真实备份导入的独立数据目录完成升级演练，主密码、系统凭据、主题、工作区、同步都正常；回退演练成功。
- 更新：beta 渠道用户至少完成一轮 Tauri → GPUI 的自动升级，没有失败报告。
- 三平台交互验收（P5-07）完成。

## 5. 报告中的证据要求

| 证据类型 | 要求                                                     |
| -------- | -------------------------------------------------------- |
| 命令输出 | 命令、工作目录、提交哈希、平台；输出可截断，但保留结果行 |
| 截图     | 文件路径；注明平台、显示器、缩放；对比截图由工具生成     |
| 录屏     | 涉及输入法、拖动、动画、安装升级时必须有；文件路径与时长 |
| 性能数据 | CSV，按 P0-01 的列格式；同时给出 Tauri 基线的同口径数据  |
| 人工结果 | 验证人、日期、设备与系统版本、步骤、结果；失败时附日志   |

评估者会抽查：至少重跑一条命令、复算一个数字、重新生成一屏对比报告。复现不出来的证据视为没有证据。
